# 選択済み原文を保った残予算の利用（未採用）

捕捉済みの題材1で、抽象費用は120,000文字を使い切った一方、実本文はそれより短い。欠落した3097行は最後まで正の価値を持ち、最終限界費用73文字で予算外になった。単独候補が選ばれたため残予算を使えなかった、という仮説はnative再生で棄却済みである。

実験前に次の規則を固定する。最初の選択を保存し、既存のfile fingerprint・DB・Work・観測Occurrenceがそのファイルの出典枠に全て存在する原文行だけを追加可能にする。既に覆ったcueの重複加点を除き、同じ整数重みと同じ選択器で残予算を使う。新しい所有者・ファイル・出典を追加せず、比較のたびに描画やJSON生成をしない。最終本文を独立に検査し、既存原文・出典を失わず両方の上限を守った場合だけ候補として記録する。必要範囲の人手ラベルは後の監査にのみ使う。

以前失敗した、全ての比較で実描画費用を計算して最初から選び直す案とは異なる。全選択の置換、係数調整、引用の優先枠、予算の拡大はしない。最初は捕捉済み入力からのモデルなし再生で機会があるかを判定し、実フック配送の成功とは数えない。効果がなければ係数や対象範囲を同じ正解に合わせ直さない。

実フックの98%配送、80人継続利用、同一条件での総トークン改善・回答品質は未検証である。採用条件を緩めず、本体・README・releaseへ採用しない。

## 結果：この追加入れでは欠落を直せない

Leanで既存行と出典の保持、受理した参照の必要条件、描画後の両上限を表現した。nativeのリンク対象77 objectは依存整合性を確認した。固定source revision 40から8,276行の元の費用基底を復元し、実フック本文内の共有原文と全bytes一致することを確かめてから追加入れした。正解リストは選択の後にだけ読んだ。

既存2,361行・全出典枠・graph所有者を保持し、28行を追加した。本文は118,716文字/118,718 bytesから119,999文字/120,001 bytesへ増え、同じ120,000文字/128,000 bytesの上限内だった。追加選択136 ms、描画と検査109 ms、入力の復元1,184 ms。これは反実仮想の再生時間で、実フックやp99ではない。別DB・別所有者・別Occurrence・別指紋の追加拒否も検査した。

凍結した3根拠を描画本文のfile frameから読み直すと、**2/3→2/3で改善なし**。部分保存3097行を分母に残し、未配送のままだった。追加の28行を配送改善の代用にせず、この案を実フックへ接続しない。係数や対象を合わせ直さず、ここで試行を止める。[再生結果](candidates/stable-packet-completion/result.json)、[独立した凍結範囲の監査](candidates/stable-packet-completion/assessment.json)。

native再生の関連RSS最大161,808 KiB、ビルド最大2,010,096 KiB、終了後の残存PIDは0。再生器の本文パスと、後段監査のnamespace指定に各1回のハーネス失敗があり、終了記録を残して修正した。回答モデル0・新しい実フック0・総token改善未測定・未採用。原典DB2個と対照/現候補runtimeのSHAは一致している。終了したhelper buildと反実仮想本文は削除し、archiveはない。

今回消えた仮説は「選択済みデータを保ち、実残予算へ同じ価値のまま詰めれば欠落が直る」である。次は三辺の構造が、範囲への投影後に個別行のmax値だけへ縮約される段階を調べる。単なるgraph係数の増量や、失敗済みの文字倍率除去・引用予約へは戻らない。
