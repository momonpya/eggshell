# 限界値の差分更新と実フックへの接続監査

未採用。候補runtime `cf366ff270ee08ebd6ee4a797608188aab50735238c481314b3969c4492cedc8`。

候補や重みを変えず、選んだ単位によって新しく覆われた根拠cue・費用nodeから、その影響を受ける候補だけを更新するLean部品を隔離実装した。費用と価値の逆引きを分け、既に共有済みの見出しだけでは価値を再計算しない。保持値は選択状態に型で結び付け、全候補の完全な逆引き、各保持値、安定した全選択順が従来の全再計算と等しいことを証明した。巨大Nat、重複cue、空集合、収まらない候補をnativeで比較した。

最初の試作は、採点のたびに共通Evaluationを再構築してしまい、512候補・16,384cueで親1,319msに対し81,753msへ悪化した。この失敗とCPU記録は残している。Evaluationを状態ごとに保持した修正で、独立native比較は親1,239msから258msとなり、全64件の選択順も一致した。256候補では136→40ms、小さい条件には改善しない例もある。

しかし、同じC7実seedの3題材は29,014 / 29,016 / 29,018msで未完了、必要原文は0/4・0/6・0/5だった。集計RSS最大1,865,248KiB、残存0。新規oracle/ContractAudit成功をこの不合格の代わりにしない。

追加のCPU監査で、**実フックは新しい差分選択器を呼んでいない**ことが判明した。`SharedCoverage.choose?`からのコンパイル時置換を2段に登録しており、呼出先は旧`chooseDeferred?`のままだった。実際のHandoff objectの未解決symbolも旧入口を指している。部品を直接呼ぶ合成試験だけでは、この接続漏れを検知できなかった。

次の隔離候補では、元の公開入口からの置換を一つだけ登録する。比較試験も公開入口を呼び、コンパイル済みHandoffの実際の呼出先を検査してから、同じ15項目を再監査する。この候補の実フックを新選択器の遅延測定とは扱わない。
