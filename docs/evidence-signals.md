# 現在質問の信号と原文選択を結合した診断

2026-10-27。Astraレビュー後の一回のモデルなし診断。固定C7、題材2、既存の準備済み索引と保存済みfocusを読み、原文候補に現在質問・引用・シナプス・実価値・選択結果を結合した。selectorや検索providerは呼び直さず、原DB・索引への出版とwarmも行っていない。製品への採用ではない。

## 確認したもの

収集器 [EvidenceSignalJoin.lean](../tools/research/EvidenceSignalJoin.lean) は凍結した正解を入力として受け取らない。直近フックのsource/index head、focusPositions、選択ID列、予算、scaleと、既存の範囲診断・数値入力を照合する。原文を持つ21所有者、11,270候補の範囲を同じ`prepare`から復元し、**各候補の基礎価値が実入力と一致することを全件検査**した。収集に使ったHandoffのsource stampも、15,476 msの実フックを記録したものとバイト一致した。

グラフは同じ5,118ノード・41,798辺を完走した。原文範囲には既存の内容ID・Work・元bytesを使い、コマンド文法や題材名で抽出対象を選んでいない。`support`、`consumption`、`coquotation`の推薦が到達している。私有usageの根はこの実行にないため、利用フィードバックの効果まで確認したとは言わない。

表の作成後にのみ、別の [AnnotateEvidenceSignals.lean](../tools/research/AnnotateEvidenceSignals.lean) で凍結した必要範囲と実本文監査を重ねた。ラベルは候補生成・特徴抽出・価値計算へ渡していない。[全表](candidates/evidence-signals/table.json)、[後付け監査](candidates/evidence-signals/annotation.json)、[要約](candidates/evidence-signals/summary.json)。

## 失われていた信号

欠落した2所有者は、現在質問の所有者focus順位で3位・6位だった。必要範囲の文字はどちらの代替でも全て、過去回答の引用priority 0に覆われ、選択へ渡る最良priorityは0になった。`coveringCue?`で一つの最良値にまとめるため、現在質問への直接focusの違いがこの値に残っていない。

| 必要原文 | 原文の長さ | 現在質問の信号が最良値に残らない文字 | 完全に含む単独候補 | 選択 |
| --- | ---: | ---: | ---: | ---: |
| ToolChain cache key | 294 | 294/294 | 各所有者に35件 | 0 |
| HLSL分岐全体 | 523 | 523/523 | 各所有者に1件 | 0 |

HLSL分岐の一部は、6位の所有者内で直接focusも7位に入っていた。他の部分は103・104位である。cache keyは一方で29・92位、他方で44・63位だった。これらは保存されたfocus出力の順位を1始まりで表示したもので、MiniLMの生スコアではない。未保存の生スコアは推測していない。

全原文区間の9,798セルのうち6,408セルでも同じ厳密な優先度の上書きが見られた。これは今回解析した原文形式の領域に対する数であり、全DBや共有ファイル行を含む全候補の比率ではない。

したがって、今回の欠落を「必要性を示す手掛かりが入力になかった」として処理しない。一方で、現在質問の信号を独立に残せば6/6になるという因果までは証明・実測していない。既往のcause保持、max-min、重み除去を再実行した結果でもない。

## 表示形式との関係

照合した実選択862単位は、全て共有ファイル行の形式だった。再構成した原文形式11,270候補は全て未選択。対応する範囲診断も、選ばれた5所有者の`selectedOriginalRanges`は空で、`selectedSharedRanges`だけを持っていた。範囲診断の候補数、予算、scale、選択ID列は直近フックと一致している。

欠落した原文は、ファイル座標の共有行を持たない側にある。294文字全体を含む最小候補の実standalone費用は2,035/1,790文字、523文字全体は2,246/2,003文字だった。費用はダミー表示から計算せず、保存済みの実数値入力から取得した。所有者の共通枠も含む。この差と上記の選択の偏りは観測できたが、それだけを欠落の唯一の原因として扱わない。表示を変えないまま費用だけを変えた以前の反実仮想は3/6へ悪化しており、再試行しない。

## 保証と限界

- 復元したのは原文形式の21所有者。共有行を持つ8所有者と非nativeの1所有者の候補価値は再構成していない。後付け監査でその領域にatomがないことを、上書きが0件という実測に使わない。`unitAudit`で解析範囲を区別する。
- dummy envelopeは原文の範囲・cue復元にだけ使い、表示の費用や実本文の再生成には使っていない。11,270候補の価値一致を、全recipeや描画・認定の新たな等価証明へ拡大しない。
- native診断には停止したRPC案の依存moduleもリンクされているが、DB・routingへの直接読出しだけを呼ぶ。RPC案の実フック・権限・期限・性能を検証したものではない。
- 収集は10,453 ms、guard内の最大RSSは278,704 KiB。これはDBの読出し、全原文候補の復元、全件の値照合、診断JSON作成を含む時間で、利用時hookの測定や合格値ではない。ビルドのguardは別記している。
- 初期の構文・型検査の修正と、インタプリタでnative FileSystem境界を呼べなかった試行を経て、nativeで一回の収集に成功した。失敗guardも残した。回答モデル・selector・全warmの追加はいずれも0回。

## 次の変更に課す条件

これで、少なくとも今回の原文では「信号を失う集約」と「表示形式による費用・共有の違い」を別々に追える状態になった。現在質問のfocusと歴史上の引用priorityを先に一つへ潰さず、同じ元bytesと出典が表示座標に依存しない単位で競うことを、次の設計条件にする。単に新しい重み、原文所有者への予約枠、上位k、旧max-minへ戻さない。この表だけから新selectorの完成実装へ飛ばさず、ラベルなしで適用できる規則と、その規則が失敗した既往案と違う点を先に明示する。

速度のバッチ照会は引き続き独立の検証対象であり、今回まだ実装・測定していない。現状の実本文は4/6、通常hook15.48秒のまま。95%・数秒・総token改善・正式6段階・多数DB80人の条件は未達。最新AGENTSの同一条件・複数反復・総token・品質・期限の採用条件は維持する。

実行体と終了済みの一時出力を捕捉後に削除した。DB/cacheは追加しておらず、原seedと一つの準備済みDBは保持した。archiveは作っていない。[guardと失敗履歴](candidates/evidence-signals/guards.json)、[入力・実行体digest](candidates/evidence-signals/digests.json)、[削除記録](candidates/evidence-signals/retired.json)。
