# 共通原文を実フックの選択と本文へ接続する候補

**隔離候補。回答モデルでの比較と本体採用は行っていない。**
前の基盤だけの成功と区別し、実際のUserPromptSubmitのstdoutを検査する。
凍結した手順は`candidates/canonical-hook.md`に保存する。

## 接続

番号付き原文だけを、既存のMiniLM数値producerと3種の推薦辺から、共通の行payloadへ結び付ける。
相対パス・指紋・バイト長・行番号で一つに持ち、元DB・所有者・Work・全occurrenceを出典として残す。
同じ行の原文費用とファイルの出典フレームを一度だけ計上し、一度だけ本文に描画する。
既存のproducer順位とRRF係数は変えない。重複観測の同じ行cueは最大値でjoinし、別の票にしない。
独立した数値cueと、全ての根拠が揃ったときだけ価値を持つ依存閉包は維持する。

従来の所有者ごとのview生成より前で、準備済みの共通原文経路へ分岐する。
キャッシュは既存のSidecar.destinationに従い、明示warm・背景index・利用eventの背景処理で更新する。
フック内では構築せず、固定したDB出版・実装・出典の印を照合して一度読む。
準備状態をmemoの入力と受領記録にも含める。推薦の探索が未完了・破損した場合は従来の本文へ退避する。

非対応の検索・ビルド等の観測、過去の解釈、制約と認定の経路は既存の経路を残す。
共通原文sliceには制御用memberと全体配送の可視キーを持たせない。
元のadvisory所有者だけを出典の可視性へ結び付け、completedやツール抑制の権限を作らない。
元のsource freshnessとその状態表示も維持する。

## 実本文と受領

本文の共通原文ブロックは、元のDBの指紋・行・文字列が一致した行だけを配送済みと判定する。
原文の各scalarは一度復号し、元座標との対応を検査する。
位置一覧は位置だけと明示し、私有利用ラベルでも本文監査でも配送済みに数えない。
原文のキーと質問ごとの計画キーを受領記録へ通し、受領済みの行や同じ計画を再充填しない。

## 先行検査

Leanのnative fixtureで、原文の実バイト照合・改変拒否・指紋変更の分離、位置一覧の除外、
複数出典の保持、行と計画の受領差し引き、重複cueとpayload費用の共通化、制御memberなしを検査した。
実Pre/PostToolUse・Stopから作った小さなDBでは、新しいチャットの実stdoutに
支持・消費・共引用・未配送後再読の原文が入ることを検査した。
既存completed=1とblocksCurrent=falseが維持され、破損した任意の推薦索引からは元の本文へ退避した。
読み取り専用profileの元DBのhead/pages不変性も検査した。ファイルシステム自体をread-onlyにした試験とは区別する。
既存のContractAuditも通過した。

最初の故障試験では、推薦索引が破損しても新しい原文経路が残り、退避先の本文一致に失敗した。
推薦が完全に構築できた場合だけ新しい経路を使うように直し、別のfixtureを最初から作り直して上記を確認した。
この失敗と修正前のバイナリ・ソースを保存している。重み調整や題材への規則追加ではない。
ビルド・検査後の圧縮中にはdisk guard停止もあり、原本を照合して未完了の圧縮だけを作り直した。
機能検査の成功と、後続の保存処理を含むguard全体の失敗を混ぜない。

## 固定6段階

同じ6snapshotを題材1から、各2つの独立チャットで測った。

| 1周目・題材2 | 保存済み必要コードの欠落0 | 22006 / 20921 |
| 1周目・題材3 | Compile境界360–371が未配送 | 22624 / 21741 |

| 2周目・題材2 | incomplete、本文なし | 28919 / 28908 |

最初の3段階は共通原文ブロックを含む実本文であり、位置一覧だけの配送ではない。
最初の2段階では、従来の共有前候補で落ちていた必要原文が入った。
1周目・題材3のno-outputとConstructJobは元snapshotにないので、上の未配送1件へ加えない。
incompleteを「必要項目が数件だけ欠落した本文」と数えない。後半は本文配送そのものの失敗である。
各段階の独立2チャットの本文は一致し、元入力と原文pagesの不変検査は全段階で通った。
六段階のdriverは計測を最後まで実行して終了0だったが、配送の合格ではない。
実配送成功は6/12、後半6/12は期限切れなので、**この候補は未採用**である。
最大RSSは2387296KiB、3GiB guard・4GiB上限内。資源guardは正常終了した。

その後に別の診断再生を行い、8秒時点では残る旧contextual supportの反復復号、
16秒時点ではunitごとの全cue走査、24秒時点では依存memberごとのunit走査を確認した。
選択の重みを変える根拠にはせず、owner/原文キーでの索引化と同一結果の検査へ進む。
共通化された番号付き原文の処理と、残している旧形式の観測処理は別々に直す必要がある。
この診断は固定6段階の後に行い、元の遅延数値へ混ぜていない。

この検査は回答モデルを呼ばず、既存の同一snapshotで配送を検査するものである。
Luna/xhighによる回答・トークンの初回／履歴あり×題材1・2・3の比較とは別である。
証明やこの検査だけで総トークン改善・品質維持・採用を主張しない。

候補の追加Leanファイルと試験は`candidates/canonical-hook/`、既存接続の差分は
`candidates/canonical-hook-runtime.patch`に保存する。差分は凍結したbundle候補を基点にする。
interval候補のcore patch、bundle候補、canonical-sourceの基盤を先に準備する。
通常の本体ソース・installed binary・README実績・リリースを変更しない。

凍結ソース・link input・実行ファイルのSHA、全試行のguard、実本文の監査結果と診断は
`candidates/canonical-hook-review.json`に保存する。追加5証明は標準公理以外に依存しない。
