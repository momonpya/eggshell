# 本文出力後の受領確認を高速化する

本文の出力自体は終わっていたが、受領確認に毎回5〜6秒を使っていた。
2周目の題材1では、その間に期限が切れ、daemonの終了確認も失敗していた。
配送キーは約1,800〜1,900個あり、`addDeliveredGraphs`は1個加えるごとに
`replaceSourceStatus`で全リストの`eraseDups`をやり直していた。

元の順序付き更新を仕様として残し、重複除去だけを既存の`hashDistinct`に置き換えた。
`replace_source_status_compiled`は、任意の旧リストと追加キーについて関数全体の一致を証明する。
ソース状態のscope置換、最初の出現順、checkpoint、重複・不正形式のキーも含む。
ハッシュの一致だけでは同一視せず、文字列全体で判定する。
generated Cで本番の`addDeliveredGraphs`が高速版を呼ぶことも確認した。
検索、原文選択、3辺、推薦と認定、鮮度、turn/epoch/期限の判定はこの変更では変えない。

実際に保存された1,925キーのnative比較で、旧処理5,813msに対し候補126ms、順序付き出力は一致した。
別の原文record候補へ接続した再構築でも6,161ms対128msだった。
最初の試験では純粋計算が時計の読み取り後へ移動し、0msになっていた。
その値を速度の根拠には使わず、失敗した計測を保存したうえで、noinlineのIO評価器でやり直した。
計算が時計の間にあることをgenerated Cでも検査した。
VMで外部native宣言を読み込めなかった試行も、成功へ数えず保存している。

共通メタデータ費用を変えた候補との組み合わせでは、全6段階・独立12チャットを完走した。
受領確認は219〜239ms、フック全体は11,637〜21,010msで、全ACKとshutdownが成功した。
監視もexit0で終わり、最大RSSは2,196,384 KiBだった。
独立したLean監査で、全6元DBの事実・出版済みpage prefix・元入力SHAと全12実stdout/本文の結び付きを確認した。
比較できる前候補の7本文に対応する8チャットは、全てバイト一致した。

ただし共通費用を変えた候補の原文欠落は0/0/1/0/0/2だった。
直前の原文record候補の0/0/1/1/0/0から欠落が移っただけで、原文配送の改善とは断定しない。
費用や重みをまた調整せず、元の原文record候補へ受領処理だけを接続した。
その候補は元の3辺・共通原文・完全な来歴とrecord閉包を保ち、共通メタデータ費用の変更を含めない。
