# 参照候補の条件付けを実フックで確かめる隔離試行

2026-10-28、実行前に固定。[前の再生](reference-closure-audit.md)で必要原文の選択が4/5から5/5になった、同じ条件付けだけを接続する。製品採用、READMEの実績、リリースへの変更ではない。

## 固定するもの

- 同じ原文snapshot、ソース、質問、MiniLM、字句、3辺、重み、cue、既存offer順、120,000文字/128,000 bytesを使う。
- 新seed、回答モデル、全warm、再埋め込みは行わない。原文/既存数値を複製した別の実験DBで、Handoffの実装印に結び付くcanonical派生viewだけをoff-hookで準備する。元DBと4/5実行体を保持する。
- 以前の条件付けに含まれた`for`、`defined`等を除かず、形状や語の規則を合わせない。構文候補を言語の名前解決や意味上の必要性の証明とは扱わない。実験として推薦の費用と原文の組を変え、Match/Union/completedを生成しない。
- 凍結正解は配送後の監査だけに使う。呼出し名や特定の行/関数/パスを選択規則へ渡さない。

## 接続

`ReferenceRequirements`は読み取った同一原文から、前の読取り診断と同じ字句・括弧・一意な構文候補を作る。共通核は同じfile/fingerprintの原文行とその費用であり、Unknownな入力や従来のMCP/JSONの候補を除外しない。この実験の構文adapterが任意の形式の依存関係を復元するとは主張しない。

選択前に参照先の原文と共有file frameの費用をofferへ含め、同じ物理payloadを二重に払わない。元のcueは保持する。選択後に元のunit由来の本文と、条件から選ばれたcanonical原文行を一緒にmaterializeする。元行の指紋・出典・bytesは既存canonical形式を使い、最後の実描画の文字/byte上限を検査する。必要な元原文がunit番号に現れない場合でも、受領の選択範囲には実際の原文bindingを加える。

ここでの実装は隔離したnative経路の検査用で、照会ごとに構文表を組み立てる。最終製品には、出版差分で準備しDBサービスで共有する工程が残る。小さい試行の時間を80人・多年の性能へ外挿しない。

## ゲート

1. 型と証明：元payload保持、cue保持、有限の元payloadからだけ描画すること。従来の`Plan.within_budget`と`keeps_control`も同じ最終描画へ適用する。
2. 抽出の分離：同じ元入力から、切り出した実装の原文選択集合と費用が前のshadowと完全一致すること。合成のコメント/引用符/観測gapの3チェックも保持する。
3. 準備：原文/既存索引の完了を確認し、必要なcanonical viewだけを更新する。準備が失敗したまま本文なしのhookを回して結果にしない。
4. 実フック：新sessionの初回UserPromptSubmitを一回実行し、5項目の元原文・範囲・出典が本文にあり、30秒未満、集計RSS 4 GiB未満を確認する。未配送や期限超過の場合は原因を記録し、語/重み/予算の調整で当たりを待たない。

合格しても製品採用ではない。初回/履歴あり×題材1/2/3の同数複数反復、同一snapshot/モデル/effort/harness、cachedと失敗を含む総入力+出力token、品質維持の比較をAGENTSどおり行う。今回の候補の正式モデル評価へ進むときはseedからruntimeを一貫させる。

終了済みの実行体/build/不要なコピーは削除し、DBやcacheを実験記録のために保管しない。次の試行に必要な現snapshotだけを保持し、archiveは作らない。
