# シナプスの整数接続をFactと同時に出版する

隔離候補・未採用。実行物は `fd726ab0074a8f14005148d5059ed285f3589edd3ee412e5c1408454a846f27a`。親は内容対応候補 `f9fd4713…`。型と射影を下位のLeanモジュールへ移し、推薦用の整数接続を元のFact・逆引きpostingsと同じPageMap、同じwriter、同じcommitにした。[差分](candidates/synaptic-publication-delta/core.patch) は親へ `--unidiff-zero` で適用する。本体・README実績・リリースへは取り込んでいない。

以前の接続DBは明示的な構築でしか作られず、通常のwarmではフックが `routing-unprepared` になっていた。別DBの準備完了を同期させる方式をやめ、`Index.publishDelta` と `replace` が、そのFactの接続だけを直接更新する形へ統合した。フックは元の索引の同じsnapshotを開くだけで、全Factの再読込、接続の再構築、別DBのopenをしない。

## 保存と境界

`SynapticTopology` にキー・Target・既存の一段の射影を移し、上位の推薦器やサービスからの依存を除いた。`SynapticTopologyStore` は辞書で整数IDを割り当て、`route:` 以下へ接続と対象を保存する。原文と質問の本文は複製しない。

追加は一つのFactの接続だけを作り、削除はFactに保存した接続IDを引いて消す。整数IDは再利用せず、旧snapshotが新しい別対象を参照することを防ぐ。Fact件数と接続の件数を検査してから、同じwriterがmanifestを確定する。取消ではどちらも公開されない。再送は同じheadを保つ。ハッシュが一致しても辞書の値が異なれば失敗する。

共有と私有の利用信号は同じ保存原理だが別scope。私有queryから共有の共起へ戻る探索も維持する。推薦用の接続であり、Union、Match、completedの権限は持たない。射影先が元のFactに支えられる定理とcodecの往復定理を維持した。既存のinverse postingsにはまだ実利用があるため削除していない。

## 検証

| 合成Fact数 | 初期構築 | 1 Fact追加 | 追加bytes |
| --- | ---: | ---: | ---: |
| 69 | 56 ms | 14 ms | 62,218 |
| 1,029 | 921 ms | 32 ms | 155,119 |
| 4,101 | 4,055 ms | 37 ms | 171,804 |

追加・削除・再追加と私有feedbackの各段階で、元のpostingsを直接たどる独立探索と、全推薦の値・重複・順序が一致した。取消、旧pin、整数IDの保持、重複再送、scope違反、壊れた準備印による未完了も検査した。これは100万窓や80人の測定ではない。

保存済み実seedの39,757共有Fact・20私有Factも、そのまま新しい索引へ投影した。独立した旧完全探索の27,825推薦と3回とも順序まで一致した。構築後の走査は1,096 / 225 / 229 ms。最初の試行も構築直後のOS cacheを使うため、冷たいディスクやp99の値ではない。元DBと元索引は変更していない。

実Pre/Post/Stopからの小試験では、通常warmだけで整数接続が用意され、実受領の `synapticComplete=true` を確認した。元の7観測・15時系列・3辺を保持し、別private・読取専用の必要コード2/2を2,147 msで配送した。新規FullSearchOracle、既存ContractAudit、原子的更新と問合せの依存監査も通った。`publishDelta` から全Fact列挙へ到達しないことと、照会からwriterへ到達しないことを検査している。

## 実seedの全体は依然失敗

同じC7 seedを複製し、新しいprivate領域で全準備を完了させてから、元の題材1〜3の初回フックを順に実行した。必要項目は配送前の4/6/5件のままで、分母を減らしていない。

| 題材 | 実フック | 必要原文の実配送 |
| --- | ---: | ---: |
| 1 | 29,014 ms | 0/4 |
| 2 | 29,017 ms | 0/6 |
| 3 | 29,007 ms | 0/5 |

全件で未完了通知だけが届いた。数値検索とシナプス探索は完了しているので、接続を開けたことを95%配送の達成とは扱わない。回答モデル呼出し0・回答6段階0/6・総token改善未測定。新しいruntimeの新seed実験でもない。

題材2の受領では、数値検索が約2.8秒、探索と原文結合が約10.3秒、2,865単位からの選択計画が約22.2秒で記録され、その後期限切れになった。選択は712単位だった。共通原文のサービスはhitしていた。CPU診断では、16秒付近は `SharedCoverage.Deferred.bestDeferred` の費用/価値計算、後半は `Bundles.receipt → presented → sharedPresented` の原文行×Readの二重ループが大部分を占めた。単なるcache missではない。

後者は本文ができた後の受領検査であり、返却を期限外へ押し出す。次の候補は、照合条件と順序を保った文字範囲postingsでこの二重走査を除く。重み、候補上限、回答モデルを変えて原因をごまかさない。

## 残り

差分になったのは接続の保存。`Build.refresh` には全Fact・所有者・トポロジーの列挙が残り、今回の静止warmにも162,233 msかかった。サービスのcanonical全体JSONの準備、共有block、80人・NAS、100万窓超、MCPの保存方針は別の未完了項目である。`同じcommitで差分接続を維持できる` と `warm全体が差分で追い付く` を区別する。

小さい記録は [records](candidates/synaptic-publication-delta/records/collection.json)。終了したDB・cache・試験実行物は記録回収後に削除し、次の診断で実際に使う入力だけを保持する。
