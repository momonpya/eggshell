# 題材1の初回配送をseedから精査

26.1%削減を報告した後、利用者の指示で計測を停止した。題材2は回答モデルに投入していない。ここでは選択器を変更せず、追加の回答モデルを呼ばずに、seed原文と実際の初回投入本文を調べた。製品への変更採用はない。

## 結果

**関連する原文は全部届いていない。主な脱落箇所は選択で、保存の成功や本文の再現性を配送の成功と取り違えていた。**

以前の「DB内2件中1件」は、旧5項目を新seedに照合した狭い検査だった。seedにある関連履歴全体を調べた数字ではない。また`toolchain-cache-key`は所有者ごと欠けたのではない。式の7104行は届き、直前の関数宣言の7102行だけが選択から落ちていた。

seed回答のすべての明示引用を列挙し、独立した原文監査に通した。47範囲すべてがDBに存在する。実際の初回本文に全範囲が届いたものは16、未完は31だった。この一覧には周辺のプラットフォーム例も含むため、47を新たな「質問に必須な項目」の分母にしない。ただし、次の直接関連する根拠も欠けている。

## 段階を分けた確認

1. **保存。** seedの37ツール完了記録について、日誌の応答と入力がDB原文・Workにすべて一致した。欠けた原文・本文不一致・Work不一致は0。最終回答も完全一致の所有者を確認した。固定snapshotと元ページも不変。これで「日誌からDBに保存する間に欠けた」という仮説は支持されない。
2. **原文の有無。** 取得コマンドの文法に頼らない既存Lean監査で、全47引用範囲をDBの原文から回収できた。索引の成功だけを存在の証拠にしていない。
3. **推薦とシナプス。** 実受領記録は初期推薦8、復元された所有者38、`synapticComplete=true`。不足する所有者もドメインに入っている。「3辺を探索し終えた」と「選んで届けた」は別だった。
4. **選択。** 47範囲に属する、座標索引で確認できた非空1,715行のうち946行を実本文で確認し、769行は候補にありながら未選択だった。769行に描画後だけの脱落はなかった。実本文のCODEは`Driver.cpp`一ファイルの2,193行に集中し、他ファイルは位置一覧だけになった。固定費28,433文字、上限120,000文字、候補単位7,847である。全47範囲が予算に入ると証明したわけではない。現在の価値・費用による選択が関連する別ファイルを落とすことまでを確認した。
5. **座標索引。** 上の1,715行とは別に、原文にはある非空91行が座標索引になかった。多くは繰り返しのコメント区切りだが、`target.c`の重複するRUN行やBareMetalの条件も含む。したがって、すべての脱落を選択だけと断定しない。曖昧な同一行を誤った一座標へ結ぶ修正はしない。
6. **実際の本文との対応。** 同じruntime・同じ保存snapshot・同じ私有履歴から独立チャットで診断用フックを実行した。全本文のSHAは実モデルの初回packetと一致し、選択ID・費用・上限・候補数も一致。21,546 ms、ピークRSS 1,506,560 KiB、終了後の残存PID 0。traceの別結果で元の失敗を説明していない。

生の端末結果とフック入口の比較には別の限界がある。4応答にツール出力の切り詰め、2応答に途中の出力を含む差があり、端末結果との全bytes一致は未確立である。中間のplan更新2件も対応イベントが未確認なので、保存監査全体の`comparisonComplete`はfalseのまま残した。フック入口の日誌とDBの37件の一致、DBからの47引用範囲の存在確認とは区別する。

91行を個別要件として汎用の合否器に入れる追加試行は、同じコメント・RUN行の代替証拠が重なるため`partition overlapping required evidence before freezing`で拒否された。これをDB不在や製品フック失敗とは数えず、47範囲の独立原文監査と、座標索引上の未確認行という診断を保持する。

## 次の作業

回答モデルの計測には戻らず、選択が一ファイルへ偏る理由と、原文にある重複行が候補表現から抜ける経路を、同じsnapshotのモデルなし再生で分けて修正する。題材固有の行・語・重み・枠の追加で救済しない。関連原文の脱落が残る状態を、モデル分散だけでは説明しない。今回の配送欠落だけで26.1%の原因すべてを説明したとも断定しない。

### 原文と配送費用の分解

続けて、同じ実受領記録の物理payload・file frame費用に照合し、全47引用の費用をLeanで調べた。正解一覧は選択器へ渡していない。原文の有無は上記の独立監査で確認済みで、この測定は配送の成功や変更の採用ではない。

| 内訳 | 文字数 |
| --- | ---: |
| 座標索引で確認できる引用行1,805行のpayload | 98,471 |
| そのfile frame・出典 | 19,463 |
| 現行の固定表示 | 28,433 |
| 上の合計 | 146,367 |
| さらに現行の関数参照依存を展開した合計 | 175,121 |
| 索引にない行も含む全47範囲の番号付き原文1,996行だけ | 101,549 |

索引にない行を含める前から、現在の形式では120,000文字の上限を超える。一方、原文自体だけなら上限より小さく、固定表示と出典の枠に47,896文字を使っている。したがって「全47が現行形式で入る」とも「原文自体が大きすぎて仕方ない」とも扱わない。全47には周辺例も含むので、これらをすべて質問の必須根拠と断定しない。

関数呼出しの字面から定義の範囲を推測する`ReferenceRequirements.prepareGraph`は、実装自身が意味的な必須依存ではないと記している。それを現在はpayloadの強制依存にしており、この診断でも引用行の1,805行が2,482行へ増える。実際の引用・消費から得た根拠と、この推測による定義補完を同じ必須条件にしないことが、次の独立した構造検証になる。

本文以外の費用を共有し、根拠集合の費用を先に確保できる表現を検討する。以前失敗した表示短縮・残差候補・引用優先の重み調整だけを再実験しない。番号付き原文101,549文字だけの測定は、出典・鮮度・プロンプト等を含む完全なpacketが枠内に収まることの証明ではない。既存モデル計測の停止と採用条件を維持する。[費用の機械記録](candidates/citation-budget.json)。追加の回答モデル、warm、DB/cache生成は0。
