# 共有行の受領と利用辺の再生

2026-10-29。隔離候補。[差分](candidates/shared-read-receipt/candidate.patch)、[Lean検査](../tools/research/SharedReadReceiptAudit.lean)、[依存境界の検査](../tools/research/SharedReadReceiptContract.lean)。本体未採用。

## 修正した不整合

共有原文の受領キー `c:<file>:<line>` を、利用の分類器が復元していなかった。旧処理は所有者単位の `h:/g:/e:` だけを扱っていたため、届いた原文を「未配送後に読まれた」と判定しうる。候補は、確認済みのキーを読み取り前の検証済みReadへ結び付ける。指紋・行・範囲の包含が成立する行だけを加え、元出力全体の受領へ広げない。未確認配送、位置通知、plan、別指紋を受領とは扱わない。

キーとReadの直積走査はしない。同じファイル・範囲の重複を除き、ファイル別の区間索引で行を引く。元の観測・binding・occurrenceは保持する。Leanの証明は「確認したキーが元の受領列にある」「返す範囲は保存済みRead内にある」「元出力のbindingと不確実性を変えない」という範囲であり、IO全体や必要根拠の完全配送の証明ではない。

派生の利用索引にも問題があった。一度記録したイベントの分類を不変としているため、分類器を修正して再生しても、古い誤分類と衝突する。候補は分類器の実バイトに対応する私有索引を使い、古い分類器へfallbackしない。原イベントの日誌は変えず、同じ分類器内の矛盾は引き続き拒否する。共有索引の形式や実装識別はこの修正で変更していない。

再生checkpointには共有索引と私有の利用索引の両identityを結び付けた。派生索引を失ったあと、元の日誌が同じだからという理由で処理済みにならない。更新はそのターンのfactだけを追加し、全利用factを読み直して足し直す旧分岐を除いた。ただし、日誌全体のturn列挙は残っており、大規模な差分再生の完了とは扱わない。

## 確認したこと

[結果](candidates/shared-read-receipt/result.json)と[guard](candidates/shared-read-receipt/native.guard.json)。

- 一部だけACKした行、重複、行の穴、別指紋、非正規キー、未確認配送を検査した。届いた行は `omitted_then_read → reread` へ変わり、届かなかった行は未配送のままである。
- 保存済みの実本文を元記録と照合した1,521 Read・1,258行キーについて、旧処理0件から1,521件を復元した。キーは実本文から模擬生成した確認済みキーであり、歴史的な実フックの利用ラベルを測った数ではない。
- 古い分類を持つ私有索引を残して、新分類を永続化できた。旧pinは不変。同じイベントを繰り返しても1件のまま。同じ分類器で矛盾させた書き込みは失敗し、headは不変だった。
- 12ターンを8件・4件で処理し、利用索引だけを削除して同じ8件・4件を再生できた。元の全日誌entryとsource headは不変である。
- 1千/1万/5万Readと40/400/2,000キーの復元部品は2/20/101 ms。DB全体の窓数や実フックのp99を測った数字ではない。

guard込み7,874 ms、関連RSSの標本最大112,560 KiB、終了0・残存0。証明は標準の3公理だけに依存する。[公理](candidates/shared-read-receipt/proof-axioms.stdout)、[読み取り・出版の境界](candidates/shared-read-receipt/contract.stdout)。

## 実seedで見つかった別の回帰

[原DBを使った再生](candidates/shared-read-receipt/historical.json)では、固定snapshotと原DBのheadが完全一致することを確認して、75 entry・37開始記録を読み直した。原DBと日誌のheadは不変。共有行ACKは0件なので、上の共有受領修正をこのseedの欠落の原因・改善としては扱わない。

一方、私有索引には `omitted_then_read=23`、`reread=1`、`delivered_then_cited=27` が保存されていた。現分類器で再生すると0/0/27となり、unknownは24件だった。開始時の索引記録は5件あり、5件とも現在と生成元の実装識別が違うという理由で拒否された。残る32開始には索引記録自体がない。旧factは監査として読み取っただけで、現runtimeが受理したとは扱わない。

source-onlyのコピーをDB所有索引の探索にも使ってしまった初回診断は除外した。[除外理由](candidates/shared-read-receipt/decision.json)。有効な診断は、元の所有DBと元の私有cache配置を使い、固定headとの一致を検査したものだけである。

次は、過去producerを現在と違うという理由だけで落とす回帰を、元publicationとReadの原文bindingの検査へ置き換える。索引記録なしの場合も、後から準備した索引を「当時存在した索引」と偽らず、当時のsource snapshotに実際に保存されていた証拠で判断する。回答側の共有ACKから正の引用ラベルを作る経路は今回未変更である。

実フック・回答モデルの追加呼び出しは0。配送本文と既存の2/3という必要根拠監査の結果は変えていない。98%配送、総トークン改善、品質、80人の8時間利用は未達・未検証のままである。採用にはAGENTSの一致比較を要する。

終了した合成DB・私有cacheと重複監査出力、計247,630 logical bytesは、結果抽出後に削除した。元seedと必要なbuild依存物は保持し、archiveは作っていない。[削除記録](candidates/shared-read-receipt/retired.json)。
