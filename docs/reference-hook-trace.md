# 題材2の選択と描画を分ける診断

2026-10-28、実行前に固定。同じ候補f69e3e06、同じ元原文・prompt・既存数値・重み・予算を使う。`EGGSHELL_TRACE_SELECTION_RANGES`と`EGGSHELL_TRACE_SELECTOR_INPUT`だけを有効にし、同じcontrollerの題材1→2→3を別の新sessionで一系列だけ再生する。新モデル・新seed・warm・再埋め込み・候補runtime変更は0。

まず通常実行の実本文とSHA/bytesが一致するかを確認する。一致しなければ、この診断を通常実行の説明として使わない。選択入力はLeanの整数として扱い、JSONの大きな整数を丸めない。

題材2では、凍結原文の各bindingを実際の`rangeAudit`の候補範囲、選択範囲、条件による追加原文、本文の順に追う。候補の和集合にないなら候補化/束縛、選択範囲にないなら選択、選択にあるのに本文にないなら描画/受領を調べる。関数や正解位置を選択器の入力にせず、診断後の照合だけに使う。

必要原文は1450〜1466行、1479〜1497行、1699〜1700行（同じDriver.cppの指紋）にあり、通常実行では所有者の原文506行が準備されていた。原文の存在やfocusの順位だけから選択済みと断定しない。診断結果に合わせて語・重み・幅・上限を調整せず、同じ失敗の当たり待ちをしない。

新しい構造が必要だと分かった場合も、その実装は別の隔離候補にし、元の部分範囲を残した原文scopeの代替や値の生成/利用などの仮説を先に固定する。正式なモデル評価へは95%未達のまま進まない。終了したsession cacheと不要な診断実行体は削除し、DBを記録のために追加保存しない。

## 結果

同じf69e3e06の診断付き実フックは、題材1/2/3が5/5・3/6・5/5、14,965/14,574/14,327 msだった。3本文とも通常実行の実bytesと完全一致した。traceは元原文factsと出版済みpage prefixを保持し、終了0・残存PID 0、集計RSSの標本最大862,416 KiBだった。回答モデル、warm、再埋め込みは追加0。

Leanの読取り監査で、同一fingerprintの各行の実origin bindingを`rangeAudit`の候補/選択区間へ照合した。全16項目は候補の和集合にある。選択済み13項目は実本文にもあり、選択されなかった3項目は全て題材2だった。

| 項目 | 選択時点で不足する行 | 実本文 |
| --- | --- | --- |
| mode-before-parse-and-config | 1464–1466 | 未配送 |
| clang-cl-pass-through-reparse | 1494–1497 | 未配送 |
| default-toolchain-selection | 1699–1700 | 未配送 |

従って、この3欠落の最初の消失段階は選択であり、描画/受領だけを直して解消するものではない。呼出し先の原文を条件に含める現候補でも、呼出し元の条件・戻り値の利用・後続の処理は自動的には揃わない。これは残った構造の診断であり、次の方法が改善することの証明ではない。

[実bindingを使った監査](candidates/reference-hook/trace/selection-audit.json)、[traceの実結果](candidates/reference-hook/trace/result.json)、各題材の実rangeAuditを保存した。最初の監査スクリプトの構文エラーと、interpreterにnativeファイルIO実装がないための失敗もguard記録に残し、native buildした読取り監査で完了した。これらは回答モデルを呼ばない診断失敗であり、フックの成功数へ加算しない。

終了した3sessionのcacheと監査実行体64ファイル・102,931,563 logical bytesを削除した。現候補/比較基準/controllerのSHAは前後一致し、archiveとDB追加保存は0。[整理記録](candidates/reference-hook/trace/completed.json)。候補は未採用、95%・総token改善・品質維持・数秒・80人での検証は未達のままである。
