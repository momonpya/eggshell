# 残る欠落の候補化と費用を実際の本文から追う

canonical-deferredの全12フックは期限内に本文を返してACKも確定したが、
DB内の必要原文が落ちる二つの段階は残った。重みや順位を再調整する前に、
実stdoutとsynaptic-deliveryの記録をLeanで読み取り専用に監査した。

| 段階 | 残った必要原文 | 引用・3辺の推薦から到達 | 全必要行を覆う候補 |
| --- | --- | --- | --- |
| 1周目・題材3 | Driver.cpp 360–371のCompileへの分岐 | なし | なし。候補全体の和集合でも不足 |
| 2周目・題材1 | Driver.cpp 3131–3135の警告 | supportとcoquotationで到達 | 4件あり、すべて未選択 |

次に、正解範囲を入力せず実際のfirst-request関数を同期実行する診断を作った。
候補、共通原文、元座標、数値と引用の手掛かり、費用、依存recipe、選択結果をLeanから記録した。
2段階とも実フックの本文とバイト一致し、別のLeanチェッカーで元DBの事実と出版済みpage prefixの
不変性も確認した。題材3では派生metadataによってhead/pagesの全体SHAが変わっていたが、
元の事実と元page prefixは不変だった。この違いを入力の改変とも完全なバイト不変とも呼ばない。

Compileの条件式は360行から370行まで続き、結論の`phases::Compile`は371行にある。
記録された候補の手掛かりは360–364行だけで、引用由来の増分はなかった。
共通原文の候補化で窓と交差する行だけを選んだため、同じ条件と結論を丸ごと選ぶ候補がない。
この失敗は、graphの辺を強めたりselectorの重みを変えたりしても直らない。
次の候補では、連続する元行と観測済みの段落境界を使い、短い原文recordを途中で購入できないようにする。
読み取りの隙間、異なるファイル指紋、未観測行は補わず、推薦と認定の境界を保つ。

警告は完全な候補が4件あり、依存recipeも2件あった。最小候補を既存の選択に足す純増費用は459文字。
一方、モデル上の選択費用は120,000文字に達しており、残り容量はなかった。
これは必要原文が120,000文字に収まらないという証拠ではない。
数値の重みは変えず、source-check等を含む保守的な固定費と実際のpacket費用の対応を追う。
実本文の長さとの差だけを、そのまま安全に使える残り予算とは扱わない。

正解範囲は記録後の監査にだけ渡した。抽出器・producer・候補化・selectorへの正解入力はない。
初回の診断はRuby2.6の`filter_map`未対応により後処理が失敗したが、完了済みの実行結果を回収し、
同じ段階を再実行していない。失敗したコンパイルと後処理も記録した。
診断用のHandoffソースとinterfaceは退避した元のものへ戻した。

全記録・SHA・候補のLeanコード・診断差分は`candidates/canonical-selection-audit-review.json`からたどれる。
回答モデルとseedの新規呼出し0、トークンと品質の改善未計測、通常runtimeへの採用0。
全Phases0–6の目標はactiveのままである。
