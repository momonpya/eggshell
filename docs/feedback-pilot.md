# 利用フィードバックを観測する有界パイロット

**2026-10-28のAstra追加相談で、以下の新seed・6段階・fresh計画は実行前に停止した。** 次は既存C7・題材2の実回答一度と、その後の同じsource snapshotで今回のusageだけを変えるモデルなし対照に縮小する。原文・過去回答・利用辺を同時に変えた結果から、利用辺の効果を推定しない。[採用した判断・停止条件・準備検査](astra-progress-review.md)。以下は停止した事前計画の記録で、現在の実行指示ではない。

2026-10-28、モデル実行前に固定する。表示短縮は悪化し、現在focusと過去引用の役割分離も選択には作用したが必要原文9/15から改善しなかった。両案は撤回済み。同じ6問で重みや閾値を変更し続けない。

これまでのC7診断では利用の根が0件で、利用の辺まで有効に働いた実証になっていない。欠落が0になるまでモデルを呼ばない運用では、回答後の引用や読み直しによる信号も新たに得られない。既存の`StudyAdmission.admit`は`purpose = pilot`の場合に既知の欠落を記録して入場でき、`comparison`では欠落を拒否する。この既存経路を使い、製品の採用条件や95%の最終目標は変えない。モデルを走らせれば欠落が解消するという成功前提も置かない。

- runtimeは復元した`3551bb5ad8df6ce3387e237e80f5c27f6f5149762edb0c70b75de893ce82687c`に固定する。新しい空DB・新しいチャットでseedを取得し、題材1/2/3、同じ質問の2周目まで6段階を1反復だけ行う。途中でruntimeを変えず、修正が必要なら別のseedからやり直す。
- モデルは`gpt-5.6-luna`、推論は`xhigh`、AGENTS無効。モデルの代替は許可しない。LLVMの既存固定commit・seedと題材の既存質問を使う。freshも同じ時期・同じモデル/推論/対象/質問/ハーネスで各段階1回取り直す。各段階はfresh→memoryの順とし、freshの履歴は次へ渡さない。
- 課金されるseedの前に、同じruntimeで空DBのnative Pre/Post/Stop、消費の辺、出版ACK、終了、source-only回復を検査する。保存と索引の完了を確認する。各memory段階の配送を見る前に、そのsnapshotに存在する必要原文を凍結する。事前の必要範囲の定義は変えず、不在と未配送を分けて記録する。
- 各段階では`pilot`の既存preflightを通し、実本文・SHA・既知の欠落・意味検索・ACK・両laneのwarmを記録する。knownOmissionsを隠したり比較合格へ書き換えたりしない。個々のnative hookが30秒内に終わることは維持する。
- 私有の利用記録を保って段階を進める。利用の種類別件数、同じ内容/範囲への結合、配送時点とPre時点、実際に保存済みかつ未配送だった範囲の再消費を確認する。読み直しを無条件で「必要」の正解へ昇格しない。利用の辺からMatch/Union/completedを作らない。
- 入力＋出力、cached input、失敗した試行の消費を全て記録する。seed費用は別記する。各6段階を個別に報告し、最良値を選ばない。単独1反復では実装の総token改善・回答品質維持・一般化・製品採用を主張しない。
- 全体のowned RSSは4 GiB未満、停止guardは3.5 GiB、空き容量下限は2 GiBを維持し、実行は直列にする。モデルやprotocolが使えなければエラーと消費を保存し、別モデルへ切り替えない。
- 新しいseedと回復が確認できたら、終了したC7のDBとcacheを削除する。各段階の記録捕捉後に不要な実行体/cacheを削除し、圧縮archiveへ残さない。進行中の共有snapshotと私有利用記録だけを保持する。

これは既知の欠落のある開発セットで、実際の利用の信号と6段階の費用を観測する診断である。最新AGENTSの同じsnapshot・質問・モデル・推論・harnessで事前に決めた同数の複数反復、総token改善、品質と期限を満たすまで新しい変更を本体・README・releaseへ採用しない。80人・複数DBの実用化、95%配送と論文の範囲は維持する。
