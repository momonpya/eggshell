# 選択済み原文から得られる文脈信号の読取り診断

2026-10-28、実行前に固定。spellingの順位分離は同じ候補・費用・束縛で4/5のままだったため撤回した。既存scoreの重みの再調整はしない。

今回は製品の選択器を変更しない。同じ保存済みcanonical原文、実選択trace、現在質問の記録済みfocusだけを読み、選択済みの原文にある語から、未配送の別の局所文脈を識別できるかを調べる。正解位置・語・題材の判定は診断器に渡さない。

比較する原文範囲は、実traceのbindingAuditにあるgraph witnessから作る。所有者・原文bindingで対応する既存行だけを取り、現行`Records.closeIndices`をそのまま適用する。これは現行`prepareCached`のcombined unitと同じ既存の閉包であり、今回の答えに合わせた包含最大化・新しい範囲幅・関数定義の認識を追加しない。同じ行集合は一つにまとめる。fileとfingerprintが違うものは別のscopeとし、VCSは前提にしない。

起点は、実配送されたcanonical行とする。同じscope内で、語tに対して配送済み行の字句の和集合C(t)、その行の現在質問focus係数の最大値a(t)、候補recordにtが現れる頻度d(t)を作る。未配送record rの信号は、共有語についての`a(t)/d(t) × |A(r)\\C(t)|/|A(r)|`の最大値とする。字句は既存`SearchRank.terms`を使い、原文codeだけから取る。語の除外表や新しい係数を入れない。

これは行を起点にした**信号の診断**であり、Astraが仮定した選択単位の同一性や、予算付き置換を実装したものではない。費用で割って配送順を決めず、ここでは追加情報の有無を先に判定する。候補は全て既存のwitness閉包であり、短い断片へ任意に切り直さない。

順位は有理数の交差積で比較し、FloatやJSON数値の丸めを使わない。順位確定後にだけ凍結項目と座標を対応させる。一位の候補に残る必要原文全体がない場合は、この信号だけで改善する仮説を停止する。別の語・幅・閾値・次数の指数を合わせない。順位が良くても95%配送、数秒、総token、品質、80人の証拠とはしない。

現在のruntime、DB、共有/私有索引を変更せず、新seed・warm・再埋め込み・回答モデルは0。診断用のnative実行体は記録後に削除する。

## 固定した診断の結果

同じ実選択の42所有者・4,243行を読み、配送済み2,373行から文脈を作った。graph witness 3,129件を既存recordの閉包へ対応させ、366種類の閉じた行集合を得た。そのうち未配送の183候補を順位付けした。

残る入力言語判定128〜137行の全体は、**25位（0始まり24位）**だった。最大のbridgeは既存字句`Pf`、候補頻度2、未見語27/28。1位は別の5472〜5496行で、必要原文全体は含まない。事前の停止規則により、この信号だけで欠落を直す仮説は棄却する。語の長さ、頻度、幅、上位件数や係数を合わせず、製品フックへ接続しない。

読取り診断は5,829 ms、guardの合計RSS標本最大129,952 KiB、終了0・残存PID 0。これは製品フックの所要時間ではない。最初の二つのビルドはLeanの識別子と既定値の型の問題で失敗し、有限添字へ直したビルドが成功した。全guardを残す。

原文の範囲が完全な候補に存在することと、必要な依存先を識別できることは別である。今回の結果は、同語・希少性・未見文脈だけでは後者を識別できなかったことを示す。4/5候補の配送、総token、品質、95%や80人利用について新しい成功はない。
