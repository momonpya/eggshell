# 出版差分による推薦索引の更新

2026-10-25。親候補 `f8577e2` では、元の投影コピーを1つにできたが、窓が増えるたびに推薦索引を全件読み直し・再学習していた。Leanの隔離候補で、初期学習と通常更新を分離した。通常更新は元DBの出版日誌から変更された所有者だけを読み、その前後の窓の差分を使う。認定、Exact、Union、3種類のシナプス、元観測の鮮度は変更していない。

## 構成

学習済みの分割関数で窓のセルを計算し、`member:<cell>:<window>` のB-tree行に元の出現回数を保存する。鍵からセルへの別の逆引き索引は作らない。同じ窓が複数の所有者や位置に現れた場合も、最後の参照がなくなるまで推薦対象に残る。参照数の減算が保存済みの数を超える更新は拒否する。「共有参照が残れば正」「最後の参照が消えれば0」となる性質を通常Leanで証明した。

セルの代表ベクトルと分割面は、明示的な再学習まで固定する。差分更新が再学習と同じ順位・recallになるとは主張しない。参照が0の行も読出し予算を消費し、DBごとの鍵枠の2倍をposting行の上限にする。複数DBへ既存の枠を分配するため、全体の上限も維持される。実際のposting行数と枠は受領記録へ残す。

セル座標の再利用には、元の投影が保持されていることも必要になる。`ProjectionRetention` は完全に同じ不変B-tree部分を参照で読み飛ばし、変更された葉について古い行のメタデータを現在のrootと照合する。追加の窓・focus・stats更新は許すが、既存投影の差替えは再構築へ回す。探索は4,096プローブに制限し、検証不能な場合は保持済みとしない。元チャンクのバイト検証は、従来どおり消費時にも行う。

元の出版鎖が連続しない場合、行列の世代・幅が合わない場合、古い投影メタデータが変わった場合、差分や検証が上限を超えた場合は、背景の全体準備を使う。索引の各変更と新しいsource/matrixの基底は1回の原子的なhead公開にまとめる。ContractAuditでは差分経路が元の出版日誌・点照会・保持検査を通り、全候補列挙・全投影catalogue・学習関数を呼ばないことを検査した。これらのIO検査を、参照数の純粋な証明と区別する。

## 検査

独立した元窓の全件censusと照合し、共有窓の片方の所有者の削除、最後の削除、座標を再利用した再追加、全所有者の削除と復旧、focusだけの追加、旧pinを検査した。小規模では1窓の追加が6 ms・投影読出し5,299 bytesで、再学習は0だった。

0参照の行が続く例では、1鍵の枠に対して2行を読んで停止し、取りこぼしを部分検索として示す。明示再学習後は現在のrootのslotを9から1に減らし、同じ枠で残った1鍵を取り出せた。これは論理rootの整理であり、過去のページを含むファイルの物理容量を回収したという意味ではない。

独立実行体の故障試験では、2件の変更をメモリ内で準備した後、最後の参照数を不正にして失敗させた。部分公開せず、古いpinも保持した。明示再構築による復旧と、異なるDBの基底を再利用せず再構築することも確認した。同じ窓鍵の投影を実際に破損させ、別の正常な値へ修復した試験では、差替えを検出し、古い座標を再利用しなかった。

## 固定5万窓

元DB、原投影、モデル、質問、数値primitiveは親候補と同じ。最終runtimeで初期推薦索引を作り、別コピーへ1窓だけ実際のローカルMiniLMで埋め込んで追加した。

| 項目 | 最終結果 |
|---|---:|
| 追加後の推薦窓 | 50,001 |
| 差分索引の更新 | 234 ms |
| 読んだ投影 | 1行 |
| 行列からの実読出し | 46,119 bytes / 11回 |
| 保持検査 | 372プローブ |
| 変更したセル | 1 |
| 索引書込み | 39,926 bytes |
| 再学習 | 0 |
| 再実行 | 1 ms・読出し要求0・書込み0 |

全membershipは「以前の全membership＋新しい元窓の出現回数」という独立計算と一致し、学習済みの分割面・代表ベクトル・旧pinは不変だった。コピーした原DBと原行列の更新前prefixのSHAも、それぞれ元の432,031,994 bytesと343,002,049 bytesに一致した。これは推薦索引の更新時間であり、他のproducerを含むwarm全体の更新時間ではない。

最終runtimeの実UserPromptSubmitは、固定clock質問3組の初回8,337 / 7,244 / 7,229 ms、ACK後の継続3,992 / 3,933 / 3,736 ms。全6回で意味検索完了・前景warm0、原文本文と継続時の空本文は親候補とSHA一致。質問1の直接provider応答も、同じ4,101所有者の全順位・根拠窓・related・coverageが一致した。全49,969所有者のrecallや、LLVM題材1〜3の品質・トークン比較とは区別する。OSページキャッシュはflushしておらず、少数試行から速度改善率やp99を主張しない。

途中の失敗・投影保持検査を加える前の試行も残した。読み取り専用の元DBのcloneをそのまま更新しようとした失敗は、head不変を確認してから、異なるinodeを持つ試験用コピーだけを書込み可能にして再実行した。成功したローカルMiniLMの追加埋め込みは予備試行と最終試行で各1窓、回答モデル・新seedは0。

全guardは終了し、所有processは0。途中の失敗を含む最大合計RSSは1,527,104 KiBで、3.5 GiBの停止境界内だった。元DB・字句・原投影・cloneの14ファイルはSHAが不変。
