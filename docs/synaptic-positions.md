# 導出辺から後続の原文行が消える不具合

抽出器の汎用的な位置欠落を修正した隔離候補である。
配送選択の改善・総トークン改善・回答品質・最終採用とは区別する。
順位式・MiniLM・配送プロンプト・認定規則は変更していない。

## 不具合と修正

旧`terms`は同じ種類/文字列を出力全体で1度だけ返し、`Trace.outputs`も同一呼び出しの1位置だけを保持していた。
同じ識別子が別の原文行に現れていても、後の行は導出辺の候補から消える。
選択器へ渡る前の欠落なので、選択の重み調整では回復できない。
一方、既存の`cuePieces`は位置の区間分割と最良順位によって重複被覆を抑制しており、
同じ根拠の重複加点を今回の原因だと断定しない。

`termOccurrences`で出力の全出現位置を保持し、転置表の種類/文字列/発生IDの先に位置列を置く。
ツール引数には従来どおり同じキーの最初の位置を1つ使う。
同じ引数を2回書いても、同じ出力の証拠が2倍にはならない。
完了通知の再送でも出現位置を追加しない。原文行への射影、元観測ID、指紋、実測時刻を保つ。
出力の文字配列は1完了ごとに1つ作り、各位置は同じ配列を参照する。

旧コミット`e026cee`の抽出器を凍結し、名前空間と試験入口だけを分離して、同じLeanプロセス内で比較した。
出力`first SYMBOL\nlater SYMBOL\n`と引数`SYMBOL SYMBOL`に対して、
旧版の証拠位置は`[6,12)`だけ、新版は`[6,12)`と`[19,25)`になる。
質問やLLVMの正解範囲を使わない最小反例であり、旧版をもう一度動かして欠落を確認した。

## Leanで持たせる証拠

開始時の`Pending`に、元の`Consumption`、実引数と実出力の文字配列、
両方の位置で同じ語が現れること、範囲内性と既存の有効性検査を持たせる。
文字配列を一度作るため、各語の検査で原文全体を走査し直さない。
検査した`pending.edge`だけを完了時にグラフへ渡す。

- `Pending.input_literal`: 指定されたツール引数の範囲が辺の語と一致する。
- `Pending.output_literal`: 指定された実出力の範囲が辺の語と一致する。
- `Pending.output_within`: 出力範囲が非空で実出力の文字数を超えない。
- `Pending.before`: 生産側の完了が消費側の開始より厳密に前である。

Unicodeの位置はバイトでなく文字の位置で扱う。
Leanの標準基盤以外の公理・`sorry`・`native_decide`を追加していない。
これらは実文字列と時刻の整合性の証明であり、文字列の共通部分が意味的な必要性や真の因果関係を示すという証明ではない。
引き続き推薦専用であり、Match・Union・completed・現在の操作省略を生成しない。

## 検査

後ろの同じ識別子が、元観測の10行目と12行目の別々の原文行へ戻ることを回帰試験で確認した。
先行する日本語・絵文字、重複引数、完了の再送、語の変更と位置ずらしも検査した。
従来の抽出/Unicode/引用/利用、索引推薦、厳密移行、私有journalの時間/ACK/共有境界の試験も通過した。
実Pre/Post/Stopと新規チャットのstdoutで3種の関係を確認し、破損した任意索引でも通常配送の本文を保った。
対応する凍結runtimeのContractAuditと上記4定理の依存も確認した。
通常worktree全体のビルドやinstalledへの適用とは区別する。

前回と同じ6snapshot・同じLLVM revision・同じ6問・同じ予算で、題材1から各2チャットを再測定する。
前後のデータは同じ移行済みheadを使う。手動の必要範囲は配送後の監査にだけ渡す。
同じ6問で重みを調整せず、部分探索の不採用・期限・受領・実配送の欠落もそのまま記録する。

位置保持だけの中間候補は検査を終え、不採用とした。
前回と同じ移行済み6headで、欠落数は第1実行が1/0/3/1/0/7、第2実行が1/0/3/1/0/3だった。
段階6の第1実行は28858msでdaemon受信期限に達し、原文の代わりに未完了通知を返した。
11フックでは実本文が届き、残る1件の受領は欠損として保持した。
計測runnerのexit 0を機能上の合格と扱わず、「全12本文が一致・全配送成功」とは報告しない。

`SynapsePayloadAudit.lean`で、正解や質問を使わず実DBと配送本文だけを監査した。
850件の導出事実のうち505件が数字だけの一致で、`1`が438件、`//`が149件、`/`が29件あった。
数字を識別子、区切りだけをパスと扱う旧分類が残っていたためである。
この件数を有益な関連度と解釈しない。位置欠落の修正は必要だが、それだけでは分類の誤りも増幅する。

別の監査では、同じファイル指紋・行番号の原文に矛盾はなかった。
第2周の通常本文には原文行の重複が170〜346件あり、異なる所有者の同じ行は実際に重複配送されていた。
ただし、これは行の件数の監査であり、総トークン削減率やメタデータまで省略できるという主張ではない。
失敗・分類の内訳・本文・証明・実行体の凍結物は`candidates/synaptic-positions-review.json`へ保存した。
終了済みの試験/不採用実行体は、復号後SHAを検証したgzipに可逆圧縮し、元SHAと復元先を保持する。

続く候補では、既存Unicode表による名前の字句条件と数字/無名パスの不採用をLeanで定義する。
題材別の除外語や重みの変更ではなく、辺が主張する語の種類を検査する。
