# 原文を直接引く配送経路への変更

現在の候補は不合格。実フック0/15件という結果を、Leanの証明や合成試験で相殺しない。

後続の原文view候補も不合格。題材2は全体被覆問題を外して13,338 msで119,349 bytesを返したが、必要原文は0/6件だった。細切れの直接frontierは撤回する。原文viewの出版差分と共有読出しの部品を、必要範囲のまとまりを保つ配送へつなぐ必要がある。未完了・残る計算・削除した試行データは[prepared-record-delivery.md](prepared-record-delivery.md)を参照する。

## 確認した設計上の問題

現経路は`indexedDiscoveryUsing → renderAutomatic → SharedRangeAdapter.plan → choose?`の完了後に本文を返す。推薦にも全候補から作る被覆問題の完了を要求している。期限を超えると、途中に有効な選択があっても本文が返らない。厳密な認定の完全性と、推薦の選択を最後まで計算することは別の要件である。

題材2の実入力は18,974候補・724走査だった。期限を外して得た本文も3/6件であり、選択順を変えない高速化だけでは95%にはならない。木に置き換えた候補も全葉の再走査を残し、直近の親に対する速度改善を確認できず、撤回した。

さらに16秒付近に、同じ束縛の原文範囲を候補ごとに重複除去し直す処理を確認した。範囲を作成時に保持する別候補では1,024範囲×128照合が353→1msになったが、実フックはなお29,023msで本文なしだった。単独の高速化だけで前景経路の仕事量を変えていなかった。

配送用のcacheにも非対称な経路がある。`CanonicalSource.prepare/observe?`はファイル行を対象にし、`observe?`は`.original`を扱わない。`SharedRangeAdapter.prepare`はcanonical行がないと`prepareOriginalRecords`へ進み、照会ごとに一般出力の原文単位を作る。一方、`ObservationContext.Prepared.catalog`には、ファイルの有無によらずJSON項目・複数行の文字列・一般テキストを列挙する実装が既にある。新しい抽出器を追加せず、この既存の列挙結果を出版時の原文viewと配送へつなぐ。

## 次の実装境界

1. **原文の読み取り用viewを出版差分から作る。** 元観測digest、元座標/JSON項目、実bytes、操作と出典への参照を持つ不変recordを準備する。file aliasは任意。shell文法、ファイル座標、Gitの有無によって原文が候補から消えない。同じpayloadを共有しても、観測・権限・来歴の束縛は残す。
2. **vector・字句・3辺を同じrecord IDへつなぐ。** フック内で所有者の出力全体を解析して原文単位を再構築しない。現在の質問による入口と展開は照会時に行い、不変の原文単位や隣接表の準備と分ける。
3. **DBサービスがpinした準備済みviewを共有する。** DB/scope/publicationに結び付く有界のcacheを使う。80接続ごとの全体復元を避け、追加・変更されたrecordだけを更新する。既存の共有準備APIがあることと、実フックがそれを使ったことを別々に検査する。
4. **推薦は直接取得・配送する短い前景経路へ変える。** 全DBの被覆問題を毎回構築し直さない。原文と出典を含む有効な配送候補を保持し、追加の探索が終わらないことだけで全本文を失わない。位置の通知だけを原文配送とは数えない。認定は完全な索引と元観測・Exact・鮮度の検査を維持する。
5. **失敗した実入力を単体で再生できるようにする。** 候補・費用・cue・範囲を損失なく保存し、抽出・準備・選択・描画の境界で時間と未配送理由を測る。合成試験だけが速い構造を実フックへ積まない。同じ一連のwarmと3題材の繰返しを探索手段にしない。

warm済みの通常照会は数秒で本文を返すことを目指す。30秒は上限であり、通常の目標時間とは分ける。新しい経路も未達の候補として分離し、同じ凍結済み必要原文の95%配送、期限、同条件での総token改善と品質を満たすまで採用しない。判定を位置通知や単体試験へすり替えない。

現在の15項目は旧固定snapshotの診断用として保持する。実験runtimeを固めた後の回答モデル比較は、新しい空DB/チャットのseed、題材1/2/3と両周、事前固定の同数複数反復で行う。既存seedを使った診断と新seedの実験を混同しない。
