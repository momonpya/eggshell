# 共有する出典枠の費用をまとめて払う対照

2026-10-29、再生前に固定。候補の重みや回答モデルは変えない。現在の実配送は診断27/47であり、目標98%は未達である。

同じ保存入力の監査では、未配送の17テスト範囲の索引行はすべて正の評価値を持つ候補にあり、選択は0行だった。別の3範囲では、索引行は全て選択済みで、索引に対応がない原文が欠ける。この二つを一つの原因にしない。後者について、取得処理は単独行の一意性だけを使い、証明済み`anchoredRun?`を呼んでいない。原文残差の失敗候補を再試行しない。

選択側には別の仮説がある。同じ出典frameを共有する短い行は、最初の一行だけならframe全額を負担するため、既にframeを払った大きいファイルの追加行に負ける。現在の大きい代替は括弧の構文から作るので、一般テキストやテストの行には同じ償却の選択肢がない。

一つの対照だけを試す。既存の同一file fingerprintの観測済み行と、その一つの出典frameを払う代替を追加する。未観測の隙間は補わず、ファイル全体を読み込まない。元offerは全て同じ順で保持する。代替が既存cueを獲得できるのは、対応する既存offerの全payload条件を払った場合だけであり、新しいcue、重み、係数、予算、検索語や正解位置は加えない。共有のsetup条件を持つデータに対する一般の純粋変換を使い、ファイル名や題材で分岐しない。

同じcanonical行と費用の対応を検査し、変更なしの728件と費用が保存記録に一致することを先に確かめる。追加候補を一回だけ選び、選択後に固定47診断と比較する。元から選んだ診断根拠を失う、または未選択だったテストの索引行の配送可能性が増えない場合、この対照は止め、幅・重み・並び順を調整しない。成功しても、実フック、未索引行の問題、総token・品質・80人運用は別の未完了条件である。本体・READMEへは採用しない。

この再生ではDB、warm、取得、回答モデルは追加せず、関連RSSは3.5 GiBで停止する。取得側の連続照合の接続は別の変更として扱う。

## 結果：選択は変わらず、撤回

同じ費用表・原文で、元の728件の順序と費用が実記録に一致したことを確認した。一般の共有条件から36代替を追加し、構築3 ms・選択1,208 ms・費用120,000/120,002だった。**選ばれた全offer IDと順序が元の入力と同じで、全47診断の索引行の選択も変わらなかった。** 初期費用をこの形でまとめるだけでは改善せず、この候補は停止・撤回する。幅、順序、重みの再調整を行わない。[判定](candidates/setup-cost-alternatives/decision.json)、[再生と元費用の検査](candidates/setup-cost-alternatives/setup-replay.json)。

`credit_has_paid_witness`は、代替が得た任意のcueについて、その既存offerの全payloadを払った証拠があることを証明した。元offer・cost・weights・limitの保持も証明したが、証明成功を採用理由にしない。回答モデル・DB・warmの追加は0、本体・READMEへの採用も0。

## 次の具体的な欠落

独立した逆引き監査では、未配送の17テスト範囲に属する索引行は、全て正の候補にあり、選択0行だった。一方、ToolChain.h 148–218、BareMetal.cpp 222–279、Compilation.cpp 38–112では、索引行54/54、55/55、46/46は全て選ばれている。これら3範囲の実配送を失敗にしているのは、索引が保持しなかった原文である。索引行だけを数える30/47を、実本文の27/47の代わりに使わない。[原文費用からの診断](candidates/setup-cost-alternatives/missing-selection.json)。

取得の`ContentCapture.finish`は、各行の一意なsuffixだけを`Trie.selected?`で取り、`ContentCorrespondence.anchoredRun?`を呼ばない。現在の`ContentCaptureAudit`は、連続したcat/nl/awkの出力でも、繰り返す`}`を受理しないことを期待している。単独で曖昧な行を拒否することと、原文が一致する連続列の中でも落とすことを区別できていない。

次は、この取得境界で連続列の照合を接続する。全入力の指紋・EOFを検証した一意な錨から、文字列が連続して一致する範囲だけを採る。単独の曖昧な行、矛盾する別ファイルの錨、途中不一致、変更された入力、期限切れは引き続き拒否する。shell文法や題材・行番号を正解として使わず、JSON/MCPの文字列投影も同じ規則にする。入力全体をRAMへ展開せず、元出力と必要な原文範囲に比例する有界な保持にする。

新しい照合で古いproducerを上書きしたり、読取時にファイルを再走査したりはしない。既存snapshotの対応が不足する場合の明示的な準備・差分出版と、原文の保存・鮮度・認定の境界を保つ。これは未実装であり、修正済みや98%達成と主張しない。
