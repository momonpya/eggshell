# 学習型の推薦索引をwarmと実フックへ接続

2026-10-25、[全次元の分割候補](vector-partition.md)を、隔離した通常のwarm・keyed discovery・native UserPromptSubmitへ接続した。ソースは[partition-native](../tools/research/partition-native/)、[実行記録](candidates/partition-native-review.json)。意味検索の完了は最終候補でも5/6回で、実フックの合格条件は未達である。製品、本体の推薦設定、README実績、リリースには未採用である。

## 元の保存物と推薦の境界

`PartitionBuild`は準備済みの候補ドメインからdiscoveryの元鍵だけを取り、既存ブロックの元binary64をストリームで読む。focus専用の投影はdiscovery推薦枠へ入れない。質問に依存しないSHA順の16,384標本から512セルを学習し、50,000鍵すべてを配属して出版する。元行ディレクトリの全座標、重複、不足、各ブロックへの所属を検査する。数値境界のfloat32変換と行ごとのNumPy dot、MiniLM encoderは変更しておらず、Pythonの追加もない。

通常のwarmは元行列・物理ブロックの準備後に学習索引を作り、その後でcheckpointを記録する。フックは既存の索引を開くだけで、欠損や異なるbasisを前景で作成・修復しない。元DB、行列、ブロックのheadを検査し、元所有者の追加・削除後の古い索引は未準備として扱う。派生memoだけの更新は、当時のheadから実際の出版日誌をたどり、元所有者の変更がなかった場合だけ再利用する。履歴の欠損や上限超過を「変更なし」と解釈しない。

更新時は同じ索引の新しいrootとreadyを一度に出版し、以前にpinしたreaderは旧ページを読み続ける。DBのidentityとauthorityを保ち、別DBの索引は拒否する。互換用の形式番号や旧wireの別名は加えていない。

前景は全セルの重心を比較し、DB全体で合計4,096の元鍵、合計8,192の物理行を上限に推薦する。これは以前のnative経路の上限128葉×32鍵に相当し、前の部品実験で固定した3,125鍵と同じ候補数の対照ではない。複数DBの枠は合計を超えないよう分ける。推薦された窓は元の位置、所有者は元のordinalへ戻し、Floatの同点がセルの列挙順で変わらないようにする。

受領記録には、元head、索引basis、推薦枠、読んだセル数、全セル数、未探索の鍵数、部分的に読んだセルの有無を残す。安全なFloat上界や厳密な停止は主張しない。4,096鍵を読む場合、残る45,904鍵は未探索である。推薦窓の元所属・Work・原文の検証は従来のresolverが行い、推薦からUnionやcompletedを生成しない。完全なe-class認定、3種類のシナプス、鮮度の経路は変更していない。

## 更新と資源の検査

合成65鍵を準備した小規模検査では、cold照会が索引を作らないこと、再warmの追加書き込み0、派生memo出版での再利用、元所有者追加後の古い索引の拒否、66鍵への更新、更新前readerの保存、別DBの拒否を確認した。同じ所有者番号を異なるDBに置き、元のsource/ordinal/window順も確認した。ゼロの推薦枠では重心を読まない。DB数1〜64と4種類の総枠による256条件で、枠の合計と各DBの上限を検査した。これは実際の複数DBの並行フック試験ではない。

通常Leanでは、標本と窓のPermutation、元所有者のidentityのPermutation、codec往復、source scope、各DBの枠が総枠を超えないことを証明した。ビルド時に通常の許可された証明依存だけであることを検査し、ContractAuditも実行した。これらは推薦の再現率やIO全体の証明ではない。

最初のfixtureはベクトル用の親ディレクトリを欠いていた。次は、元データ用の鍵を書きながら空の変更差分を申告し、既存の保護で拒否された。fixtureを実際の`memo:`名前空間へ直した後に成功した。保護を緩めず、失敗ログも残す。

## 明示warmと実フック

同じ書き込み禁止の固定DBと既存の私有キャッシュを使い、runtimeのSHAと3質問、新チャット/ACK後継続の各3組を実行前に固定した。LLVM題材1・2・3ではなく、以前の規模診断と同じclock質問である。warmは別の子プロセスで終え、準備heapを前景へ残さない。stdout・本文・出版・ACK・履歴状態・検索状態・manager終了を照合する。

初回の明示warmは197,539 msで、元文書の埋め込み0件、元行列・物理router・blockの追加書き込み0だった。うち学習索引の準備は39,478 ms、学習2,921 ms、全件配属14,315 ms、書き込み6,665,935 bytesである。全体には従来の全キャッシュ検査と99,969行の元投影検査も含むため、新索引の準備時間だけでimport全体が高速になったとは扱わない。生成Cでも学習・restoreが対応する計測clockの間に評価されることを確認した。

再warmの索引準備は4 ms・追加書き込み0だった。ただし再warm全体は153,176 msであり、全体検証の固定費は残る。この時間を4 msと表示してはいけない。

最初の接続候補は、初回24,031 / 23,305 / 22,633 ms、継続23,618 / 22,297 / 22,719 ms。全6回で意味検索が約14.3秒で時間切れとなり、字句の原文21,346 bytesと、ACK後の正しい空応答を配送した。期限内に本文が届いてもベクトル経路の合格ではなく、意味検索の検査は失敗として残した。

期限を外した同じproviderの診断では、推薦後の4,132窓の採点が11,779 ms、うち元ブロックと索引の読出しが11,395 msだった。内積は合計2,233 µsで、元ベクトルのhitは2,734、missは1,398。2秒の数値daemon標本では、元ブロックと索引ページのBLAKE3計算が支配的だった。標本区間を全体の時間割合にしない。profilingした実行の時間も速度比較へ使わない。

そこでLeanの既存BLAKE3の6関数にコンパイラの`inline`属性だけを付けた。属性を外したソースが元ファイルとバイト一致することを検査し、計算式・保存形式・ダイジェスト・検証の省略は加えていない。この候補の直接provider出力は、元の4,101所有者の全順位、根拠窓、related、coverageと完全一致した。同じ4,132窓の採点は9,489 ms、うち読出し9,073 msだった。各1実行の診断であり、一般的な改善率やp99の主張にはしない。

この最終候補も、実行前に同じ3質問・3組を固定して測った。

継続は全3回で、確認済みの履歴を重複配送しない正しい空だった。stdoutと出版SHA、初回のACK、初回/継続の状態、manager終了・endpoint撤去を照合した。ここでいう「意味検索完了」は検索処理の完了であり、作業を省略する権限の`completed`ではない。この合成課題では後者は0である。

最初の1回を除外せず、意味検索5/6回のまま不合格として保存する。runtime・索引の準備contractは実際の`Warm.required`で照合し、同じsource headの前のwarm証拠を再利用した。準備の全体検証を繰り返さずに済ませたことと、前景の最初の失敗を区別する。旧候補と最終候補の測定順は固定の前後比較で、OS cacheはflushしていない。

元DB・字句の6ファイル、元行列・物理routerの7ファイルは実行前後でSHAが一致した。全guardは終了済み・所有プロセス残存0で、途中の失敗を含む最大合計RSSは2,088,672 KiBだった。追加の回答モデル・新seed・元文書埋め込みはいずれも0。失敗ログを保持し、アーカイブは作成していない。

## 残る条件

ここで使う512セルと全体metadataの準備、元の物理axis/block基盤、basis変更時の作り直しは100万窓以上の最終構成ではない。現在は学習したセルと元ブロックの配置が異なり、推薦後も多数のブロックを検証する。次はこの物理配置と検証費用を減らし、最初のフックでも意味検索が安定して完了するかを測る。重みや対象質問に合わせて推薦枠を縮める方には戻らない。

さらに変更分のsegmentと再集約へ進め、全体の再準備・重複した保存・更新時の肥大を除く必要がある。安全な採点上界、階層化、実際の複数DB・共有並行利用、p99、MCPの保存前policyと実利用も未完了である。

数値上位の保持、必要な原文の配送、回答品質、総トークン改善は別の検査である。前の部品実験にある自己照会の取りこぼしも残す。必要原文の独立した保留条件と、同じsnapshot・質問・モデル・推論設定・harnessによる題材1・2・3の両周・複数反復の総トークンと品質の採用条件を満たすまで、本体へ取り込まない。Phases 0–6は継続する。
