# 実験監視器の停止と回収

2026-10-24。研究用制御器の変更であり、配送候補の採用ではない。

固定runtime `efb9a11d…` のseed2を空DB・新規チャットから取得したところ、
監視器が合計RSS 3,146,720 KiBで停止した。利用者の上限4 GiBには届いていないが、
内部の停止閾値3,145,728 KiBを992 KiB超えていた。
生RPCで最後に観測された消費は148,913トークンで、最終消費は不明である。
この試行を成功seedに含めず、元出版・日誌・生RPC・失敗費用を保持する。

監視器は終了時に所有プロセスを一度だけ取得してkillし、その後は残存を観測するだけだった。
最初の回収中に別のフックがdaemonの起動を終えると、その新しいdaemonとworkerが残る。
実試行では3プロセスが残り、別の回収記録で実際の残存0を確認した。
元の失敗記録を成功へ書き換えていない。

`ResourceGuard`は同じ2秒の回収期間で所有集合を取り直し、新しく現れた子も回収する。
検出したプロセスの開始時刻を保持し、親から切り離された後も識別する。
監視器とその祖先をシグナル対象から除く既存の型・証明を各回に使う。
空の集合が100ms続くことを確認し、最後に再取得した実集合を記録する。

停止閾値の既定値は3 GiBを維持し、許容する最大設定は3.5 GiBとした。
設定値が4 GiBから512 MiB以上の余裕を取ることはLeanで証明する。
これは設定値の性質であり、OSの実RSSの上限を証明したものではない。
実測値と回収後の残存集合を引き続き保存する。生成開始前2 GiB・実行中512 MiBの容量条件は維持する。

`ResourceGuardCleanupChecks.lean`は、最初の子がkillされた直後に、保護された試験側から
同じ所有prefixを持つ別の子を起動する。実モデルや大きなメモリ割り当てなしで、
初回の回収後に現れるdaemonを再現する。旧監視器の取り逃しと修正後の回収を同じfixtureで比較する。
