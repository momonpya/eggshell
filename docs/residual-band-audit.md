# 固定した25価格の解集合を調べる診断

2026-10-30、実行前に固定する。新しい選択候補ではない。既存の前線候補は不採用のまま、保存した25個の価格をそのまま再生する。価格、費用、重み、offer、予算、基準の選択を変えない。人手の必要範囲を読む前に全価格の極小・極大source cutを確定する。

各価格で元の極小cutの報酬・費用・頂点数・辺数・phase・augmentationが前回と一致することを要求する。flowの残余グラフでsourceから到達できる頂点が極小側、sinkへ到達できない頂点が極大側になる。両側について同じflowとのcut値一致を独立に検査し、小規模networkの全cut列挙で最小cut全体の共通部分・和集合とも比較する。残余閉集合の上下界はLeanで証明するが、任意networkのmax-flow/min-cut定理を形式化済みとはしない。

極小・極大から実offerを復元し、元Problemの両費用を再計算する。payload nodeだけが入っていても、それを持つ実offerがなければ配送とは数えない。両予算内の極小と予算外の極大を持つ価格だけを、正解を使わずに境界として選ぶ。その後で原文対応と既に凍結した題材1の3項目を読み、各境界の上下界を採点する。

境界でだけ診断用oracleも調べる。凍結項目の原文nodeを種に残余閉包を取り、同じ最適cut値を持つこと、復元した実offerがその項目を覆うこと、両予算内であることを別々に記録する。これは正解を使った存在診断で、実行時の規則や候補には使わない。失敗から全予算内の解で不可能とは結論しない。

同点の解に欠落がなければ、同点の並べ替えを新候補として実装しない。同点に実予算内の証人がある場合も、今回のoracleを採用せず次の候補を別途固定する。実フック・回答モデル・新seedは呼ばない。完了したhelper build/cache/logは小さい証拠を抽出して削除する。

解集合の記述は[PicardとQueyranneの一次資料](https://publications.polymtl.ca/5993/)を参照する。元Problemは予算付きでORの代替も持つため、この部分問題の診断を全体の最適性や配送98%の証明として扱わない。

## 結果：この欠落は同点の選び直しでは救えない

保存済み25価格を再生し、極小cutの全ての固定統計が前回と一致した。両端のflow/cut証明書も全て通った。独立した全cut列挙との比較は、意図的な同点・孤立nodeを含む33 networkで、最小cut全体の共通部分・和集合・指定nodeからの残余閉包が一致した。残余閉集合の上下界のLean証明もkernelで確認した。[全結果](candidates/residual-band/result.json)、[native依存87 objectの整合](candidates/residual-band/native-closure.json)。

人手のラベルを開かず選んだ予算境界は文字軸の1価格だけだった。極小側は108,420文字/108,422 bytes、極大側は126,530文字/126,532 bytes。両側の間には1,077頂点の差があったが、どちらも必要原文は2/3だった。欠落した部分保存の3097行（67文字）は極大側にもなく、この価格の同点解の選び直しでは含められない。正解を使った診断でも、既に届いている二項目には同じcut値かつ予算内の実offerの証人があり、未配送の一項目の原文nodeは上界の外だった。nodeだけを配送として数えていない。

3/3になるのは、価格0とその次の過大な解だけだった。これは、この固定したprincipal部分問題の評価と予算では必要性が十分に表現されていない証拠である。元のORと両予算を持つ全問題について、解が存在しないことを示してはいない。必要な67文字自体が大き過ぎるわけでもない。この結果から同点SCCの選択器や価格・重みの再調整へは進まない。

全25価格の求解と両端の検査は2,483 ms、原文復元とoracle込み3,790 ms。外側guard全体10,597 ms、関連RSS標本最大200,384 KiB、終了0・残存0。実フックの時間ではない。最初のnative buildの予約語と配列境界の型エラーは修正し、失敗guardを保存した。原典snapshotは不変。実フック・回答モデル・新seedは0で、実配送10/14の基準は更新しない。新しい採用候補はない。

次は同じ代理目的の別solverを作らない。必要性の弱い信号が実際の仕事・結果・利用の関係からどこまで得られるかと、質問によらない原文対応を再構成する遅延を別に扱う。観測にない意味依存を存在すると仮定しない。98%・両周3題材・同条件複数反復の総token/品質・80人負荷は引き続き未達である。

終了した診断buildと設定1,096ファイル・111,812,019 logical bytesは削除した。archiveはない。原典2 snapshot・現存runtimeのSHAは削除前後で一致し、現存3 runtimeのlink入力651件を保持した。[削除と実行体/入力seal](candidates/residual-band/retired.json)、[削除guard](candidates/residual-band/retired.guard.json)。不要な旧replayの共通化は採らず元ソースへ戻した。その追加typecheckは既定の並列実行で-M1024のmemory上限に達しており、成功として数えない。今回の新診断自体はLEAN_NUM_THREADS=1のguard内でbuild・実行が成功している。削除済みhelperを現在もそのまま起動できるとは扱わない。
