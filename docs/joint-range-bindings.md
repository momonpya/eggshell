# 引用範囲を複数の原文単位から束縛する隔離候補

2026-10-27。親は `prepared-selection-domain`。本体・README実績・releaseへ未採用。旧C7の固定snapshotによるモデルなし診断であり、新runtimeからの新seed実験や回答モデルの比較ではない。

## 一単位に全範囲を要求していた

シナプスの `Bundles.Bound` は、一つの原観測への元位置を保持する。一方、配送候補は、その原出力の行やJSON項目などの複数の単位へ分かれる。

従来の `memberCovered` は、引用の全spanを一つの `UnitPlan` だけで覆うことを要求した。各単位の和集合が引用全体を覆えていても、その引用に対応する束の候補が作れない。範囲を細かくした結果、既存の依存関係を配送候補へ戻せなくなる条件である。重みや予約枠の変更ではない。

修正後は、同じ元所有者の選択単位の範囲を合わせ、引用の全位置を覆った場合だけ完全な束として認める。別の所有者のbytesで隙間を埋めない。複数の完全な元観測がある場合は代替候補として保持し、既存の共有費用に対する実際の追加費用で選ぶ。引用元の順位・cueの価値・配送予算・認定規則は変更していない。

束が得るシナプスの追加価値には、従来どおり完全な束の選択が必要。個々の原文が持つ独立した基礎価値は残る。共通枠や原文payloadは、束に含まれる単位間でも既存のノードIDを共有し、一度だけ計上する。

## 元範囲の索引

所有者ごとに原文の区間を開始位置で並べ、そこまでに到達できる最大の終端と単位IDを保持する。一つの位置から最も先へ届く区間は二分探索で引ける。必要範囲の終わりまで、返った区間をつなげる。各引用について全候補を走査する処理と、同じ所有者集合を束ごとに作る処理を置き換えた。

この索引は推薦の候補を提案する。受理する前に、元の区間検査で同じ所有者の和集合が全spanを覆うことを再確認する。範囲をつなぐ提案器そのものを認定に使わない。現時点では同じ照会の所有者ごとに一度準備し、80接続での共有や出版差分への接続まで完了したとは扱わない。

`covers_position` と `member_covered_positions` により、受理した引用の各位置が、その元所有者に属する選択済み単位の原文範囲に含まれることをLeanで証明した。公理は標準の `propext` / `Classical.choice` / `Quot.sound` の範囲。認定に使うWork/Match/Unionの生成規則を変えていない。

## 検査した範囲

- shellやファイル座標を使わないMCP形式の元観測で、一単位では失敗する引用を隣接する二単位で完全に束縛するnative回帰試験。
- 1文字の隙間がある場合と、別所有者の原文を混ぜた場合の拒否。
- 区間索引の170点の照会と3,600範囲を、全候補の走査による被覆と比較。
- 既存のnative束のgate。複数所有者、予算不足時の部分的な追加価値の拒否、独立した基礎価値、重複辺、展開後の費用を検査した。古いテストの入力を現行の `Routed.Hint` / `Routed.locate` へ修正し、無効な旧fixtureを通ったことにしない。

実フックの必要原文配送・所要時間と、これらの部品試験は分けて記録する。95%配送、総token改善、数秒、80接続・数年・NASの達成は別の未完条件である。

## 同じC7での実フック

runtime `10bd8331…` の通常照会は18,222 ms、範囲診断付きは18,441 ms。意味検索completed、全warm/回答モデル追加0回。必要原文はどちらも4/6件で、親と実本文117,523 bytesが一致した。候補13,645件、診断側の選択は862単位だが、描画時の原文併合があるため、単位数を実配送量として扱わない。

原文のsourceは4,421件、そのうち完全な代替がないものは113件。複数単位からなる完全な代替は19件あった。19はこの実行の件数であり、旧実装からの純増数は未計測。3,521の投影済み束から3,415の選択用の束を作り、最終的に選ばれた束は1件だった。これらは6件の必要原文の分母とは別の数である。

未配送の元所有者2件には、406件/335件のシナプスの範囲が届いており、それぞれ完全な配送候補へ束縛できた。ただし必要なcache keyの294文字やHLSLの523文字の全体を、これらの手掛かりの和集合だけで覆ってはいなかった。原文候補全体は必要範囲を覆い、該当所有者の選択は0件。これを理由に必要項目を分母から外さない。

通常の関連RSS最大2,059,472 KiB、診断付き1,758,016 KiB。部品の修正は確認したが、必要原文や時間の実用目標は改善していない。候補は未採用。[実本文・段階記録・原文監査](candidates/joint-range-bindings/records/collection.json)。

## 元の窓を再結合する追加案は撤回

同じ値・順位・予算で、独立したproducerの元範囲を複数の原文単位からまとめる選択肢を追加した。固定費がある合成入力では、既存価値21から24へ改善することと、元原文への展開費用の一致をnativeで確認できた。これは総トークンの改善ではない。

実フックでは、1,335の追加選択肢のうち1件を選んだが、19,224 ms・117,763 bytes、必要原文は**3/6へ悪化**した。従来の2件に加えて `tracked-input-language` が欠けた。runtimeは `2f67677b…`。これ以上の診断フックや回答モデルは実行せず、追加案を撤回した。失敗したソース・native試験・元本文・runtimeは[撤回記録](candidates/joint-range-bindings/window-groups/collection.json)へ残す。通常フック1回の結果であり、診断フックや性能反復を実施したことにはしない。

同じ窓幅・重み・予約枠の調整でこの追加案を再試行しない。ファイル行と一般出力で異なる原文の基底・共通枠・描画費用を、既存の出版済みrecordと来歴から統合する方針へ戻る。追加案のソースは、保存した契約と同じbytesへ戻してnativeを再構築し、実行ファイルも `10bd8331…` とSHA-256まで一致することを確認した。[撤回後の実行ファイル](candidates/joint-range-bindings/window-groups/restored-runtime.json)。新しいseed/正式な6段階や総token改善の検証はまだ行っていない。

終了済み試行、read-cache、helper、撤回用script、親runtimeの複製など12対象を削除し、archiveは作っていない。追加案の診断フックは未実行のまま取り消した。原seed、一つの準備済みcheckpoint、復元した候補と実際に依存するobject/interfaceは保持した。[削除・終了guardの記録](candidates/joint-range-bindings/window-groups/retirement.json)。
