# 参照の閉包を候補化する前の読取り監査

2026-10-28、実行前に固定。製品変更・追加回答モデル・新seed・warmは0。同じ4/5候補の実配送traceと、同じ準備済みcanonical原文だけを読む。

## 過去の実装を先に回収した

同じチャットの2026-10-21の記録に`source-definition-cues-1`から`-4`の構築と試験が残っていた。最初の試行は、native出力中の`name(`と定義形の先頭を照合し、別の観測から参照された窓をfocusへ加えていた。途中の変更は候補窓の整合、既存順序の保持、2,048文字以下の定義形の閉じ行までの追加だった。最初のnative試行の題材1では6項目中4項目が欠落した。これは当時の別seedの値で、現在の5項目と比較しない。最後の行までの補完と19チェックの成功も、全題材や総tokenの成功ではなかった。後にコード形状への依存を理由に退役した。

したがって「呼出し名から定義の窓を推薦する」という骨格は既出である。これを新しい研究成果とはしない。記録の場所は、このチャットのJSONLの47468行（最初の構築）、47559行（初回native結果）、47761行（閉じ行までの変更）、47810行（19チェック）、48034〜48035行（退役後の説明）。抽出した古いPythonは実行していない。

## 今回だけ確かめること

新しい方式を採用する前に、保存済みの範囲で依存先の候補と閉包の大きさを測る。旧試行のように推薦窓の順位を変えず、実際に選ばれた原文の行を出発点にする。

Leanの診断器は、同じfile/fingerprintの連続観測行を字句へ分け、`name (...) { ... }`の釣り合った形を記録する。文字列・文字リテラル・通常のコメントを無視し、行の欠落とfileの切替で括弧の状態を切る。宣言位置を参照として数えない。同じfile/fingerprintで形の候補が一つだけある呼出しを、一意な**構文候補**として扱う。新しく加わる候補の行にある参照も展開し、有限の行集合を一度ずつ処理する。版、取得形式、scopeを越える同名の結合をしない。

これはC++の名前解決器ではない。制御文も同じ形を持ち、overload、macro、条件付きコンパイル、raw string等には完全対応していない。対応が一意に見えても意味上の依存が一意・必要とは証明しない。曖昧なものや対象が見つからないものも全件報告し、固定の関数名や除外表で都合よく取り除かない。これらの制限を合成3チェックにも明記する。

測るのは、配送済み行数、呼出し形の数、構文候補の数、一意/曖昧/不在、初回の行から直接/推移的に展開した原文行数とcode文字数。原文は有限添字からしか取得せず、本文や境界を生成しない。正解ラベルを渡さず、記録を出した後で凍結範囲と照合する。

## 判定と停止

- 残る必要原文が構文候補の閉包に入らなければ、この抽出による改善を仮定した実フック変更へ進まない。
- 入っても、意味上の参照の確認がなければ「依存を認識した」とは言わない。制御文や同名の誤対応を含む閉包は、必要性を保証する根拠にならない。
- 追加codeだけで配送予算を超えるなら、全ての参照先を無条件で必須にする案は使えない。予算内でも、描画・出典・既存の選択を含む正確な費用の検査が別に要る。
- 比較相手や上限、形状、除外語を今回の欠落へ合わせて変更しない。診断の結果を新たな配送成功や総token改善と扱わない。

診断の実行体とbuildは終了後に削除し、結果とguardのみ残す。現runtime、seed、索引、現在の4/5候補は保持する。

## 最初の読取り結果と、選択だけの再生条件

読取り診断は6,691 ms・合計RSS標本最大129,696 KiB、終了0・残存PID 0。4,243行中2,373行が初回に選ばれていた。呼出し形2,158件のうち一意な構文候補は58件、曖昧240件、不在1,860件。278の括弧の釣り合う形のうち20件が展開され、173行・code 8,197文字が追加された。入力言語判定128〜137行の全体は、実配送された7182・7183・7248行から同じfile/fingerprintの候補として見つかった。名前や正解位置を抽出器へ渡していない。

一方、`for`と`defined`も候補に含まれた。この抽出器を名前解決器や必要性の判定器とはしない。これらの語を見た後で除外表や形状を変えない。

次に一回だけ、全ての一意な構文候補を推薦上の条件と仮定した、**選択器だけの隔離再生**を行う。原文の必要性が確認されたとは扱わず、製品へ接続しない。目的は、依存先の費用を選択前に含める操作が、固定予算でどの原文を選ぶかを確かめること。単なる優先窓の追加とは区別する。

実traceのselectorInputをLeanの正確な整数として復号する。file frameと行payloadの位置・費用を原文から再構成し、対応する全費用が実入力と一致することを検査する。まず変更なしの選択器を再生し、実記録の物理payload集合と一致しなければ停止する。その後だけ、各offerへ、その原文にある参照の推移的な候補範囲を追加する。費用表、cue、重み、offer順、固定費、二つの上限は保持する。参照先の追加は無料にせず、同じ原文の共有費用は一度だけ払う。新しいcueや加点は作らない。

選択後に、宣言した条件が閉じていることと予算を検査する。出力した原文キーだけを凍結範囲と照合する。旧4件を落とす、必要全体が戻らない、費用の対応が一致しない場合は、除外語・重み・件数を調整せず停止する。この再生を実フック配送、30秒以内、総token改善、95%の合格とはしない。

## 選択器の再生結果

最初の再生は診断器が`tools.VerifiedWinnerCoverage`をimportせず、参照版の`choose?`を呼んでいた。78,597 msで当該の子プロセスだけをTERMし、guard終了143・残存PID 0を確認した。本番と同じ、結果の一致が証明された高速化をimportして再buildした。停止した試行をタイムアウト後に完了したものとして数えない。

本番の選択器を使った再生は、**変更なしの物理payload集合が実フックの記録と完全一致**した。全4,243行のpayloadと各file frameの費用も元の実入力と一致した。そのうえで、同じ費用表・cue/重み・offer順・固定費・上限のまま、構文候補の原文を条件へ含めた。
