# 空の共有payloadによる虚偽の被覆を除く

隔離候補・未採用。実行物 `b0424224a8bfbec49db71bc0a404aa7750e3495ca7c70a10b51411d200632681`。親は受領準備候補。前段の説明で、未配送7件中6件が「全原文を選択済み・単独費用0」になっていた。その原因である空のcanonical行配列を、共有payloadとして構築・復号できない型にした。

`Delivery.Part` は行が非空である証拠を持つ。constructorとJSON境界で空を拒否し、配送ACKで残りが空になればPartを返さない。canonicalの空配列は表に挿入せず、描画側も検査済みPartだけを共有経路へ渡す。file対応がない場合は元の任意ツール出力のenvelopeを作り、原文recordを使う。コマンド、質問、正解範囲による特例はない。

通常のコード、JSON文字列、日本語、MCP形式の構造化出力の合成試験では、全原文が候補の和集合に残り、全単位の費用が正で、native-controlは0。空/壊れたJSONの復号拒否、構築拒否、制御フィールド保持のLean証明を確認した。新規FullSearchOracle、ContractAudit、シナプスの依存監査も成功している。

既存CanonicalHookTestsには、個別行を検証する現行の受領関数に対して「1行の改変でfile全体をuncertainにする」と要求する断言と、全record候補の費用を最初の1候補だけと比較する断言が残っていた。最初の実行はそこで失敗した。製品の受領関数は親から変更せず、改変行は未配送・無傷の隣接行は配送、同じpayloadを別ownerが持つ場合は追加費用0、という契約を直接検査するようfixtureを改めた。指紋変更、位置だけの通知、ACK後の再送禁止、共有payloadの重複排除と制御なしも検査した。失敗したguardは残している。
