# 配送候補を対象にした全次元の分割

2026-10-25、既存routerの「12座標で分け、近い枝を深さ優先でたどる」方式を置き換えるLean候補を実装した。[ソース](../tools/research/vector-partition/)、[実行記録](candidates/vector-partition-review.json)。現在の製品・README実績・リリースには未採用で、通常Warm・keyed provider・nativeにもまだ接続していない。

## 対象と構造

現行routerは99,969投影すべてを扱う一方、discoveryで所有者へ戻せるのは、その出版の配送候補50,000窓である。focus用の投影も同じ推薦枠を使える設計になっていた。今回は配送候補だけを対象とし、対象の変更と分割の変更を分離するため、配送候補だけで作り直した元の軸分割も対照に置いた。

質問を使わず、保存された鍵の独立したSHA順序から16,384標本を固定する。標本を全384次元の重心で均等に二分し、4回の更新を行う。32標本以下の葉になるまで繰り返し、同点は元の鍵で分ける。全標本が残ることとnode codecのtail付き往復を通常Leanで証明し、通常の証明依存だけであることをビルド時に検査した。同じベクトル65件でも標本を失わず、葉の上限を守り、循環したnodeは拒否する。

全件の投影をRAMへ持たず、既に検証できる元ブロックからストリームで読み、各候補を512セルへ配属する。セルの重心は全候補で集計する。質問時は全セルの重心を比較して順に読み、32鍵以下のpostingsを、合計3,125鍵の上限まで返す。深さ優先で隣接する葉をまとめて選ぶ方式から、全セルを比較する方式へ変えた。

索引は元DB・元行列・元ブロックの各headと、配送候補の鍵集合のSHAへ結び付ける。出版時に全鍵の重複と鍵集合のSHAを検査し、変わったbasisは有効な空結果にせず未準備とする。推薦は鍵と被覆状況だけを返し、Work・Union・completedの権限を持たない。元binary64と既存のfloat32 `np.dot` は変更せず、追加Pythonもない。

球面重心と有界な学習標本は [Faissの公式clustering仕様](https://faiss.ai/cpp_api/struct/structfaiss_1_1ClusteringParameters.html) を参考にした。ここでの実装は、均等な階層分割とページ化した元鍵を組み合わせたもので、Faissを依存には加えていない。[Ram–Grayの内積探索](https://arxiv.org/abs/1202.6101) にある枝刈りの考え方は次の候補だが、現在のNumPy float32 dotに対する安全な上界はまだ閉じていない。今回の探索は予算で打ち切る近似で、厳密な停止の証明は主張しない。[2025年のPSP](https://www.vldb.org/pvldb/vol18/p1770-ke.pdf) のグラフ索引も選択肢だが、今回は元ベクトルを変換せず読む共通の後段と、小さな派生索引に絞った。

## 比較条件

同じ固定DB・元行列・キャッシュ済み質問投影・NumPy dot・所有者の元ordinalで比較した。自然言語3問は以前のnative規模診断と同じclock質問で、LLVMの題材1・2・3ではない。さらに標本へ入らない保存ベクトル8件を、独立したSHA順序で事前指定した。

後者は自己照会の診断である。分割用の16,384標本には含まれないが、通常の索引対象として全件の配属・セル重心の集計には含まれる。独立した保留リポジトリや未知の意味質問の評価ではない。質問を見て分割や上限を調整していない。

比較基準は、配送候補50,000窓すべてを元ブロックから読み、元の数値primitiveで採点したもの。最初の質問では、保存済み3,125窓の全スコアビットと、元の完全providerの上位8所有者が一致した。全11照会の完全なスコア列も保存した。モデル呼び出し・新seed・元文書の埋め込みはいずれも0回。

## 結果

全件採点で選ばれた上位8所有者のうち、各候補経路が保持した件数：

| --- | ---: | ---: | ---: |
| clock-A | 0/8 | 0/8 | 8/8 |
| clock-B | 0/8 | 2/8 | 8/8 |
| clock-C | 0/8 | 0/8 | 8/8 |
| 自己照会0 | 3/8 | 2/8 | 7/8 |
| 自己照会1 | 8/8 | 2/8 | 8/8 |
| 自己照会2 | 1/8 | 4/8 | 8/8 |
| 自己照会3 | 5/8 | 3/8 | 8/8 |
| 自己照会4 | 4/8 | 3/8 | 8/8 |
| 自己照会5 | 6/8 | 3/8 | 8/8 |
| 自己照会6 | 5/8 | 2/8 | 7/8 |
| 自己照会7 | 3/8 | 5/8 | 8/8 |

全次元の分割は各回3,125窓を推薦し、自然言語3問の数値上位8はすべて保持した。自己照会では62/64であり、取りこぼしは残る。元窓の上位32/128件についても、正解集合・実推薦集合・保持した集合を記録した。配送候補だけに絞る変更だけでは改善せず、悪化する自己照会もあったため、対象の整理だけを成功と扱わない。

512セルの大きさは57〜163件、合計50,000件。学習2,867 ms、全件の配属13,969 ms、出版2,789 msだった。元行ディレクトリの列挙4,005 msと、標本・対照の準備読出し13,943 msは別である。索引は約7.1 MiB。これは明示準備であり、フックの時間ではない。

新しい索引の推薦部分は、同じreaderの最初が299 ms、以後80〜110 msで32〜33セルを読んだ。元ベクトルの再採点・所有者検証・配送・プロセス起動は含まず、OS cacheもflushしていない。完全な数値基準の採点は13,935〜14,460 msで、こちらもnativeフックの測定ではない。

配送候補だけの軸分割に記録された0 msは速度評価から除外する。生成Cを確認すると、純粋な構築・照会の評価が終了clockの後へ移動していた。結果の集合には影響しないが、この区間は時間を測れていない。またこの対照はメモリ上、他の2経路は出版済み索引のIOを含むため、そもそも等価なIO速度比較ではない。値を消さず、実行記録にも除外を明示した。

最終ビルドと試行のguardは終了コード0、発火・残存プロセスなし。最大合計RSSは1,481,120 KiB、実試行は612,944 KiBで、3.5 GiB guardと4 GiB上限を守った。元DB・字句の6ファイル、移動前からの元行列・軸routerの7ファイルのSHAも一致した。初期のimport・型・レイアウトの失敗は保持し、実行前に捨てたhelperはSHAだけを記録して削除した。アーカイブは作っていない。

## 次の境界

このDBはclockに偏った合成データであり、数値上位の再現を必要な原文の配送率やトークン改善と置き換えない。現在の512セル上限、全体メタデータを使う準備、作り直しだけの出版は100万窓以上の解決ではない。差分更新・圧縮、セル階層やshardによる規模対応、複数DB・共有並行利用は残る。

次は推薦と認定の分離を維持して通常の準備・keyed discoveryへ接続し、元ベクトルの読出しまで含む実フックを測る。取りこぼしのない停止を表示する前に、実際のfloat32採点・複数質問窓・同点順序を含む安全な上界を確認する。必要原文の独立した保留条件と、題材1・2・3の両周・同条件複数反復の総トークン・品質・期限も未完了であり、採用条件を満たすまでは本体へ取り込まない。
