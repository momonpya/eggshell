# 実際の選択から原文の消失段階を説明する隔離候補

2026-10-27。親は `prepared-cue-incidence`。本体・README実績・releaseへ未採用。旧C7 snapshotのモデルなし診断であり、新runtimeでの新seed実験や総トークンの採用比較ではない。

## 残る2件は選択で落ちる

同じ実フックが使った `Plan` の候補・選択配列から、所有者別の原文位置の和集合を記録した。重なる範囲だけを併合し、隙間を埋めず、別所有者の原文を混ぜない。位置の診断は配送成功の宣言ではなく、独立した実本文の監査と組み合わせる。通常照会ではこの追加診断を行わない。

凍結した必要原文6件中、未配送は `toolchain-cache-key` と `complete-hlsl-branch-scope`。どちらも以下の2所有者の原文候補に完全に存在し、どちらの所有者も選択0件だった。

| 所有者 | 原文候補 | 候補の原文位置の和集合 | 選択 |
| --- | ---: | --- | ---: |
| `v6074522768795721594` | 1,114 | `[0,43243)` | 0 |
| `v8230242550905737408` | 1,220 | `[0,45212)` | 0 |

一方の所有者では凍結した必要範囲が `[14291,14585)` と `[22126,22649)`、他方では `[3753,4047)` と `[11588,12111)`。いずれも候補の和集合に含まれる。候補の描画途中の切断や座標の監査失敗を原因として扱わず、選択前に情報がなかったという説明もしない。元DBにない別項目 `dumpmachine-reports-toolchain-triple` は当初不在として別記し、6件の分母を変えていない。

同じPlanの費用と基礎cueを追加診断したところ、1,114/1,220候補の全てに正の基礎価値があった。最小候補の費用はそれぞれ1,743/1,500文字、そのうち所有者の共通枠が1,718/1,475文字だった。byte費用は1,747/1,504。価値0のfilterで落ちたのではなく、小さい原文にも共通枠の初期費用がかかる。

これは固定費を共有する選択の調査対象を明確にする結果であり、この費用だけが欠落の決定原因だという証明ではない。安価な候補が一つあることも、必要範囲一式の配送費用の証明ではない。次は実際の束と共有費用を追う。失敗済みの重み調整・予約枠・細切れfrontierを同じ仮説で再試行しない。ファイルaliasを持たない原文も、出版時に準備した同じ原文単位・来歴から扱う方針を維持する。

## 候補リストの全体コピーを除いた

候補を一つ追加するたびにclosures全体を末尾追加でコピーしていた。汎用の `LinearOutput` は逆順の蓄積と最後の一回の反転を使う。初期出力、状態更新、出力順序、重複、失敗を含む完全一致をLeanで証明し、実際のノード生成と `problemPrepared` 全体へ接続した。費用・価値・束・認定規則は変えていない。

native検査は順序・重複・状態・失敗と128候補のノード生成を比較した。`nm` でHandoffの選択objectが `LinearOutput.pairPrepared` と既存の増分selectorを呼ぶことを確認し、source・include_str・dependencyと選択objectの対応も記録した。公理は標準の `propext` / `Classical.choice` / `Quot.sound` の範囲で、`sorry` / `native_decide` は使っていない。
