## 29秒を「選択器だけ」の時間としない

二つ目の候補のtraceは、検索の開始から原文復元まで830 ms、source focusまで1,384 ms。その後にrender完了の記録がなく、受信期限に達した。この境界の後には、シナプスの原文への結び付け、根拠束の投影、候補準備、選択、描画が含まれる。したがって残る約27秒を内積・貪欲選択・描画のいずれか一つへ割り当てることはできない。

**同じddacea32実行体を変更せず**、新しい診断sessionでOSのCPU標本を2区間取った。新しい選択方式・重み・予算・期限は加えていない。元のpublicationとruntime SHAの不変を確認した。診断でも未完了となり29,113 ms。標本では次の実行が見つかった。

- `Synapses.Transport.build → IndexedBindings.resolve → Index.Reader.lookup → PageMap.getAt`。範囲の結び付け時に点照会・page検証が走る。
- `Synapses.Bundles.project`と`SharedRangeAdapter.prepareCached`。束の投影と元recordの準備が照会中に走る。
- `CanonicalSource.Delivery.merge → Registry.store → Array.qsort`。原文の再併合に加え、比較ごとにkeyのJSON化と文字列化を繰り返す。

これは2区間の標本であり、各関数の全実行時間や全27秒に対する割合の測定ではない。`source focus`の完了を、これらの準備まで完了した意味に読み替えない。暖まったDBがあっても照会側でこの準備を作り直す経路が残り、80人・増加するDBでの性能は未達である。

## 利用者の指摘後に確認したキャッシュ境界

「保存時に済ませる準備をretrieval/rerankingで行わない」が次の実装修正の条件である。上の比較キーの部品を主経路へ接続して済ませない。

固定基準の`CanonicalSource.Shared.Loaded`は、検証済みregistryと所有者への投影をサービス内で保持する。`ObservedRecordView.Geometry`にも原文の構造が保存されている。しかしクライアントは`sourceRows`受信後に`CanonicalSource.load`を呼び、`Transport.build`は再び`Delivery.merge`し、さらにHandoff側で再併合と`Records.prepare/catalogue`を行う。既存キャッシュを読む経路と、実際の選択に必要な準備済み構造を使う経路が最後までつながっていない。

保存・背景準備で保持する対象は、原文座標とbindingの対応、シナプスの接続/逆引き、抜粋recordの単位、共有payload ID、原文長などの固定費用である。出版差分で更新し、同じscope・source pin・実装の準備を共用する。現在の質問による探索、順位/価値、選択状態、必要な権限/鮮度の確認は照会側に残す。原文のACKを背景の準備完了待ちに戻さない。質問ごとの回答本文自体を出版時に固定する意味ではない。

80人・複数DBへ向けた別の明確な不整合もある。`CanonicalSourcePrepared.Pool`の容量は496 MiBだが、各entryは原文等の費用に加えて256 MiBと64 KiBを固定予約する。したがって**2 DBのentryを同時に保持できない**。`maxEntries=128`でもこの算術的制約は変わらず、複数DBの借用・退役・再準備に影響する。サービス全体で容量を共有するという契約を、この実装が満たしたとは扱わない。これはコードの上限の確認であり、80人の実負荷試験を行った主張ではない。
