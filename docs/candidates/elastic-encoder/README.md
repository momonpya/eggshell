# 要求に応じて増やし、余剰モデルを保持しない

runtime-keyから分離した未採用のLean候補。runtimeは`8bf8ab430d62bb6c6472d8829ea4c69418c682aeb1f62336985879ea68ccda73`。16/80同時の資源停止を解消したとはまだ主張しない。モデル・ベクトル・順位・認定domain・配送予算・期限は変更しない。

親は2基を一度起動すると、推論をしていない時も両方を保持する。新候補では、待ち要求がある間は両方を使い、待ち要求がなくなると温まった1基だけを残す。停止した余剰モデルは、次の需要があればもう一度起動できる。CPUに応じた同時起動上限2は保持するが、以前の512MiB/modelという実測と合わない配分値は除いた。2基の実RSSを静的に保証したという扱いにはしない。

待ち件数を既存の管理stateで数える。要求FIFOや別の検索queue、タイマー、追加の共有Mutex/Ref/CASは作らない。各検索actorは独立したまま、起動・推論・停止は管理Mutexの外で動く。待ち要求を取り消した最後の要求もidleを整理するため、取消だけで余剰モデルが残り続けない。

整理でretiringへ移したモデルは停止確認までslotを占める。新しいticket世代を付け、古い完了で別ownerのslotを空けない。実行中・既にretiringのslotは整理で変わらないこと、待ち要求がある状態では整理しないこと、待ち要求0ではidleが高々1個であることをLeanで示した。停止する値の一覧は短い管理操作が返し、それから停止する形を実装と等式で接続した。IO全体の線形化や数値ライブラリの正しさを証明したという意味ではない。

所有権の部品検査では、2つのcallbackの並行実行、管理Mutexを保持中のcallback完了、需要中の2基保持、最後の待ち要求の取消後の整理、余剰モデルの停止前の枠保持、停止中の管理Mutex利用、古い完了の拒否、一度だけの停止、activeなshutdownが通った。これらは偽のNat resourceによる部品試験であり、実MiniLM・全hook・80人容量の証拠ではない。
