## What this identifies, and what it does not

The candidate's publication-service process consumes93.31 and92.49 CPU seconds
over the two waves, including44.70 and43.83 system CPU seconds. Its captured
service sample contains216 threads. The source/index/model service is shared,
but nested dedicated supervisors, provider operations and timer/socket waits
still multiply per query. The sample also shows request-local router cell
lookups, B-tree restoration and decoding. Shared-page hits update a common
mutable cache. These are concrete next inspection points, **not** a measured
causal attribution of all elapsed time to one cache or lock. Parked thread stack
counts are not CPU percentages.

Keep per-chat logical execution and complete certification. Next remove nested
polling/dedicated waiters, and reuse immutable prepared router/page state with
request-local tracing; parallel CPU stages must fit the host's capacity. Do not
repeat this unchanged actor burst, grow the deadline, clamp certification to
advisory K, tune evidence weights, or call lexical fallback semantic success.
