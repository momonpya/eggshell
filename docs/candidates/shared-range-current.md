# 原文範囲の共有選択と生成元証明

新しい配送候補を、実用候補の検索・期限管理・memoと、開発ソースの認定証明へ結合した。
候補は隔離したままである。実フックの全6段階とLuna比較を通ったという記録ではない。

## 選択の単位

所有者全体の最低抜粋を先に確保する方式から、現在の質問窓に対応する原文範囲を、
局所の条件・結果・出典と組にして独立に選ぶ方式へ進める。
元観測の構造解析は所有者ごとに一度だけ行い、各窓の前提範囲を保持する。
同じ所有者の重複断片は、原文座標と重なりの一致を検査してまとめる。
検索窓が重なる位置へ重複加点しないよう、端点で分割した位置セルへ被覆を付ける。
重みは既存の検索順位から作り、期待する関数名・行番号・題材名を条件にしない。

`SharedCoverage`は出典枠などの共有ノードを一度だけ課金する。
選択は文字数とUTF-8バイト数の両方を型で制限し、最終的な実パケットの費用も再検査する。
推薦による原文追加はnative controlを作らない。

貪欲解に加え、単独で収まる完全な候補のうち被覆が最良のものを求め、被覆の多い方を選ぶ。
同点では元の貪欲解を維持する。宣言した費用・被覆において、結果が貪欲解と各実行可能な
単独候補のどちらよりも悪くならないことを証明した。単独候補の前提を途中で切らない。

[予算付き最大被覆の原論文](https://thibaut.horel.org/submodularity/papers/khuller1999.pdf)の
集合ごとに加算する単一予算とは、共有ノード・二重制約という条件が異なる。
その近似率や最適性、関連履歴の十分性をこの実装へ流用して主張しない。

## local Unionの生成元

`Discovery.localOrigins`は必須の証明フィールドであり、現在のlocal Unionごとに、
実際の`localUnion?`呼出しと生成時のMatch、`retrieved = false`の証明を保持する。
通常controllerは各生成バッチでこの証明を作り、継続ごとに合成する。
terminal経路はlocal Union列が空であることから構築する。
証明は消去され、Matchを受領記録のために再構築したり、等価性を再計算したりしない。

`completed_generator_origins`は、completedに使った等価性が現在の生成子から導かれ、
Exactの足跡を保ち、その各生成子が永続DBの入力か、非retrieved Matchによる実際の
local生成かに分類できることを示す。現在のlocal Unionの祖先を完了判定側の仮定にしない。
`originCertified_erases`は証明付加後も既存viewをそのまま返すことを示す。
両producerと実際の配送抽出への接続をContractAuditで検査する。

永続DBのUnion入力は信頼境界に残る。任意の過去DBのUnionが利用者コマンドだけから
生じたことや、元観測の意味的正しさを証明したとは言わない。
source reader・鮮度・memo serde・最終断片の由来とIO完全性も別の境界である。

## 統合と検査

実用候補と証明側の共通祖先は`edf25cb67f422ba122e165d25304fd71afb076c3`。
この祖先からの三方向統合で、実用候補の埋め込み・検索・warm・workerと、
現在のmemo・生成等価性・fixture分離・local生成元証明を保持した。
元のMiniLM経路・数値provider・hooks・worker・source evidence・埋め込みランタイムの
指定7ファイルは、実用候補とのSHA一致も検査した。
Matcherは実用候補の計算と証明側の追加を統合しており、バイト不変とは扱わない。
必要なhelperモジュールを全て登録し、既存ビルドの残骸だけでimportが通ることを避ける。

共有被覆の反例・重複・前提閉包・二重予算、元cue前処理との関数等式、
原文座標・Unicode・局所cue閉包・共有materialization・実費用の試験が対象である。
失敗した構文・import・証明・監査の記録も残す。
[差分](shared-range-current.patch)と[検査記録](shared-range-current-review.json)を参照。
差分は正確な原文を保つzero-context形式で、`git apply --unidiff-zero --check`による検査も通った。
アダプタIO試験、ContractAudit、test supportのbuild、TestMain全体のelaborationが成功した。
全native IO suite・モデル比較を実行した証拠にはしない。
その後、閉じた検証のコンパイラ中間物だけを回収し、native実行の容量条件を満たした。
ソース・DB・モデル・raw履歴を保持し、残すnativeバイナリとライブラリのSHAも照合した。
native準備3GiB・モデル投入4GiBの容量条件、集計RSSの3GiB停止値は維持する。

最初の統合版は題材1の2チャットで必要な元コードを落とし、モデル投入前に拒否された。
native controlの予約条件を`Selected.blocks`へ正した版も、同じ本文で同じ不合格だった。
診断で、必須範囲・小さい代替範囲・任意の周辺範囲を一つの候補へ加算していたことを確認した。
これらを完全な必須閉包とそれを含む任意の拡張に分け、同一の原文断片を複数候補間で共有した。

この修正版の全6段階・各2新規チャットを実nativeフックで検査した。
12本文は各段階でバイト一致し、16.8〜28.6秒で完了した。数値検索は完了し、
ソースベクトルの欠落・使用不能・フック内の再埋め込みはいずれも0だった。
しかし全6段階に必要な保存済みコードの配送漏れが残り、モデル投入は拒否している。
最大RSSはビルド3,002,432 KiB、全6段階の実行1,422,864 KiB。
[修正版の差分](shared-range-closures.patch)は上の統合差分に重ねる形式で、
[実配送と失敗の記録](shared-range-closures-review.json)に本文SHA・時刻・欠落項目を保存した。
この候補の新しいトークン削減率は未測定で、本体・READMEへの採用もしていない。

## 次の評価

全6段階の実フックで、DBにある質問に必要な元コードを出典・適用条件・鮮度付きで
期限内に配送できることを確認してから、候補r0を題材1から順に実行する。
[条件が一致する旧fresh](fresh-baseline-reuse.md)を対応するr0対照として使う。
停止済み旧比較へ追加投入せず、新候補と不足freshは新しい比較記録へ保存する。
最初は1反復に留め、採用判定には事前固定した同数反復の検査を維持する。

LLVMの6段階は開発用であり、独立した汎化評価とは扱わない。
[serde_jsonの保留予約](delivery-holdout-reservation.json)はcommitと質問の予約までで、
oracleや評価の凍結完了ではない。最終runtime固定後、配送を見る前に必要な原文範囲・
適用条件・実行テスト・seedを固定する。評価後に調整したら、その保留セットは開発用となる。

同一ファイル指紋だけでは、番号付き観測が正しい同一読み取りかは分からない。
所有者をまたぐ統合には原文と観測範囲の対応が必要であり、Unionの認定を省略しない。
過去回答に引用先があるだけで、結論・制約まで既配送と扱って短縮しない。
ツール呼出し0やcached input 0を誤再利用の判定にせず、実際の認定経路と正誤を分ける。
