# 返信の所有と、要求ごとの独立した読取組み立て

`compact-reply`（7035f6e0…）から分離したLean候補。本体・READMEの実績・リリースには未採用。質問、対象ソース、凍結したDB内原文、検索順位、配送予算、MiniLMは変更しない。

共有の読取窓口が、各要求の可変カウンター・bitmap・ページfrontの生成まで直列実行していた。`CheckedFrame`で検証済みの不変imageだけを渡し、読取セッションは各要求のactorが作る。渡す値から共有ページownerへの参照を削除した。カタログ検索と未準備imageの構築は依然として一つの所有者が行う。全検索が無同期という主張ではない。

元のsource順序とhead、prepared input、scopeの検査を残した。`CheckedFrame.original_boundary`、`original_key`、`local_fork`と`Session.readOnlyPages`をLeanで検査し、実際の読取組み立ての依存と渡す構造体のfield型が、共有Mutex・Promise・queue・待機に到達しないことも監査する。ファイルdescriptorの寿命・OS/FFI・Leanランタイム全体の無同期性の証明とはしない。

監査は`import all`で非公開の実装も読み、組み立ての本体が見えなければ拒否する。非公開wrapperで探索が止まった5依存の中間監査は使わず、最終版はカタログhitと統計も含む517依存・96型を検査した。共有ページownerのMutexを保持したままカタログhitと統計取得を行い、80要求が各3原典を読み、全bytes一致・局所カウンター独立・共有cache不変で完了した（部品2ms）。異なる入力・順序は拒否し、私有usage rootは共有キーに混ぜない。この数字は全フックの速度や80人継続利用の測定ではない。

従来は`Pool.stats`が毎回`pool.pages.stats`を呼び、診断のために共有ページownerのMutexを取っていた。通常受付の診断は所有者が単独管理するカタログ情報だけで作り、この呼び出しを削除した。診断用の共有ページ統計を通常の読取hitへ戻すと、実装の依存監査と、ロックを保持するnative検査の両方が失敗する。

返信は、従来JSONを構築した後で容量を予約していた。予約を構築前へ移す際、受信側が切断しても作成側が終了するまで容量を返さない二者の所有状態を加えた。終了順序にかかわらない容量保存・一度だけの解放・閉鎖後の再取得拒否をLeanで証明した。既存の容量上限は変えず、独立した検索actorも減らさない。受付・取消・終了・容量の可変状態には同期を残す。pureな状態遷移やJSON codecへ共有ロックを持ち込まない。

中間版9529d9ff…の容量検査は80/80、同時エンコード最大3、最終予約0だった。ただし最初の検査は、検査プログラム自身が読取窓口を閉じず、終了時に残ったtaskを待っていた。sampleを保存してそのPIDだけを停止し、exit143を失敗として残した。`finally`で窓口を閉じる修正後の検査はexit0・残存0。検査の終了失敗を製品配送の成功として数えない。

最終版ec1064be…でも容量検査は80/80、4MiB本文の同時エンコード最大3、最終予約0、部品252msで終了した。検索actor数を3本に減らしたものではなく、完成した返信のエンコード・保持を既存24MiB枠で制限する。返却する容量が0なら共有の容量Mutexを開かない。replyのwire容量だけで総RSSが証明されたとは扱わず、実行は既存の資源guard内で行う。

同じ原典からの実配送は6/6で合格した。各本文は親`compact-reply`の対応する本文とbyte一致し、必要原文32/32、意味検索・シナプス・packet検査・ACKは全6件で完了した。warm要求0、元の出版内容も不変だった。

セッション保守の`state.guard`待ち合わせ警告は今回も残った。読取組み立ての部品成功で、この状態更新の競合まで解消したとは扱わない。ACK後の6,554キーを次の汎用再現入力として保持し、終了済みの6実験sessionと6部品DBは削除した。元DB・現在のproject cache・必要なnative依存は保持し、DBのarchiveは作らない。

詳細は隣接する機械可読記録に残す。これらは回答モデルを呼ばない検査であり、初回・履歴ありのモデル比較や総トークン改善を代用しない。80人8時間、増大するプロジェクト、NAS、p99、品質・総トークンの採用条件は未達。
