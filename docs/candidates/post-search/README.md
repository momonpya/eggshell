# 検索後の処理の実測

未採用の診断。回答モデルは呼んでいない。旧4GiB停止の記録と混同せず、5GB条件で正常終了した同一runtime `bac5016c…` の80要求を先に調べた。

[保存済みの時系列](saved-stages.json)では、80要求すべてで数値応答を受領した一方、原文候補の記録は41件、選択の記録は29件だった。29件の選択記録はすべて未完了通知より後に書かれていた。これは配送成功数ではない。

原因を絞るため、製品を変更せず既存の時間計測だけを有効にし、3問のprimeと4件の実フックを実行した。[実測](profile.json)では全件の本文・ACKが一致し、関連RSSは2,439,072KiB、4件全完了は5,548ms。選択は551〜809ms、描画後の確定は506〜543msだった。原文viewは45〜56msであり、行の再結合をこの試行の主因とする仮説は支持されなかった。4件の診断値を80件の達成値やp99とは扱わない。

確定処理には、配送済み履歴が空でも各原文行のファイルIDを繰り返し作る経路と、最終キーの二次時間の重複除去が残っていた。続く[remaining-source](../remaining-source/README.md)で意味を保ったまま除く。全件が同じ質問だから全処理を共有できるとは仮定せず、scope・snapshot・質問・既配送状態の違いを維持する。

実験制御と所有データの削除はLeanの `PostSearchStudy.lean`。終了済みの補助実行体・コピー・出力・所有session/receiptは削除し、原DB・project cache・モデル・比較本文を残す。圧縮archiveは作らない。
