# 配送キーのバッチ更新と、ACKの準備・確定の分離

`reply-ownership`（ec1064be…）から分離したLean候補。本体・READMEの実績・リリースには未採用。質問、元のsnapshot、凍結必要項目、検索・認定、モデル、予算、期限は変更しない。

従来の`addDeliveredGraphs`は、キーごとに現在の全リストをハッシュで重複除去していた。一回の除去が線形でも、通常キーの追加列全体は二次になる。通常キーをまとめ、source scopeの状態更新に達したときだけflushする。scopeの置換規則と順序、最初の同一キーを残す規則、空入力で元のリストをそのまま保つ規則は変えない。`DeliveryKeys.batch_exact`を全入力について証明し、元の定義を保った`csimp`で実行へ接続する。

`ThreadState.deliveryClaims`も、同じ順序と要素を保つ`hashDistinct`へ`csimp`する。いずれもハッシュ一致だけで同一視せず、元の完全な文字列で決める。

ACKのキー更新は不変の`Plan`としてセッションロックの外で準備する。確定時に元のキー集合と同じなら準備済み結果を使い、並行して変化していれば現在の集合に同じ差分を適用する。`Plan.apply_exact`はどちらでも元の逐次更新との一致を保証する。`prepared_offer_exact`はenabled、turn、epoch、期限を含む元の受理・拒否規則と状態全体の一致を示す。準備は受領や認定の権限を持たない。共有Ref・Mutex・Promise・CASは増やさない。

実行前の型検査は合格した。最初の検査は部分的なライブラリが同名namespaceの他のimportを隠して失敗したため、親のinterfaceを複製し、更新するファイルのリンクを外してからコンパイルする方法へ修正した。続いてnamespaceのopenとrecordの改行を修正し、Productの新定義と証明が通った。失敗は記録し、元のnative実行体ec1064be…は不変と確認した。

実際のACK後に採取した6,554キーのSHAを固定して、初回・履歴あり・倍の入力を各3回測る。旧逐次処理は候補のバッチ`csimp`を呼ばない別の関数として残し、元の定義との一致を証明する。時計の後でIO.Refから入力を取り、結果をIOのsinkへ渡してから時計を読む。純粋なletが時計の外へ移動した数値を採用しない。小さい入力の全組と、並行変更・無効化・期限切れ・別turn/epochもnativeで照合する。

Native検査では5,329組のキー更新と16条件のACKを照合し、順序を含む全結果が一致した。実際のACK経路の準備・確定の接続と、準備・差分適用の355依存に共有状態・待機がないことも検査した。280 native objectは整合し、製品のsource差はPluginHooks、PluginModel、PublicationWire、ContractAuditと追加helperに限られる。
