# 字句推薦にもWorkGraphの関連観測を渡す

隔離候補。本体への採用0、回答モデル呼出し0、有料比較0/18。80人8時間・成長DB・NASの達成を主張しない。

## 確認した原因

同じ固定snapshotと質問を使い、字句postingsの完全順位、元観測の所有者、実フックの候補domainと選択範囲を照合した。以前の未配送3項目は、postingsには存在する一方、どの保存先所有者も上位8件の外にあった。

| 題材 | 欠けた根拠 | 保存先の字句順位（1始まり） |
| --- | --- | --- |
| 1 | 入力言語の追跡状態 | 9位・23位 |
| 1 | 末尾の言語警告 | 9位 |
| 2 | dumpmachineが返すToolChainのtriple | 10位・14位・21位 |

いずれも候補のhydrate前に落ち、選択器へ届いていなかった。シナプスはcompleteと報告されていたが、字句経路は`semanticMatcher.isSome`を条件にWorkGraphの近傍取得と支持観測を無効にしていた。推薦の種8件だけを渡す経路になっていた。

## 修正と検証

[差分](candidate.patch)は二つの条件を`recommendation`へ置き換える。8件は探索の起点として維持し、字句の推薦でも既存のWorkGraphから関連する原観測を候補に加える。新しいcacheや重み、題材固有の規則を追加しない。認定、モデル、質問、配送枠、元snapshot、全hook期限は変更しない。元のSourceSupportの経路証明を保持する。

候補runtime SHAは`444841ae76f60281f6f4acb08963746f526758b434b0f99c75e9c61bc4c79ee5`。native閉包321 objectが整合し、source照合は共通320 moduleで直接Handoffのみの変更と、その実バイトを埋め込む3 moduleの更新に一致した。製品moduleの追加・削除はない。入口のハーネスはsource比較の対象外で、通常のnative閉包検査には含む。

題材1〜3を各2独立native chatで検査した。[実測](evidence.json)は次のとおり。stdoutの保存・flush後のACKも全18件通り、全サービスの正常終了とguardの終了・owned PIDなしを確認した。

## 診断の失敗も残す

診断側は製品と共通320 moduleが同一で、native閉包321 objectも整合した。[診断の差分](diagnostics.patch)は既存のFullHooksから所有者・字句順位・段階記録を採るためのもの。詳細記録付きの通常要求は本文なしで失敗したため、通常対照は詳細を外して題材1から再開した。通常対照は6/6本文一致・32/32だった。詳細な字句診断は6/6本文が以前の字句本文とbyte一致した。

詳細な字句記録では、selection-planがない場合に`Receipt.observeSelection`が`Json.setObjVal!`へnullを渡すpanicも出た。診断の既知の不具合として記録し、修復済みとはしない。候補の配送比較ではこの詳細記録を無効にした。途中停止したビルド、構文修正、診断失敗を含め、終了状態と結果を証跡へ保存する。
