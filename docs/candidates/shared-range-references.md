# グラフ参照を原文範囲の選択へ保持する

隔離候補の記録である。題材2は両周の必要コード検査を通ったが、題材1・3には未配送が残る。
回答モデル・新seedは投入していない。トークン削減率・品質維持・本体採用の証拠にはしない。

## 接続漏れの修正

既存の処理は、現在のグラフに入った過去の解釈から引用先を探し、すでに読み込んだ元観測の
番号付き行へ対応付け、`referencedContextPlan`で原文範囲を追加していた。
新しい`SharedRangeAdapter`は候補を再構築する際、テンプレートの出典枠だけを使い、
その追加範囲を使わず、数値位置だけから候補を作り直していた。

`Family.references`で既存の参照位置を明示的に渡し、原文候補と被覆の両方に保持した。
数値とグラフ参照は同じ元観測への独立したヒントであり、重複位置では最良の順位を一度だけ使う。
同じヒントが両経路に現れても二重に加点しない。
数値位置が空でも、入場済みグラフの参照先は元観測の候補として残ることを試験した。

参照文字列から新しいファイルを開かず、候補は既存の読込済み・グラフ入場済み所有者に限る。
新しいMatch・Union・completed・native controlを作らない。元観測・出典・鮮度の検査と二重予算も維持する。
MiniLM、provider、warm、Worker、SourceEvidence、埋め込みランタイムの保護対象7ファイルは前候補とSHA一致。

## 不採用にした配分案

先に、各所有者の総価値を順位だけで固定し、窓へ正規化して配る案を隔離検証した。
長さ・窓数・分割による総価値の増加を防ぐ保存則、正の整数スケール、丸めなしの計算は証明できた。
しかし題材1の1項目が届く一方で題材2・3に新しい欠落が出た。
2周目題材1は本文自体は期限内に完成したものの、保存済み監査根拠を一つも照合できず、
準備検査が拒否した。残りの2周目題材2・3は未実行である。
この案は撤回し、参照保持候補には含めていない。
[不採用記録](shared-range-mass-rejected.json)と[隔離差分](shared-range-mass-rejected.patch)を保持した。

## 次に直す範囲の混同

providerが計算済みの窓ごとのスコアを診断用の別実行で記録した。現在の返答はそれを
`positions.map Prod.snd`で落とし、観測内の窓の順序だけを渡す。
診断の2回とも本文は参照保持候補とバイト一致した。
題材1の警告コードの先頭文字を含む窓は、focusの保持上位16窓内にあり、スコア0.404389だった。
この一点の包含は必要コード全文の被覆ではなく、類似度も必要性の保証ではない。
記録表での順位は、印字された保持スコア内の順位であり、全窓の正確な順位とは扱わない。
源泉の対応付けにはfocusのWork除去後の窓鍵列を照合し、同じ内容を持つ複数所有者の曖昧性も残した。

さらに、実際の検索窓と、周囲を広げた配送用文脈を混同する反例を確認した。

- 1000文字の元観測と1文字のWork接頭部では、末尾の実検索窓は元観測233文字分だが、`meaningContext?`は512文字を返す。
- Workとの境界で元観測280文字を検索した場合も、配送用範囲は512文字になる。
- Work接頭部が1100文字の場合、窓が元観測180文字に交差していても、窓の中心がWork内なので`none`になる。

これらは文字列の長さを仮定した記号的なkernel検査で確認した。
配送用に周辺を広げること自体は許されるが、新しい被覆選択器はその広がり全体を検索上の価値にしている。
次は検索した正確な元観測範囲と、配送する条件・周辺文脈を分離する。残る全欠落の原因と断定しない。
具体的な長い文字列をkernelで展開した最初の試験は、3GiB監視が3,185,584 KiBで停止した。
記号的証明へ切り替えた最終検査は976,576 KiBで成功した。4GiB上限と監視記録は維持した。

[参照保持の差分](shared-range-references.patch)は`shared-range-marginals.patch`の後に適用する隔離差分。
[検証記録](shared-range-references-review.json)に本文SHA、受領記録、監視、失敗、診断の入力・出力を保存した。
[スコア診断だけの差分](shared-range-score-diagnostic.patch)は参照保持候補と分けている。
この診断変更や不採用の正規化を、本番採用したとは扱わない。
