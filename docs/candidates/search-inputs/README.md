# Reuse captured provider inputs: local gain, capacity gate still fails

Rejected as the next isolated runtime. The five changed product files and the
native dispatcher are [restored to the parent](restoration.json). Public product,
README benchmark and release adoption remain unchanged. Answering-model calls
are zero; paid matched comparisons remain **0/18**. The80-person, eight-hour,
growing-project, NAS and real98% evidence goals remain unproven.

## Missing shared preparation

The existing worker-owned `PreparedReaders` catalogue retained shared synapse
and owner inputs, but not the provider's window, lexical, routing and matrix
inputs. Typed keyed discovery restored all sixteen sources on every invocation.
The isolated [patch](candidate.patch) extends that same bounded catalogue with
checked immutable input images. Borrowing creates fresh counters, traces, page
cursors and owner bitmap state; numerical work can overlap graph discovery.

The captured provider is an in-process value, never a wire-supplied reader.
Its boundary contains complete ordered source scopes, public prepared roots,
model/encoder and owner references. A changed boundary is rejected. Current
questions are not retained, and private usage roots remain operation-specific.
The [Lean laws](laws.txt) describe exact key acceptance, query erasure from that
key and changed-key rejection. They do not prove arbitrary filesystem IO or
all privacy properties. Existing catalogue bounds remain32 images,8MiB charged
metadata and512 handles, with the existing128MiB page pool; no bound is raised.

This does not share one decoded image across the three worker processes, free
a lane during numerical waits, or incrementally reuse individual source images
when a whole captured cut changes. Those remain material limitations for a
growing shared project. Complete Work/e-class certification, parallel append
owners, vector/scoring policy, synapses, selection and delivery limits are
unchanged.

One predeclared parent/candidate burst pair uses the same complete16-source
cut,82 exact original input/output observations and two required original fields.
It uses no new writers and must not be compared as the same workload as the
earlier mixed60/80 result. Each arm independently audits all82 originals.

Both gates fail. A single pair does not prove that this change caused three
additional failures, but no capacity benefit is demonstrated. Local header
reuse is not the next runtime. Do not raise owner/worker counts, deadlines or
budgets, or repeat an unchanged burst as a substitute for identifying the
remaining serialization and CPU/wait costs.

The initial implementation used `Snapshot.forkReader` for provider originals.
That function intentionally retains original counters and traces; the new
borrower-isolation test failed before any model scoring. The corrected consumer
uses the existing `SnapshotImage.borrow` constructor, which allocates fresh
mutable state. The failed test is preserved. Initial private-constructor,
nested-return and metadata-serialization compile errors are also retained;
they are not counted as successful native checks.

## Check diagnostic publication before weakening it

Code inspection showed that even best-effort observations use the durable
publication primitive. A separate Lean[native probe](../../../tools/research/ReceiptPublicationProfile.lean)
measures512 actual publications through all four write/sync/install/durable
boundaries and512 receipt observations. Payloads contain0/256/4096/16384 chars,
with64 unique-name and64 overwrite calls per size. Readback checks exact bytes
and receipt data. Filesystem and receipt product sources are unchanged.

The [local profile](receipt-profile.json) observes publication medians209–243µs,
data-plus-parent sync medians68–75µs and full receipt medians265–317µs. This
unloaded filesystem experiment does not explain the seconds-long loaded query
queue, does not count every overwritten observation in real hooks, and cannot
attribute their loaded cost. No durability guarantee is relaxed. Next measure
actual worker CPU versus waiting time before deciding on a phase/lifetime change.

All controlled native/build guards finish without owned survivors or resource
stops; peak related RSS is2,830,768KiB under the unchanged3,670,016KiB stop/4GiB
ceiling. Ended trial DBs, private caches, raw logs, rejected builds and temporary
source snapshots are[deleted](cleanup.json), not archived. Current originals and
the active parent executable/link inputs remain.
