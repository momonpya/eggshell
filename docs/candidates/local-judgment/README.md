# ローカルの判断モデルによる推薦候補

**隔離した数値推論と実seedの判断入力を検査済み。製品への接続・採用は0。**
既存のMiniLMや、取得済みseedの製品・封印したharnessを変更していない。

固定したllama.cppとQwen3-Reranker-0.6B Q8の[取得記録](native-probe/downloaded.json)を
残した。公式配布元からの取得物のSHA-256とサイズを検査し、展開用の圧縮ファイルは
削除した。[実測記録](native-probe/README.md)では、実seedの19段落の採点は各問
3.081〜3.308秒、数値試験の最大標本RSSは約1.3GiBだった。実フック全体の性能や
16並行、80人、98%配送の達成を意味しない。
[実フックの候補監査](../project-query-receipt/README.md)では、今回の未配送5項目は
すべて候補の和集合に含まれ、最終選択で落ちた。これは予算内の有効な配送packetを
構築できる証明でも、判断モデルが配送を改善したという実証でもない。
今回の未配送5項目中3項目は、段落のみの採点で上位4位までの引用に含まれた。
残る2項目は過去回答の引用にない。引用された主張の順位だけに判断を限定せず、
元の観測も対象にする必要がある。引用がないことを、グラフから到達不能とは扱わない。

## 解く問題と、解けない問題

グラフは、過去の仕事・結果・依存・利用を記録する。現在の質問から、これから
判明するすべての必要条件を予知するものではない。必要な原文へ到達できることと、
限られた配送枠でそれを選べることは別の問題である。98%は、DB内の必要項目を
配送前に凍結した評価で達成する実測目標であり、任意の未来の問いへの保証ではない。

小さな判断モデルを推薦側に置き、現在の質問に対して過去の仕事・主張がどれほど
有用かを採点する仮説を検証する。質問とコード断片だけの類似度で、間接的な
根拠を再び落とす設計にはしない。過去の仕事・主張と、既存の支持辺が示す原文の
関係を入力にする。関連する仕事を選んだ後に、その根拠を単独の低スコアだけで
切り離さない。どの単位を使うかは実selector入力を捕捉して一案を固定し、同じ
問いの失敗を見ながら重み・閾値・予約枠を繰り返し調整しない。

ただし、元の原文が候補になっていない、座標対応が欠ける、探索が未完了、という
不具合は採点モデルでは修復できない。[受理seedの監査](../../practical-runtime/complete-delivery-cohort/README.md)
に残る原文対応の問題を分母から外したり、モデルによる補完で隠したりしない。

## 確認した候補

2026-11-13に公式のmodel cardを確認した。公開ベンチマークやパラメータ数を、
このMacの速度・常駐メモリ・Eggshellの配送率に読み替えない。

| 候補 | 確認できた性質 | この用途での位置付け |
| --- | --- | --- |
| [Qwen3-Reranker-0.6B](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B) | 0.6B、100以上の言語、コード検索、指示に対応、Apache-2.0。公式実装は末尾のyes/no logitsから採点する | 日本語の質問とコード・過去の仕事を結ぶ判断役の第一候補。長い回答生成は不要 |
| [gte-multilingual-reranker-base](https://huggingface.co/Alibaba-NLP/gte-multilingual-reranker-base) | 306M、70以上の言語、encoderによる対の採点、Apache-2.0 | パラメータ数の小さい比較候補。日本語とコードを混ぜた今回の用途での精度・速度は未測定 |

Qwenの公式手順は、yes/noの二つのlogitを正規化する。長い思考文や回答を
生成する必要はない。ただし、出力が短くても入力全体の計算は必要である。
全DBの全原文をモデルへ送る方式は採らない。公開model cardのスコアを
「必要である確率」として較正済みだとも扱わない。

[llama.cppの公式運用例](https://github.com/ggml-org/llama-pages/blob/master/src/docs/serve.md)
にはQwen3のrerank経路がある。数値推論のnative engine候補であり、採用済みではない。
汎用chatとrerankのテンプレート、token、logitの意味を混ぜず、固定した小例で
公式採点の意味と対応することを確認してから性能を測る。GGUFや量子化の違いも
モデル実体のhashに含め、量子化前と同じ判断になると無検査で仮定しない。

## 実装境界

- 保存時に作るものは、原文への不変参照、支持・消費・共引用・利用の関係、
  共有可能な仕事・主張の表現である。質問に依存する判断だけを検索時に行う。
  同じ原文対応・結合・描画の準備を、判断モデルの導入で再び検索へ戻さない。
- vector・字句・シナプスで得る候補と、認定用の完全な探索は分ける。
  最初の比較では候補集合・入力snapshot・配送枠を固定し、入口の欠落と判断の
  欠落を別に数える。正解リストはモデルにも製品にも渡さない。
- 調停、入出力検査、予算、キャッシュ、記録、graphとの接続はLeanで実装する。
  推論だけをnative数値engineへ委ねる候補とし、新しいPython/Rubyの制御器は作らない。
- モデルは共有して常駐させる候補とする。各chatで重みを複製せず、全件を巨大な
  単一要求にもせず、有界な候補群を処理する。要求ごとの期限・取消・メモリ上限を守る。
- 判断のキャッシュ鍵は、正規化した質問、仕事・主張・根拠の内容と依存、
  モデル・tokenizer・指示・実行設定のhashで構成する。無関係な出版で全判断を
  失効させるためにDBのhead全体だけを鍵にしない。project/権限の境界も守る。
- 判断値は推薦にしか使わない。Union、completed、鮮度の証拠を生成しない。
  古い判断のキャッシュが、原依存の鮮度検査を省略する権限を持つこともない。

## 検証の順序

1. 同じ固定製品・受理seedから実selector入力を捕捉し、通常のフック本文との
   バイト一致を確かめる。入場・graph展開・候補化・選択・描画の最初の欠落を追う。
2. 同じ入力で判断モデルだけを隔離評価する。現行方式と同じ枠の下で、初回の
   必要根拠配送率、候補数、モデル入力token、遅延、常駐/ピークメモリを記録する。
   このMacの5GB以内を維持し、速さや適性を測る前に大きなモデルへ広げない。
3. 必要根拠・質問・配送枠を固定したDB増加試験と、調整に使っていない問いで
   評価する。三題材だけで都合のよい閾値を合わせない。
4. 回答モデル比較へ進む場合は、先に候補と計画を固定する。同じ保存snapshot・
   対象ソース・質問・回答モデル・推論設定・harnessで、題材1/2/3の初回と履歴ありを
   それぞれ同数の複数反復で比べる。現行の計画は各cell三反復である。
   回答モデルの入力+出力はcached inputと失敗消費も含め、seed費用は別記する。
   追加したローカル判断の入力+出力も別明細と合算で報告し、無料の処理とは数えない。
5. 本体への採用には、現行より総token削減が改善し、品質とフック期限も守ることを
   要する。配送や証明だけの改善、未測定の設計上の期待では採用しない。

モデルを追加すれば98%になる、という結論はまだない。小型モデルに欠けた判断を
補えるかを、この順序で確かめる。原文対応の不具合を残したまま、別のseedの結果や
配送枠の拡大をこの候補の効果として報告しない。
