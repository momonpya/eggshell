# ローカル判断器の数値実測と、判断単位の監査

**Qwen3-Reranker-0.6B Q8をnative engineから動かした。製品接続・配送改善・採用は0。**
制御・入力準備・監査はLeanで実装し、数値推論だけを固定したllama.cppへ委ねた。
MiniLM、回答モデル、保持製品、受理seedは変更していない。

## 実行条件と実測

[資産](assets.json)はSHA-256とサイズを検査した固定物である。
llama.cpp b12110の[reranking API](https://github.com/ggml-org/llama.cpp/blob/b12110/tools/server/README.md#post-reranking-rerank-documents-according-to-a-given-query)
を、他のサービスと共有しない私有Unix socketで呼んだ。
全順位と元のindexを受け取り、欠落・重複・非有限値・順位順序をLeanで検査した。
APIから得る数値を「根拠が必要である確率」として較正済みとは扱わない。
GGUF Q8と量子化前の公式実装との数値一致を検証したわけでもない。

短い日本語の質問と関連文/無関係文の2候補は、235msと73msで採点できた。
順序を逆にしても同じ関連文を上位にした。初回の起動は5.016秒だった。

次に、受理済みseedの過去回答を、製品の主張区分と同じ二重改行で19の非空段落に分けた。
見出しも除外せず、同じ3問で全段落を採点した。正解の必要項目も配送本文も、
入力準備器と数値モデルへ渡していない。元exportと質問のSHAを検査した。

| 入力 | 題材1 | 題材2 | 題材3 | 数値試験の最大標本RSS |
| --- | ---: | ---: | ---: | ---: |
| 共通の過去作業説明＋段落 | 4.363秒 | 4.231秒 | 4.450秒 | 1,343,632 KiB |
| 段落のみ | 3.088秒 | 3.081秒 | 3.308秒 | 1,339,120 KiB |

後の2起動は355/349msだった。OSやkernelのcacheを消していないので、常にこの起動時間を
得られるとは主張しない。モデルは各run内の3問で再利用した。16並行は未測定である。
合成例のcontextは2,048、実seedは4,096で、同一条件のcold/warm起動比較ではない。
いずれも並行slotは1、CPU threadは2、GPUへのoffloadを指定した。
この数値処理だけの時間を、実フック全体の時間へ読み替えない。

## 共通説明が個別の判断を覆っていた

共通の過去作業説明を全段落へ付けると、題材1の単なる「結論」という見出しにも
0.9987が付いた。説明だけを外した比較では0.00015になった。全段落・全質問・モデル・
数値設定は同じで、段落の打ち切り、閾値、上位kの調整は行っていない。
過去の仕事が関連することを、その中のすべての段落の価値に流用する入力は使わない。
それでも「ソース変更はありません」という段落に高得点が付く例は残り、
このモデルの順位を、そのまま必要性や正しさの判定にはしない。

## 実根拠への引用を別に監査した

[引用監査](grounding.json)は数値推論が終わってから、配送前に凍結済みの必要範囲を参照した。
実フックのcanonicalなファイルID・内容指紋・行番号と、製品の引用parserを使い、
同じclaimの複数引用の和集合も検査する。段落の採点器は正解範囲を見ていない。

未配送5項目のうち、題材1のcache key/HLSL、題材2のHLSLは、段落のみの採点で
4位だった同じ引用段落から覆われる。一方、題材1のinput-language-predicateと
題材3のsyntax-only-compile-cutoffは、過去回答の引用の和集合にも入っていない。
主張の順位付けと引用の優先だけでは、この2項目を拾えない。元の観測の判断も必要である。
この監査は引用の被覆であり、グラフの推移的到達性・予算内のpacket・実配送の証明ではない。

## 消費・検証・削除

[集計](summary.json)は118組・8数値要求を含み、API報告の総tokenは62,863。
数値推論が報告したtokenを別明細とし、回答モデルの削減率には読み替えない。
回答モデル追加0、seed費用4,383,984 tokenは別で、総token改善/品質の比較は0/18のまま。
全118組で省略がないことをserverの記録と照合した。
[実入力](requests.json)は元のUTF-8文字列を保持し、各variantの全順位・応答数値は
JSONとして記録した。

初期の制御器と引用監査のcompile失敗は記録して修正した。失敗時の数値推論は0である。
その場限りの再開・修復コマンドは制御器から除き、失敗の監査記録だけを残した。
全数値guardは終了0・ownedPids空で、5GBの制限を緩めていない。
所有した数値serverは結果を受け取ってからprocess groupを停止したため、server自身の終了値は137。
pipeのjoinと私有socketの削除は確認済みで、正常な自然終了0とは表記しない。

[引用parserのソース照合](grounding-sources.json)は製品と15共通moduleで一致した。
これは引用用componentの照合で、追加コードが製品全体の経路を再現したという意味ではない。
終了した3つの検査用build、二つのsourceコピー、入力展開とrun cacheは[削除した](retired.json)。
圧縮・archiveは作らず、次の検査で使うmodel/数値engine、受理seedと現在の捕捉入力を保持する。
[削除後の保持製品](retained-product-native.json)も347 objectで整合した。

次は同じ候補集合で、引用された根拠と引用のない元観測を分けて判断し、
その後にwork graph/シナプスの依存を保つpacketを作る。既存の元観測経路を
過去回答だけの推薦へ置き換えない。実本文で98%/30秒を測る前に、採用とはしない。
