# 通常フックの段階別診断

未採用。製品を変えず、`remaining-source` の通常runtime `0b0bbca8…`を使った。保存済み80件の結果では受付待ち最大13ms・要求ごとのworker最大80であり、検索の受付を一件ずつ直列化したことを主因にしない。数値応答160/160の完了も本文成功0/80とは区別する。

[実フックの時系列](phases.json)は3問の直列primeと4同時の小診断。全7本文が固定済み本文とバイト一致し、ACKと正常終了を確認した。直列は7,831/6,114/5,798ms、4同時は各4,802〜6,091ms。関連RSS最大2,565,872KiB。段階traceを有効にした計測なので、無観測の速度比較には加えない。4同時のtraceは要求ごとに帰属させていない。

最初の意味検索はtrace開始より前に走る。開始後に見える1〜3msのnominationを意味検索全体の時間にしない。既存のdecoded page cache、共有prepared reader、索引走査を確認し、同じcacheを追加し直さない。

[サービスの記録](profiles.json)で、同一processの原文views・選択・本文取得には直接経路がある一方、原文bindingは自分へのRPCを使っていた。題材2/3では960範囲・775ページ・722葉を走査し、約514KBの元本文に対して921,829bytesのJSONを返していた。走査は581/371ms、通信を含む要求は673/459ms、復号8/6ms、検証2/3msだった。走査そのものを通信費と数えない。

選択は直列558〜750ms、原文viewは初回356ms・後続43/45ms。準備から描画完了の区間は1,230〜1,498msで、その後の区間は302〜345ms。異なる範囲の部品timerを差し引いて原因の費用を算出しない。比較時の実行体の内容ハッシュ確認という仮説は、実際にはOSのstamp/size照合だったため支持されなかった。

次の隔離候補は[typed-bindings](../typed-bindings/README.md)。同じ検証済み射影を直接受け渡し、権限・固定head・保持トークン・返却行の検査を保つ。これだけで80件の未完了が解消するとは主張しない。回答モデル0、総token比較0。現行原DB/cache/model/比較本文を残し、終了した診断の重複本文・session・receipt・traceはarchiveせず削除する。
