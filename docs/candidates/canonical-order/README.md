# 原文の順序を保って比較値を一度だけ作る

resident-sourceを親にした隔離候補。現在の原文mergeでは、出典の比較ごと、ファイルをまたぐ行の比較ごとに同じJSONを作り直していた。既存の行キー単位のmemoは維持し、出典はその行の中で、ファイルは行集合の中で、完全な比較値を一度だけ作る。

Hashはmemoのbucketを選ぶだけであり、完全なOrigin/Fileを照合する。比較値は元のJSONそのもので、数値の行番号、全origin、衝突する本文の拒否、無効な入力の拒否は変えない。モデル、検索順位、認定domain、予算、期限、並行枠、RSS/disk上限も変更しない。

`orderOrigins_exact`、`orderRows_exact`、`storeCached_exact`、`mergePreparedOrder_exact`で任意の入力に対する元の順序・結果との一致を証明した。実装は`csimp`でその等式へ接続する。参照実装は親に既に存在する行キーmemoも含めて独立に残し、候補のコンパイラ置換が参照側に入らないことを検査した。

これは取得後とmaterializeで繰り返す正規化全体を一つにした変更ではない。二度の正規化は残っており、今回除くのはその中の反復した比較値生成である。

[80のguard](capacity-80.json)は3,675,664KiBで既存の3,670,016KiB停止条件に達した。終了後の残存は0。停止時のpublisherは2,143,728KiB、モデルは814,832KiBだった。publisherのRSSを全て生存graphと断定はしない。

[既存記録の監査](stopped-query-stages.json)では、全80件のkeyed到達、48件のprepared-window-focus、20件のdelivery-domainを確認した。これらは配送成功件数ではない。最終結果が保存された21件は356 bytesの未完了通知で、ACK/本文一致はfalseだった。通信が閉じた失敗も記録されている。残る59件は最終結果がないため、0/80という配送率や全件成功へ読み替えない。監査はPIDだけでなく、同じ実行のprimeの観測時刻と結び付け、PID再利用による旧ログ混入を防ぐ。

この80負荷は繰り返さない。次は、取得完了前から保持する問い合わせ用のグラフ/配送表現を調べ、不変の準備を共有し、原文の再正規化を一度にする。文字索引の単体時間が短いことだけで、その保持量まで小さいとは判断しない。全6件の本文と原依存の一致を保ち、上限を緩めず検証する。

終了したsession・重複receipt・停止したendpointは記録後に削除した。80試験だけで166ディレクトリと4つの接続記録を回収した。[退役記録](retired-ended-artifacts.json)では、使い終えた3実行体パス・20重複ログ・3つの試験データディレクトリも削除した。現在の製品/検査器・必要なnative入力、元DB・project cache・モデル・小さな証拠は保持し、archiveは作っていない。元seed・現DBのhead/pages・固定fixtureのハッシュ不変も確認した。
