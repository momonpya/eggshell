## 汎用全体探索は、最適性を確認できなかった

[shared_coverage_mip.py](../../tools/research/shared_coverage_mip.py)は、nativeの完全な候補集合を
共有費用・二重予算・重複しない被覆の混合整数計画へ変換する研究用ツール。
各候補が必要な費用ノードをすべて払い、選ばれた候補だけが手掛かりを覆う。
返った候補集合の費用と価値は、元の整数を使って別途計算し直す。
HiGHSは実験の私有ディレクトリだけに置き、本体の依存へ加えていない。
[公式Python例](https://github.com/ERGO-Code/HiGHS/blob/master/examples/call_highs_from_python.py)に従ったAPIを使う。

同じ候補・同じ費用・同じ価値に対する各45秒の探索では、題材1/2周目題材3の最良解は
元の貪欲解から改善せず、数値上界との隔たりも27.36%/49.97%残った。
最適解を得たとは言えず、この結果から元の評価関数と最適化器のどちらだけが原因かは確定しない。
必要コードを強制する別の診断も45秒で打切りとなった。これは正解指定の機会費用検査で、
その条件を通常の最適化や実行時の選択へ渡していない。
浮動小数点の数値上界と係数変換の誤差も記録し、形式的な最適性証明とは区別する。

小さな6条件では独立した全列挙と最適値が一致した。共有費用、bytes制限、巨大な整数価値、
複数候補の和集合による必要範囲、複製、分数緩和や未配送の手掛かりへの誤った加点を検査した。
最初の出力親ディレクトリの不足と、正解指定診断の「どの所有者でも必要コードを出せる」という
誤った仮定による準備失敗は保持し、修正後の成功と分けている。

## 同一incidenceの集約

[incidence_quotient.py](../../tools/research/incidence_quotient.py)は、同じ候補群に要求される
費用ノードを一つへまとめ、同じ候補群に覆われる手掛かりの価値を足し合わせる。
任意の候補集合Sについて、同じincidence群の要素はすべて同時に有効/無効になるので、
群の和へ置換しても費用と被覆の価値は変わらない。到達不能な要素は寄与0である。

| 入力 | 費用ノード | 手掛かり |
| --- | ---: | ---: |
| 題材1 | 2,633 → 1,563 | 2,673 → 1,594 |
| 2周目題材3 | 4,491 → 2,779 | 4,836 → 2,764 |

小さな全4部分集合と、実入力の各66集合で費用・価値・実行可能性の一致を検査した。
構成上の恒等式と実装検査であり、新しいLean証明や、集約後のMIPの最適解・高速化を実証したものではない。

## 引用と原文の融合案を実入力で試した

入力adapterの先へ、次の一つの仮説を凍結して接続した。

- 同じpath・file fingerprint・行・実際の本文hashを持つ保存済み原文は、一度だけ価値を持つ。
  対応は既存DBの番号付き観測とliteral readの情報から取り、外のソースファイルを読まない。
- 元のfocus手掛かりと引用依存の手掛かりを二つの信号集合に分ける。focus側には既存処理で
  組み合わされた参照位置もあるため、これを純粋なdense検索だけの集合とは呼ばない。
- 行への信号量を上限付きで分配し、同じ行に対する同じ信号の複製はmaxでまとめる。
  引用全体が保存されていない場合も、保存された行だけへ比例した値を渡す。
- 元の局所前提を持つ候補だけが信号を受け取り、元の共有費用・予算・候補は維持する。
  番号付き原文に対応できないデータは元の座標によるopaqueな手掛かりとして残す。

題材1で5,265行、2周目題材3で9,148行を対応付け、指紋と行が同じなのに本文が異なる衝突は0だった。
この対応が可能な所有者は15/36件で、全形式の観測の正規化を完了したとは扱わない。

[signal_coverage.py](../../tools/research/signal_coverage.py)は、各信号集合の総量で正規化した被覆を
max-minで比較する。上限付きの被覆を費用あたりに選ぶ探索と、候補全体の最良単独案、
元の選択を比較し、宣言した代理目的ではseedを下回らない。
提案1,048,576回・閾値探索8回を選択前に固定した。共有費用での閾値探索はヒューリスティックで、
目標に届かなかったことを実行不可能の証明や最適値の上界とは呼ばない。

4試験が成功。247通りの二重予算と5種類の作業量、独立全列挙との比較、seedからの非悪化、
入力順、同じ候補の複製、片方の信号がない場合、共有前提を検査した。
実入力の探索は3.18/3.85秒、必要メモリは約75MiBだった。これは実hookの時間や本番十分性の証明ではない。

| 入力 | focus代理被覆 | 引用代理被覆 | 必要コードの未選択 |
| --- | ---: | ---: | ---: |
| 題材1・元の選択 | 20.61% | 23.93% | 1項目 |
| 題材1・融合試作 | 26.24% | 31.77% | 2項目 |
| 2周目題材3・元の選択 | 9.38% | 12.91% | 5項目 |
| 2周目題材3・融合試作 | 15.78% | 18.63% | 5項目 |

表は代理関数の値で、必要事実の再現率やモデルのトークン削減率ではない。
選択後の別処理だけが既知の必要コードを照合した。入力生成器と選択器は正解リストを読まない。
さらに、同じ評価・探索のまま未選択グラフの枠予約を所有者単独の追加枠へ変える費用診断も行ったが、
未選択数は2/5のままだった。この単独枠の費用モデルを任意の実packetの上界として証明したわけでもない。
新しい実packetの生成、全6段階のnative再実行、回答モデルの投入へは進めていない。

必要行を一部配送して末尾だけ切った現象ではなく、これらの範囲はまとまって未選択だった。
手掛かりが元候補へ届き、安価な実行可能な必要コード集合があることは既に確認できているが、
全体の代理被覆を増やすことだけでは、現在質問に必要なコードを選ぶ条件にならない。
この同じ試作を、閾値や係数を調整して再挑戦しない。
次は現在質問と引用付きの主張の対応を直接測り、質問の論点と、チャネル全体の被覆を区別する。
同じMiniLMを保ち、追加の回答モデルを使う前に、保存済みの主張から原文へ至る経路を調べる。
