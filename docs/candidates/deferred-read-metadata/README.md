# 来歴メタデータの展開を選択後へ移す

隔離候補、未採用。現行byte-pagesの80並行で、数値160/160完了後、原文準備から選択までにLean側のRSSが増えたため調べた。[差分](candidate.patch)は、検査済みの原文descriptorから全Readを展開して保持する時点を、選択前から選択後へ移す。重み、候補、予算、原文、鮮度確認、e-class、認定、プロンプトは変更していない。新しいcache・queue・mutex・worker制限も加えない。

原文descriptorがaddressableかどうかだけを先に検査し、descriptorとその証明を持つ。最終の配送確認で、従来と同じ順序でReadを展開する。単に展開する時点を移すだけで、最終的に作る全Readの数は減らしていない。

## 証明と実行体

Leanで、任意のdescriptorについて「先行検査の成功」と「従来の展開の成功」が同値であること、展開結果そのものの一致、追加したdescriptorの順序を保つことを証明した。[公理](axioms.txt)はpropext / Quot.soundのみ。新たなsorry、native_decide、Z3や無証明の実装差替えはない。この証明は純粋な展開の一致であり、RSSの減少や80人の容量を証明するものではない。

通常のnative buildによる実行体・リンク閉包・全sourceを[照合](validation.json)した。直接変更はHandoff / SynapseTransportの2件、追加は証明用module1件だけで、削除moduleは0だった。検査器も閉包と全製品coreが一致する。検査器では実際のTransport.buildが新しい先行検査を呼び、prepareDeliveryが遅延展開を呼ぶことも宣言から確認した。

最初の構築で入口にMainを指定し、比較元のReplayReadinessChecksが持つ共有サービス等の部品を落とした。厳格なsource照合が実行前に拒否し、その実行体は一度も起動していない。同じ入口を指定した新しいsource/buildで作り直し、通常builderによるcache入力の照合を通した。入口を誤った生成物は削除した。検査器のroot宣言監査で`open Lean`が欠けたコンパイル失敗も、成功と混ぜず検証記録の`rejected-entry` / `harness-compile-repair`に残した。

検査器のcapacity本体は同じまま、既存のprobe/cellsと同じ実行体から呼べるように入口だけを[追加](harness.patch)した。原文検査や30秒・本文・ACKの条件は変えていない。

[同じsnapshot・3題材・各2独立チャット](delivery.json)で、全6本文が親正本とbyte一致し、凍結した必要原文は32/32だった。

関連RSS最大は2,884,480KiB。guardはexit0、残存processは0。`packetVerified=true`はpacketの存在を示す欄であり、全partが検証済みという意味にはしない。全6件に未検証part番号8があり、親の40要求でも全て同じ番号8だった。今回の差ではないが、全partの認定完了とも扱わない。

最初の開始試行は、前の80並行の保護停止で残ったpublisher endpointにより拒否された。対象PIDが実際に死んでいることを確認して接続記録だけを回復し、新しい結果先で実行した。生きた所有者の記録やDB原典は削除していない。検証記録の`recovered-study-endpoints`に確認結果を残した。

## 4/16並行と採否

[小負荷と段階の記録](capacity.json)は4件・16件とも、意味検索、シナプス、親正本と一致する本文、ACKが全件完了した。必要原文104/104、全波の完了は4,020 / 10,392msだった。関連RSS最大は4,175,312KiB（約4.275GB）である。入れ子の経過時間は足し合わせない。

親byte-pagesの同じ4/16試験の最大RSSは4,167,680KiBだった。異なる時点の単発試行なので因果的な増減を主張しないが、減少は確認できなかった。展開を遅らせても全量を最終段階で作るため、この案だけを80並行の容量対策にはしない。新たな80試行や回答モデルの投入は行っていない。

次は、原文の処理中に保持される検査用構造を調べる。具体的にはJsonScalars.AddressがJSON木・全文字配列・scalarを実行時に持ち、LocatedOutputの消費側が主にpathを読む箇所がある。参照がRSSの主因という結論はまだ出していない。必要なpathと、その検査済み性を表すPropへ分けられるかを確認する。単にcacheを追加したり、同じ遅延案を再試行したりしない。

これは中断した未受理seedでのモデルなし性能・配送検査であり、受理済みseedからの題材1/2/3の両周や、総トークン・品質の比較ではない。回答モデル0、有料比較0/18、採用0。80人8時間、成長する複数DB/NAS、98%の全体目標は未達である。

終了済みの実行体、source/build、prefix、試験DB台帳・重複本文・生ログ7,729ファイル・776,677,698論理byteは[削除](cleanup.json)した。これは先に削除した入口誤指定の生成物とは別である。archiveは作らず、原DB・現行byte-pagesの実行体/検査器・project cache/model・正本本文を保持した。23件のSHAは前後で一致し、削除後の製品309 object・検査器331 objectも整合した。未採用のコードは差分と証明記録に限り、本体や通常のresearch moduleには残さない。小さな証拠は検証・配送・並行負荷・削除の4記録にまとめ、元の記録のdigestも残した。
