# 出版済みの引用信号が0になる原因

受理済みseedの同じpublicationをLean nativeで読み取り、元DB・索引を変更せずに確認した。

| 公開済みの記録 | 件数 |
| --- | ---: |
| ファイル行の読み取り | 9,197 |
| 原出力の読み取り | 13,862 |
| 消費の辺 | 2,577 |
| 文字列一致による支持 | 4,260 |
| 引用による支持 | 0 |
| 回答/主張の共引用 | 0 / 0 |

過去回答には、公開済みファイルと対応する引用44件があり、すべて既存のファイル行記録に重なった。WorkGraphの子をたどる一括経路と索引経路は59 Workで一致し、Workごとのpostingsも全Factの独立走査と一致した。必要な候補は到達している。

一方、同じ回答・同じ原文から製品の引用作成処理を再生すると、`citation is not covered by its recorded read`で失敗した。出版処理はこの失敗を受けると、その回答の引用グラフを採用せず、別処理の文字列一致の支持だけを残していた。単に読取用exportで共引用が失われたのではない。

原因となる境界は、ファイル行と元出力の文字範囲の対応である。同じ呼出し・owner・Workの出力に同じファイル行が複数回現れると、別の読取区間に属する行まで集計できてしまう。作った文字範囲が元のReadを越え、既存の安全検査が拒否する。

元Readの文字区間に収まる行だけを用いて同じ入力を再生すると、引用支持3,189件と共引用4,368件を生成できた。範囲・owner・fingerprintの検査を弱めた結果ではない。現行publicationは変更していない。

この再生は製品修正の実フック試験ではない。検査用wrapperの全組合わせで配列を繰り返しfilterしたため65.548秒かかっており、検索・配送時間として扱わない。製品候補は従来の交差検査後の行filterに範囲条件を足すだけとし、このwrapperを検索へ入れない。

[最初の計数](report.json)、[Work経路と元処理の再生](route.json)、[元出力区間に限定した再生](scoped.json)を保存した。[隔離した製品候補](../citation-read-scope/)で実フックと総tokenを検証するまで採用しない。
