# 無関係な出版による原文構造cacheの再読込

モデルを呼ばない診断。本体も隔離候補runtimeも変更していない。比較対象は空引用ガード候補 `1e3c3107…`。原文の構造cacheがindexの全Headを鍵にするため、無関係な出版でも変更のない所有者を再解析することを、実際のnative保存で確認した。

[制御コード](../../../tools/research/GeometryPublicationChecks.lean)は16所有者の一般JSON/多言語の原出力を新しい小DBへ保存する。最初の取得、同じheadの再取得、別所有者を一件ずつ8回出版した後の取得を、同じ一つのcacheで実行する。最後に元の所有者を変更し、変更後の値と古いpinの両方を確認する。コマンドの構文やgitを前提にしない。これは索引DBと構造cacheの部品検査であり、実際のPost/Stopからの保存全体、80人の混合負荷、シナプスの準備債務の測定ではない。

[結果](result.json)は次のとおり。

| 範囲 | 所有者の再解析 | 投影時間 |
| --- | ---: | ---: |
| 初回16件 | 16 | 6ms |
| 同じheadの16件 | 0 | 1ms |
| 無関係な出版の後、各16件×8回 | 各16、計128 | 各6〜8ms |

再解析した16件の全geometryは、毎回初回と完全に一致した。cache内のentryは16から144へ、計上bytesは223,944から2,015,496へ増えた。変更された原文は古い値を再利用せず、古いpinは古い原文を保った。従って重複は確認できたが、これだけで秒単位のフック遅延の主因と結論しない。新しい永続形式やcacheをこの小試験だけで追加せず、元のHead検査も取り除かない。

[native閉包](native-closure.json)は46 objectが整合し、[製品と共通する45 module](native-sources.json)のsource/include bytesは一致した。entryのsource witnessも制御コードと照合した。[実行記録](resources.json)では試験の関連RSS最大87,216KiB、正常終了・残存0。5,000,000,000 bytesの総上限と4,358,524KiBの保護停止を維持した。初回の補助entryは文字列構文とnamespace指定の誤りでcompileに失敗し、訂正後にnative buildと試験を実行した。失敗を製品の配送試験に数えない。

次は、既存の4/16並行profileと過去の選択単体の再生を踏まえ、実際にサービスで共有される不変viewと、保存・差分準備・要求固有の処理の境界を追う。選択器単体の並行性は既に測られているので、今回の小さな再読込だけを直して80件を再試行しない。

終了した小DB、補助実行体、source/buildコピー、一時controller、生ログは[削除](cleanup.json)し、archiveを作らない。原典、現在のruntime/監査器、準備済みproject cache、モデル、比較本文は保持する。回答モデル0、有料比較0/18、採用した製品変更0。80人8時間・成長する複数DB/NAS・98%必要原文・総token・品質の全体目標は未達。
