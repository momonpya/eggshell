# 完全な条件分岐を追加するだけでは配送は改善しなかった

同じ受理済みsnapshotと、[引用修正候補の実選択入力](../citation-read-scope/trace/captured-inputs.json)だけを使ったnative Leanの診断。製品変更、新DB、warm、実フック、回答モデルの呼出しは0。本体へ採用していない。

既存のScopeAlternativesは主に括弧と波括弧の形から範囲を作る。波括弧なしの `if … else` も、条件と両分岐を一つにした原文範囲を選べるか確かめた。元offerの順序・費用・cue重み・固定費・二つの上限は保持し、完全に観測された範囲を任意の追加offerにする。推測したcall→定義を必須依存には戻さない。[実行前の停止条件](plan.json)。

## 部品と境界

Leanの有限なstatement recognizerで、括弧、ブロック、文末、入れ子、elseの対応を扱う。元のファイル/指紋の連続行だけから作り、読取の途切れと指紋の変化で解析を分ける。前処理を含む範囲や未対応のraw stringがあるrunは追加しない。これは限定された構文上の候補であり、C++の意味解析器ではない。

Unicode、braced/unbraced、dangling else、constexpr、複数行条件、コメント/文字列、loop、途切れた文、preprocessor、raw string、空入力に加え、読取gapと別指紋の13対照が通った。[結果](fixtures.json)。範囲が同じファイルの取得済み原文を使うことをkernelで確認したが、必要性や言語全体の正しさの証明とはしない。[証明の公理](proofs.txt)は標準公理のみ。

元の選択器は3題材とも実記録の選択ID列を完全再現した。元ファイルの全行と費用を実入力に照合し、共通native sourceは変更していない。これは部品のnative closureであり、候補製品全体をビルド・実フック検証したという主張ではない。[入力・source・native・失敗したcompiler段階も含む検査](verification.json)。

## 一度の比較で停止

各題材の実費用nodeに対応する同じ7,097行から537範囲を認識し、348 offerを追加したが、どの題材でも新offerは選ばれなかった。元の費用/重み/上限を調整して再試行していない。

| 題材 | 実親本文の必須原文 | 候補が選んだ原文の利用可能性 | 元選択/候補選択（ms） |
| --- | --- | --- | --- |
| 1 | 4/5 | 4/5 | 386 / 448 |
| 2 | 7/7 | 7/7 | 392 / 442 |
| 3 | 4/6 | 4/6 | 401 / 448 |

新しい構文準備は40〜41ms、3題材と原文の再構成を含む最初のnative診断全体は5,498ms、RSS標本最大243,456KiB。いずれも実フックの速度とは扱わない。実親本文の18ラベルに対する推定器の一致を先に確認した[独立した監査](assessment.json)でも15/18のままである。新しい実配送が15/18だった、回答の二周が終わった、総tokenが改善した、とは報告しない。

観測項目だけを加えた後も、全3題材の選択node・費用・候補数は元の診断と完全一致した。記録の追加を別の選択方式として数えない。

## 残る箇所がどこで落ちるか

正解座標は候補の実行後に独立診断だけへ使った。[対応と限界](context-signals.json)。

- Compileの境界は342〜386、352〜386、360〜386行の完全な候補になり、正の追加gainもあるが、最終選択後にはそれぞれ2,002/1,876/1,352文字を追加できない。
- ConstructJobは条件と両分岐を含む6381〜6385行の5行が認識され、有効なofferになった。最終選択に加える費用は117文字、gainも正であるが、先に別の範囲で枠が埋まっていた。原文の欠落や認識失敗を原因にしない。
- input-language-predicateは関数定義で、この条件分岐の候補を増やす方式の対象ではない。元の必要項目から外したり、既出の推測call closureへ戻したりしない。

全ての必要項目を含む最適解が存在することや、117文字の空きを作れば他の必要項目を保てることを、この診断だけで証明していない。確認できたのは、元の目的関数のまま完全な条件範囲を追加しても、この3題材の選択は改善しないということ。予算や係数の調整では解決としない。

停止条件どおり製品接続を止めた。使わない二つの研究moduleと診断用source/build/cacheも削除し、実行したLean sourceはSHA・proof・native入力と一緒にverification.jsonへ記録した。[削除と保持製品の整合](cleanup.json)。圧縮archiveは作らない。保存・座標・構文範囲の追加を、現在の質問に必要な根拠を選べたことと混同しない。

履歴の自律確認へ戻る前に、[現行の判断器制御](../../../tools/research/HistoryNavigator.lean)の二点を調べる。toolで終了する契約にtool_choice=autoを使っていることと、前の原文ページを次の判断から除き、読了一覧には先頭80文字だけを残していること。モデルが原文を読めることと、その内容を保持して判断できることは別である。この制御が以前の失敗の原因だったかは未検証であり、失敗記録を成功へ読み替えない。同じLLVM3問へのmodel/promptの再調整は再開しない。
