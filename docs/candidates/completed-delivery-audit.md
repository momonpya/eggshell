# 保存済みモデル実行の認定配送を全フックで数える

**このLLVM課題群では認定配送は観測されなかった。推薦配送の検査と、認定の効果の実証を分ける。**
終了済み `query-anchor-tokens-20261022` の候補13実行・比較13実行を監査した。
全6段階は各2反復、段階1のみ3反復。現在の隔離候補を使った新しいモデル実行ではない。

| 対象 | 検索受領記録 | 件数が明記 | completed合計 | Handoffなしで件数null |
| --- | ---: | ---: | ---: | ---: |
| 初回 UserPromptSubmit | 26 | 26 | 0 | 0 |
| ターン途中 Pre/PostToolUse | 294 | 96 | 0 | 198 |
| 合計 | 320 | 122 | 0 | 198 |

実モデルのthread/session IDと `request.json` を一致させ、準備用セッションを除外した。
アプリ側の全hook通知数とも照合した。対象の初回・ツール前後に検索受領記録の欠落はない。
配信済みpacketのSHAと、各receiptの出版完了も確認した。`dispatch.completed=true` は
プロセス完了なので、認定件数に数えていない。

`search.completed` は配送の重複除去後の `handoff.map completed` である。
null 198件は `empty` 124+9件と `reconciled-empty` 94件で、Handoffが残らない記録。
これを内部照合の「認定候補も0件」とは読み替えない。実際に認定を配送した記録はなく、
equalityOriginも全てnullだった。初回の自然言語質問が同じだけではExactの権限を作れない。

従って、この既存データから「推薦と認定の分離がトークンや誤再利用に効いた」とは主張しない。
予約済みの未観測holdoutには、必要な同一読み取りが後の作業で繰り返される課題と、
指紋・呼出し変更の対照を、正解凍結前に追加した。Exact・鮮度・権限を緩めず、
実際に認定可能な操作がない場合はその未評価境界を報告する。
ビルド/テストは入力・環境の十分な鮮度モデルがある場合に限る。

## 価値の提案について既存の失敗と区別する

文字数を外して「完全な局所前提一組につき一票」にした再生は既にある。
`shared-range-closed-demand-probe-20261022/probe.py` は、元のRRF順位を残し、
文字数倍率を除き、同じ閉包を重複加点しないよう変更している。
段階1は4必要項目すべて、段階6は7項目すべてが未配送だった。
固定費も条件化した別案では段階1は4件、段階6は6件が欠けた。モデル・実フックは未実行。
「費用だけの試験」ではないため、この同じ式は繰り返さない。
これは全ての文字数非依存方式を否定する結果でもない。

今回の別候補は、位置や局所前提一組の票ではなく、元観測に現れる語・識別子を
候補間で共有して反復の価値を飽和させる。実配送結果を別記録に残し、代理目的の改善を成功としない。

MiniLMの質問→引用付き主張照合で必要な主張が49件中39/44/45位だった結果も保持する。
これは調べた追い質問における上位k選択の否定的証拠であり、意味検索一般の不可能性や
依存構造を加えた方式の優位性の証明とはしない。

再現スクリプトは `tools/research/completed_delivery_audit.py`、実行別・段階別件数と
元receipt・packetの証拠は [completed-delivery-audit.json](completed-delivery-audit.json)。
新規モデル呼出し・seed取得・本番実装/README実績の変更は0。
