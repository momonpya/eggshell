# 実LLVM原典での配送失敗と内部応答の測定

2026-11-07。回答モデル0、有料比較0/18、本体未採用。実際の配送失敗を記録しており、部品試験の成功で置き換えない。

親 `read-runtime` の検索期限Mutexを除いた `search-read`（SHA `54f6020654cfe694a7d0a642b02436d37759c269851b7322e4c4a45d55119556`）を、保存済み実原典から複製した同一snapshot、同じソース・質問・500,000文字の既存実験枠で監査した。凍結したDB内の必要項目は題材1/2/3で4/7/5。原典と独立参照・native moduleの整合はfrozen/closureの各記録に残した。新seedやモデルは作っていない。

準備では1,977窓を62batchで埋め、missing/invalidは0。再warmのrequested/batchesは0だった。最初の新チャットの題材1は7,432msで返ったが、本文は356文字の未完了通知のみ、必要原文の配送は0/4だった。以後の5セルはfail-fastで実行していない。フック時間内という事実を配送成功とは扱わない。

別の診断専用実行体（SHA `bdd8b8ce99f2c16e50a578551f67ca5270b8501f1dcd0ac0b04f768296814fbc`）で、保存済みの同じ準備済みDBを使い、新しいチャットで返送直前のサイズを計った。native実行体と検査器の完全な製品sourceを一致させた。古い検査器の流用はPublicationWireの不一致で実行前に拒否し、欠けた研究用importによるbuild失敗も保持した。

測定値はpayload **13,420,015bytes**、予約分込み **13,421,039bytes**、通信上限 **8,388,608bytes**。意味検索・シナプス探索は完走し、内部本文は約49万文字あったが、OperationPoolの予約が返送を拒否していた。診断フックは9,091ms、実配送0/4だった。原文来歴を含むpacketが約12.34MBで、同じファイル・呼出し・所有者の情報を各行に繰り返している。順位の再調整やフック期限の延長を原因対策にしない。

この失敗の時点では内部本文の必要原文を未監査だった。後続の [compact-reply](../compact-reply/README.md) で独立監査し、4/4が含まれることを確認した。内部に本文があったことと、ユーザー側への配送を区別する。一部の未検証partが応答全体を拒否した、という初期説明は誤りで、サイズ超過が直接の返送拒否理由だった。

失敗・測定・native sourceの照合・guardは本ディレクトリに保存した。実際の13.42MBの応答はprivateな現行再現資料として、そのSHAだけを `failure.json` に記録する。診断の生本文保存は明示した研究用フラグだけで有効で、通常の共有DBへの保存経路には加えない。

後続のcompact-replyは、本文・順序・原依存・ACK/reconciliationを変えずに共有表で送るLean実装を行い、同じ凍結原典の全6件で必要原文の実配送を確認した。8MiBの上限は拡大していない。この小さい配送検査を、80人・8時間・増大DB・総token改善の達成とは扱わない。
