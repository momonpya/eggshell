# 検索窓の順位保持と差分計算

候補は隔離したままである。必要な元コードの配送条件を満たしておらず、モデル投入・本体採用・新しいトークン削減率の主張はしていない。

## 新しい範囲選択で直したこと

連続する数値検索窓を表示用に結合した後、結合範囲のリスト位置を窓の順位に使っていた。
結合された広い範囲へ強い順位を付けないよう、元の窓番号と順位を保持し、各位置では重なる窓の最良の順位を一度だけ使う。
未検索の周辺文脈には被覆の重みを与えない。重複・隣接・順位の飛びを含む例を検査した。
MiniLM・provider・検索順位の生成コードは変更していない。

この修正単独では、題材1〜3の必要コードの漏れは解消しなかった。
2周目題材1の2チャットは約28.8秒で未完了となり、ACKがなく準備処理が停止した。
残りの2周目題材2・3は未実行で、全6段階成功とは扱わない。

選択器は各候補を比較するたびに、すでに選んだ全候補の費用と被覆を計算し直していた。
選択済みノードと手掛かりをハッシュ表で一度だけ用意し、新候補の追加分だけを計算するようにした。
ノード・被覆に重複がある入力も含め、追加費用・価値・提案・同点時の選択が元の関数と全入力で等しいことを証明した。
`best_cached_compiled`でコンパイル経路に接続し、生成されたCもこの経路を呼ぶことを確認した。
この修正は選択基準を変えない。

固定した実際の候補ドメインをLean実行環境で再生すると、選択65候補と費用は一致し、
選択計算は193,929 msから3,606 msになった。この比率をnativeフック全体の速度とは扱わない。

## 残っている問題

題材1の事前に定めた4項目を、元観測の完全なコード行と照合した。
4項目それぞれに必要なコードを全て含む完全な候補が存在したが、選択後には全て落ちていた。
コード名や正解範囲はこの監査だけで使い、実行時の選択へ渡していない。
他の段階の欠落も全て同じ原因だと断定しない。

現在の配分は、窓が覆った文字数へ所有者順位と窓順位の重みを掛けている。
この宣言済み被覆を速く正確に最大化しても、質問に必要な原文の配送を保証しない。
次は既存の数値評価とグラフ由来に対応する追加価値の定義を見直す。
長さ・分割・重複だけで価値が増える問題を、汎用の例と実配送で検査する。
同じ所有者枠の優先順を切り替えたり、題材固有の条件を加えたりしない。

[差分](shared-range-marginals.patch)は`shared-range-current.patch`、`shared-range-closures.patch`の後に適用する隔離差分。
[検査記録](shared-range-marginals-review.json)にはソース・実行バイナリ・本文SHA、失敗した検査、期限切れ、
数値受領記録とメモリ監視を保存した。モデル呼出し・新seed取得は0。
全6段階で必要履歴が届くまでLuna比較へ進まない。以後の候補比較は題材1から始め、既存fresh対照を使う。
