# 原文の接続を使う拡散：固定試験で改善せず終了

隔離した推薦の試験。本体・登録フック・MiniLM・保存DB・認定は変更していない。追加のモデルやseedは呼ばず、同じ受理済みsnapshot・題材1/2/3・引用修正候補の実選択入力を使った。前回の全原文rerankerとは異なり、既存の原文payloadの接続と既存の質問信号だけを使う。

グラフ上の関連を伝える方法として、[HippoRAGの一次論文](https://arxiv.org/html/2405.14831v1#S3.SS4)のPersonalized PageRankとrestart 0.5を参考にした。論文のLLMによるグラフ生成や性能値は移植していない。この試験を新しい研究上の発明とも呼ばない。

## 実行前に固定した方法

入力は原文単位のofferと、既存の3辺から投影された束である。owner/fileの出典frameは接続から外す。同じ原文ID集合は一つのhyperedgeへまとめ、別aliasの重複で票を増やさない。原文→接続→原文と進む際に接続数と構成要素数で割り、広い束だけが際限なく値を増やすことを避ける。質問の起点は既存のbase cueに限り、同じcueの値をそれが指す原文へ分配する。新しい質問・語・モデル・正解は入力しない。

restart 0.5、32反復、結果の整数化は2^50倍で固定した。拡散後の原文ごとの値だけを推薦の目的にし、元の証明済み選択器へ渡す。すべての元offerの前提、物理費用、固定費、120,000文字/480,000 bytesの上限を保持する。結果を見て係数、範囲、Kや予算を変更しない。全3問の選択を保存してから、独立した既存の原文照合器が凍結正解を開く。

元の共有Fact台帳をそのまま使うPPRではなく、選択入力へ既に投影された原文集合の接続を使う。消費の向き・辺の種別・元Factの出所を復元したという主張ではない。scopeは元の入場済み候補のままで、Union・Match・completedを作らない。

Leanで、既存の証明済み逆引き索引を再利用した。endpointの範囲内性、逆引きの完全性、元の費用/上限/前提の保持を[kernelで検査](proofs.txt)した。新しいaxiom、sorry、native_decideはない。浮動小数演算、32反復の定常解に対する誤差、関連性や98%を証明したものではない。

独立した小さいfixtureでは、2段先への伝播、接続のない原文の値0、重複aliasの除去、孤立した起点の保持、空/不正な起点や範囲外IDの拒否、元予算と前提の保持を確認した。浮動小数の全結果の有限性・非負性と合計massの誤差も実行時に検査する。全原文×全接続を走査する逆引き構築は使わない。

## 結果：15/18のまま

| 題材 | 親候補の実配送を再現した選択 | 拡散した選択に含まれる原文 |
| --- | --- | --- |
| 1 | 4/5 | 4/5 |
| 2 | 7/7 | 7/7 |
| 3 | 4/6 | 4/6 |

全18ラベルで、原文照合器による親の選択の推定は実本文と一致した。拡散後は選ぶofferが全3問で変わったが、残るinput-language-predicate、syntax-only-compile-cutoff、frontend-job-constructionは同じだった。[独立照合](assessment.json)、[選択が実際に変わったこと](choice-comparison.json)。候補の列は実フック配送ではない。現行の実配送13/18、親候補15/18と区別する。

各問10,732 cost atom、重複を除いた接続1,927、接続内の原文参照17,844。接続の準備11ms、拡散80〜82ms、元の選択再生406〜411ms、候補の選択329〜340msだった。入力JSONの読込み・復号、起点の構築、検査・出力等を含む全3問のnative guardは13,411msであり、80msを全フック時間へ読み替えない。原文照合のguardは6,678ms。データと[各段階の記録](replay.json)を残した。

事前の全問98%条件に達しなかったので、不採用として停止した。再学習・係数変更・新しいモデル・実フック・回答モデルへの追加実行は行わない。この結果は「接続をこの方法で拡散しただけでは、今回の欠落が直らなかった」という範囲である。完全なFactグラフ、3辺一般、未知の課題での不可能性は導かない。初回/履歴ありの回答試験や総token削減率の代用にもならない。追加のモデル呼出・新seed費用は0。

全guard終了・所有processなし、原典と保持製品2つのSHA/native closureを確認した。native再生の関連RSS標本最大225,360KiB、独立照合239,552KiB。compile失敗も[検証記録](verification.json)に残した。不要になった実験source/build等616項目・129,459,641論理bytesと、新規候補module2個を[削除](cleanup.json)した。archiveは作らず、小さい結果と[実際に実行したLeanソース](executed-sources.json)だけを保存した。

次の候補にこの拡散の係数調整を持ち込まない。現在の`PreparedSourceCosts.Bound.requirements`は意図どおり空であり、関数scopeの任意offerは関数間の参照辺ではない。削除済みの推測したcall→definitionの強制を戻すことと、記録から検証できる参照が既存の推薦接続へ渡っているかを調べることは区別する。次はその対応を独立した反証課題で確認し、曖昧な名前一致を必要依存や認定へ昇格させない。原文にない意味や隠れたモデルの推論は補わない。
