# 独立した射影とシナプス読み込みを重ねる

隔離候補。回答モデル0、採用0。比較元はcanonical decoder候補
`7cc1432d2d3931a26d60e3e614807545e3f6b522737838bdabc1b1c626e657ab`。
選択器だけをpoolへ移した旧候補の再試行ではない。

共有batchを借りた後、focusの純粋な射影と過去回答の引用対応は、
シナプス索引を読むIOと独立している。元の純粋式をthunkとして
Leanの通常のCPU poolへ渡し、要求のactorは元のtransport IOを進める。
結果を合わせてから、従来の選択・描画へ進む。新cacheやapplication queue、
新しいworker数の設定、順位付けや認定規則の変更はない。
Leanのtask scheduler自体の待ち行列がなくなるという主張ではない。

要求は子taskを所有し、通常終了・例外・取消のいずれでもcancel/joinを
済ませてから共有batchのreleaseへ進む。poolにはDB IOを持ち込まない。
純粋な対の射影の値はLeanで等しいが、これはOSの並行実行や終了時間の
証明ではない。nativeの寿命検査と実フックで別に確認する。

時計を読む位置が前に動くため、graphDeadlineの式は元のままでも、
期限ぎりぎりの実行の振る舞いまで全入力で等しいとは主張しない。
失敗時の副作用の順序も同じとはしない。同じsnapshot・質問・モデル・
予算の本文、意味検索とシナプスの完了、ACKで実際の経路を検査する。
producerの実バイトに応じた私有cacheを分け、比較元を上書きしない。

事前固定の順序は親→候補→候補→親、各armは3prime・4並行・16並行。
初回cache準備は波の時間と分ける。p99、80人の継続利用、一般98%、
総tokenや品質の改善を、この性能試験から主張しない。

二つずつの観測で安定した性能差やp99は立証していない。
メモリ削減も確認できない。数秒の目標を満たす根拠がないため未採用。
この配置をまた主解決として試さない。

事前確認7件と比較92件の全99本文が基準とbyte一致し、ACKが成立した。
測定waveの84件で意味検索・シナプスが完了し、元DB全ファイルのhashは不変。
基準本文の全体保存18/18・部分込み19/19は維持するが、これは最終headの
性能fixtureの値である。前の6モデル段階や一般98%へ拡張しない。
候補SHAは`6630a8bbb9010f9f53be5a932f452601dc3e92428aeea9324bec7ee25b7fd4b6`。

[実link検査](native.json)と[source比較](sources.json)は、直接変更Handoffのみ、
helper追加1、埋込literalの変化3か所、既存module除去0を確認した。
[native call](native-calls.json)には実discoveryからpipelineへの呼出しと
元の純粋式が残っている。これはC compiler全体の証明ではない。
Leanの対の射影の等式は公理なし。nativeの通常終了・callback例外・
期限切れ・親の取消の[検査](controls.json)も通過した。

親A1では`retained unfinished session maintenance`の警告が出た。
配送の合格と背景maintenanceの完了は分け、後者を完了したとはしない。
hookの5試行すべてのguardは正常終了し、所有processを残していない。
最初の候補専用warmは1.270秒で、cloneした索引を再利用できた。
モデル・埋め込み実装・予算・候補順位・認定規則は比較間で同じ。
有料回答モデル0、総token/品質の採用比較0/18、本体採用0を維持する。

この結果は、独立した計算とIOを重ねるだけでは16並行の全体時間を
大きく減らせなかったことを示す。poolの追加や配置調整を繰り返すより、
既存project imageにある不変な原文・引用対応を要求ごとに再構成する仕事を
減らす必要がある。すべてのpool設計を否定した結果ではない。

終了した候補のsource/build/実行体/私有cacheと99clientの状態・重複本文を
[削除](retired.json)した。各armの削除を合わせて15,375項目、
1,198,260,263論理bytes。archiveは作っていない。4,690の現行compiler入力、
現行runtime/制御器/原DB/正本本文のhashを確認し、削除後の親runtimeも
[native検査](native-after-retirement.json)を通過した。MiniLMと使用中cacheは保持する。
退役した候補を再開可能とは扱わない。

開発時のmetadata検査4件とnative controlのコンパイル1件の失敗は
[別記](development-failures.json)し、成功したhookへ混ぜていない。
削除用metadataの最初の検査も、保持する実行体の隣に任意のlib directoryが
あると仮定して止まった。この時点ではrootを削除しておらず、存在する
compiler入力だけを検査する修正後に削除と保護hashの検査を完了した。
