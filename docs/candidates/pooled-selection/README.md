# Selection on the Lean worker pool

Isolated diagnostic, **not adopted**. The user permits a pool when its ownership
and performance justify it. This partial candidate does not establish that.

Only the pure selection phase of the publication service moves to a default
Lean task. The checked view remains borrowed until the child finishes; deadline
handling cancels and joins the child before releasing that borrow. The pure
result is definitionally the existing selector. This equality does not prove OS
scheduling, cancellation or bounded thread creation. Lean's task machinery has
its own scheduling queue; this is not a claim of a queue-free runtime.

Both arms unset `LEAN_NUM_THREADS` on the same ten-core host, keeping native
numerical-library thread limits at one. Six independent initial hooks first
preserved canonical body bytes, ACK, semantic and synaptic completion, and all
32/32 DB-present originals. These hooks are not the requested seed followed by
six actual answering-model stages.

The fixed ABBA comparison then produced:

| Parent A | 4.277 s | 10.883 s | 3,744,512 |

Every wave completed all clients with byte-equal bodies, semantic search,
synapses and ACK. All four guards exited zero, left no owned processes and did
not trigger the resource bound. Initialization was outside the timed waves.

There is a small latency difference and **no demonstrated RSS improvement**.
Two observations per arm do not establish a stable latency improvement or p99.
The profile differs from older one-thread observations, so those older RSS
numbers are not a causal control. No local 40/80-client trial is needed under
the user's updated instruction. The current local sixteen-client target of a
few seconds remains unmet.
