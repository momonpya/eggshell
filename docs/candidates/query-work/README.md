# Prepared query work: profile and rejected citation-reach candidate

The citation-reach candidate is **rejected**. It removes a measured repeated
calculation and preserves actual bodies, but does not demonstrate whole-hook or
load improvement. The isolated source is restored to `e6e9e2e5`'s source and the
rejected executable is deleted. Product adoption remains false; answering-model
calls are zero and matched inclusive-token/quality comparisons remain **0/18**.

## Evidence before changing code

`shared-startup-build/StudyMain`, the retained sixteen-owner cut, 82 original
input/output records, the original question, MiniLM and the 120,000-character
limit. One explicit warm precedes them. Existing handoff/service tracing is
enabled, so their times include instrumentation. Both deliver the two frozen
original fields; all original heads remain unchanged.

Whole CLI hook processes take 6,859/4,421 ms. These are not p99 or causal speedup

Client automatic preparation takes 25 ms and service/finish 295/289 ms. The old
LLVM selector stack therefore cannot simply be reused as the current diagnosis.

An additional two-second native sample targets a verified direct child query

## Candidate and negative results

The [isolated patch](candidate.patch) precomputes each parent's reachable Work
membership set once for the exact All/Union inputs, then filters parents for
each candidate. It retains parent order, duplicates and text. A Lean theorem
proves equality with the original filtered sequence for arbitrary inputs; the
declaration audit connects the actual indexed query to those helpers. Ordinary
ContractAudit passes. No graph/candidate, ranking, numerical, freshness,
budget or completion-authority rule changes.

The two unsampled candidate hooks deliver both original fields and their
88,172-byte bodies are **byte-identical** to both parent hooks. Nevertheless,
whole process times are 8,143/5,117 ms, above the parent's 6,859/4,421 ms. The
candidate's running indexed query takes 3,537 ms, versus 3,102 ms in the initial
parent profile. This pair does not establish improvement.

A matched-window candidate sample shows the intended repeated graph walk
disappearing: the main old branch contains 356 recursive sample observations,
while the candidate has only small 1–2-observation branches, including the
one-time citation preparation. Recursive counts are not CPU percentages, and
eliminating that branch is not proof of a whole-program speedup. The sampled
candidate's running hook takes 5,223 ms. [Candidate stack](candidate-stack.txt).

After confirming actual work removal, the unchanged retained-cut native
eighty-reader protocol is run once on the candidate. It fails:

| Ordinary cold readback | Parent | Candidate |
| --- | ---: | ---: |
| Both required fields delivered | 35/80 | 21/80 |
| Operation admission reached | 80/80 | 74/80 |
| Failed clients | 45 | 59 |

Three candidate successes use meaning search and eighteen lexical fallback;
every success contains both original fields. All eighty input captures are
complete and all sixteen original heads remain frozen. Candidate measurements
span 18,356–29,816 ms, including failures. Final observations exist for 24
operations: queue median/max 20,156/25,670 ms and work median/max 1,793/15,247 ms.
The unchanged 3.5 GiB stop is respected (2,843,088 KiB sampled peak), no guard
trigger occurs, and shutdown leaves no owned processes. The test exits nonzero
because of the 59 failed clients. This single pair does not isolate a causal
regression, but it supplies no basis for keeping the candidate in the active
implementation. The failed 80-query burst is not repeated unchanged.
