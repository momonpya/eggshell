# 原文候補の残差を保つ単独候補

2026-10-28、結果を見る前に固定。題材1の同じ実receiptから再構成した根拠束は1,465件で、選択器へ届くのは926件、539件が欠落する。7101行・128行を含む3つのclaim束はすべて欠落し、その中の1〜5範囲に対応する単位がない。必要なファイル行そのものは束縛できている。共有したfile/lineがある所有者でも、ファイル行に対応しなかった元出力の範囲が同じ所有者に残る。現在の`prepare`はcached行があれば原文record側を候補にしないため、この混在が束の欠落を起こしうる。

一つの修正を隔離候補で試す。cached行が覆う元出力の位置の和集合を作り、元出力全体からその集合を引いた残差だけを、同じ所有者のboundedな原文候補にする。元出力を丸ごと複製せず、コード行と残差で原文位置を覆う。特定のコマンド、言語、題材、正解位置の規則は加えない。raw原文のcontext費用はraw単位だけに課し、共有file行に元所有者のraw frameを課さない。残差にあるfocus/引用/導出のcueだけを同じ係数で計上する。認定・検索順位・値の係数・予算は変えない。

Leanでは、残差の任意の位置が「元の範囲内、かつ既存範囲の外」であることと、既存範囲の外を全て残すことを証明する。既存のmaterializeと最終の実packet予算検査は維持する。

同じlive DB・実private root・準備済みindex・質問を、新しいsessionの実フックで題材1だけ一度検査する。回答モデルは呼ばない。凍結5項目は監査専用で、候補に渡さない。未束縛範囲と束の欠落数が減るか、実配送3/5が改善するか、30秒以内に返るかを記録する。改善しなければ、この候補の重みや範囲幅を調整せず終了する。95%・数秒・総token改善が未達なら合格と呼ばない。AGENTSの同条件複数反復・総token・品質・期限の比較前に本体やREADMEへ採用しない。
