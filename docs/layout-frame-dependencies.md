# 選択した本文に観測済みの見出しを戻す診断

2026-10-31。隔離したLeanのモデルなし診断。**必要原文の改善なしで停止**。本体・README・releaseへ未採用。

グラフで到達した範囲を個々のscore/costで選別する現在の経路には、利用する仕事と根拠の関係を保持する義務がない。ただし、全子の同時調査を必要依存に変えたり、ヒューリスティックな消費辺を必須にしたりする理由にもならない。

保存済みの[R40の辺の監査](candidates/query-cache-llvm/missing-support.json)を再読すると、未配送の部分宣言へ届く消費3本は`Args`/`ToolChain`のidentifier一致で、dumpmachineの1本は`n`のidentifier一致だった。Compile境界には消費も支持も共引用もない。[該当行だけの分類](candidates/layout-frame-dependencies/retained-missing-relations.json)。これは保存済み監査の分類であり、新しいDB全件走査や意味的な不要性の証明ではない。用語の一致を必要依存の権限へ上げず、推薦の情報として保持する。

## 今回だけを検査した規則

過去のbounded record全体の強制閉包や、call名→定義全体、予約・重み・solverを再実行していない。今回の問いは、選択済みの原文の条件・見出しだけが抜け、その**観測済みlayoutの祖先行**を補うだけで直るかだった。

[LayoutFrameDependencies](../tools/research/LayoutFrameDependencies.lean)は、同じfile fingerprintで行番号が連続するrunだけを対象に、字下げの単調stackから直前の浅い行をparent IDとして用意する。空行は親を作らず、欠けた行、別file/fingerprintを越えない。文字列、質問、言語、ツール、VCS、正解リストは規則に入らない。準備後は選択行の親だけを辿る。これはlayoutのヒューリスティックであり、構文解析や意味的必要性、認定を与える関係ではない。一般出力を新たにこのfile layoutへ強制変換していない。

Leanでは、checked結果が元の要求行と全parentを保持し、追加行が元の配列内にあることを示した。prepareが全言語の正しい構文木を作る証明ではない。fixtureでは入れ子・空行・閉包の再実行・read gap・同じ字下げの別項目・別fingerprintを検査した。native closureの67 objectはsource stampまで一致した。

実入力は固定R40・sealed supplement込み8,276行。既に配送された3題材の本文を再解析した。3件のlabel非依存の追加集合を全て固定した後に、従来の凍結正解3/7/4を評価器だけが開く。開発者が過去のラベルを知っている開発セットの診断であり、盲検・保留評価とは呼ばない。

[全結果](candidates/layout-frame-dependencies/audit/result.json)。一度の準備で4,623 parentを作った。追加を予算で削る前から必要原文は増えなかった。実本文は118,309〜118,716文字なので、単にこの追加を後付けすると従来の120,000文字を超える。これを予算内の実配送成功とは数えない。補完による別の必要原文の退行を隠す再選択も行っていない。

診断の閉包は約0.8秒/題材。これは独立した最終checkを含むリスト実装で、運用の高速実装やp99の値ではない。準備の22 msだけを全フックの性能へ外挿しない。guard全体8,674 ms、関連RSS標本最大130,864 KiB、終了0・残存0だった。元DBのheadとdataのSHAは固定値と一致した。

この結果で、字下げの親補完をruntimeへ進めず終了する。正解に合わせてgapを越える、関数名や構文別の例外を増やす、粒度や係数を調整する、追加の回答モデルを呼ぶことはしない。新フック・warm・seed・回答モデルは0回。98%配送・総token改善・80人の継続利用は引き続き未達である。採用にはAGENTSの同一条件・同数複数反復・3題材両周の総token改善と品質・期限を別に確認する必要がある。

次に必要なのは、観測から実際に得られる仕事の依存を、単なる同時所属・語の一致と混同しないこと。既存の3辺だけから全ての未配送項目を必須と決められるという仮定は置かない。今回の否定的な診断を、重みの再調整や別名の全文閉包へ戻る理由にしない。

[終了後の削除](candidates/layout-frame-dependencies/retired.json)で、診断用buildの54通常file・107,359,124 logical bytesと準備設定を削除した。元DBと保持する3 runtimeのhashは削除前後一致。新しいDB/cacheは作っておらず、archiveも作っていない。最初のメモリ上限による準備失敗と、binder/adapterのbuild修正も小さい記録に残した。失敗したshell cleanupはプロセス作成前に拒否されたため、固定した所有path・終了済みguard・保護hashを検査するLeanの削除器で完了した。
