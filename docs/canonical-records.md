# 共通原文の途中で切れた候補を閉じる

canonical-selection-auditで、Compileの条件と結論を全部含む候補がないことを確認した。
隔離候補に、元行のインデックスだけを扱うLeanの原文record閉包を加えた。
観測された空行境界、または先頭行から字下げされた連続行とその終了境界を使う。
ファイル指紋と元の行番号が連続し、2,048文字以内のまとまりだけを閉じる。
元の要求行は残し、閉包に入れたrecordは全部を残し、追加される行も元の配列に存在することを証明した。
証明の範囲は保存された原文の完全性である。
数値のproducer・順位・RRF・重み・3辺の依存recipe・認定・鮮度の規則は維持した。

空行だけを使った最初の候補は、実際の必要範囲を候補化できなかった。
ソース、実行ファイルの復元情報、成功した証明・native試験と失敗した到達検査を保存し、
この版での全6段階の再実行には進めなかった。
字下げによるrecordも使う候補では、保存済みの候補を使ったLean診断で、
Compileの全12行を含む候補が0件から1件になった。正解範囲はこの事後診断だけに渡した。

その後、全ソースと実行ファイルを固定し、題材1から全6段階を実フックで各2チャット検査した。

| 利用 | 題材 | 2チャットの所要時間 | DB内の必要原文の欠落 |
| --- | --- | --- | --- |
| 1周目 | 1 | 20,223 / 16,717 ms | 0 |
| 1周目 | 2 | 20,471 / 18,152 ms | 0 |
| 1周目 | 3 | 20,053 / 18,039 ms | Compile境界 |
| 2周目 | 1 | 25,670 / 22,747 ms | 末尾の言語指定の警告 |
| 2周目 | 2 | 21,604 / 19,487 ms | 0 |
| 2周目 | 3 | 24,840 / 23,191 ms | 0（必要7項目すべて） |

12本文は全て前候補から変わったが、必要原文の欠落は段階順に0/0/1/1/0/0のままだった。
各段階の独立した2本文は一致した。全12件でACKのrpcCompleted/offerAcceptedがともにtrue、
shutdownはexit0だった。回答モデル・seedの新規呼出しは0である。
候補化の不足を直しただけでは、最終的な選択漏れは解消しなかった。この版も未採用とする。

全6結果とACKの保存後、監視を起動した実行セッションは終了コード143となり、guardファイルはrunningのまま残った。
正常終了へ書き換えず、その状態と観測を保存した。通常のguard成功とは数えない。
別の凍結済みLeanチェッカーを復元し、全6元DBの事実・出版済みpage prefix・元入力SHAと、
実stdoutのSHA・保存本文の対応を独立に検査し、全件を確認した。
試行中の最大記録RSSは2,169,584KiB。ビルドと独立監査のguardはそれぞれ正常終了している。

ビルド途中でlibrary interfaceとIRのcacheがなくなっていたため、110個のローカルmoduleを直列で再構築した。
ソースとコンパイル済み入力を記録し、nativeオブジェクトも同じmodule集合から揃えた。
record閉包、依存束、実フックの元データ・指紋・共通費用・認定境界のnative試験とContractAuditは通った。

入力・失敗した候補・全試行・source freeze・リンク入力・実本文・ACK・独立監査は
`candidates/canonical-records-review.json`からたどれる。
通常runtime・README実績・releaseへの採用0、総トークンと品質の改善は未計測。
次は選択時の共通費用を調べる。現在のplannerは全候補に対するsource-statusの予約を固定費に入れている。
選ばれた所有者だけに必要な費用を共有ノードへ移せるかを検証し、順位や重みを再調整する試行へ戻らない。
全Phases0–6の目標はactiveのままである。
