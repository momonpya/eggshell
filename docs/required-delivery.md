# 必要履歴95%の判定

2026-10-26。`tools/research/RequiredDelivery.lean`で、必要原文の配送を整数で判定する。`19 × 必要件数 ≤ 20 × 配送件数`かつ分母が正であることを条件とし、空の分母を合格にしない。1件の欠落を許せるのは必要件数が20件以上の場合だけであることも通常のLean証明で確認した。

必要な単位は、同じ内容指紋を持つファイルの行範囲か、元のツール応答digest・Work・文字範囲で表す。MCP、一般JSON、ログ等も後者で扱える。代替の根拠は配送前に列挙し、DB内に存在すると確認できたものを固定する。別名で同じ根拠を重複登録しても分母は増えない。異なる必要単位が重なる場合は凍結前に分割・整理を要求し、評価器が都合よく数え方を変えない。

配送の判定には、実stdoutの元bytesと出典・元座標を照合して得た範囲を渡す。位置だけ、要約、出典のない一致文字列、途中の欠落、同じパスの別指紋は成功としない。凍結後に索引や検索で見つからなくなっても分母を減らさない。最初からDBにないものは別の一覧で報告する。

既存のLLVM向け`NativeTrialAudit`もこの評価器へ接続した。元DBから必要範囲の代替を確定してから実本文を検査し、`frozenEvidence`と`requiredDelivery`を出す。空の有効なフック応答は配送0件として扱う。既存のモデル採用ゲートをこの測定だけで通す変更はしていない。

検査では19/20と18/20の境界、ファイルと一般応答の混合、別名の重複、重なる必要単位、異なる指紋、部分配送、検索欠落後も不変の分母、空の分母を確認した。実際のJSONの元座標と配送表記を使い、出典のない本文・位置・改変bytesが配送成功にならないことも確認した。

[出版候補の試行](group-publication.md)では、必要コード2件を配送前の独立したDB snapshotに対して固定し、新しいチャットの実フックstdoutへこの監査を適用した。両方が原文で届いた。これは評価器の接続を確認する合成試行であり、対象実務全体に95%以上を実証したものではない。次の評価では題材・周・負荷条件別に分子・分母・未配送と全体micro/macroを報告し、全体平均で弱い条件を隠さない。

検証ビルドでは、研究用コードが可変のproject側にあるのに、親候補の古いinterfaceを利用できる経路も修正した。研究moduleはその候補で一度コンパイルし、以後は実ソースの一致するlocal cacheだけを利用する。監査コードの変更を古いinterfaceで検証したことにしない。
