# 既存数値daemonによるブロック採点候補

2026-10-25。元のbinary64投影を検証済みブロックから読み、16進文字列に戻さず既存の数値境界へ渡す候補を隔離実装した。[実装](../tools/research/block-score/)、[実行記録](candidates/block-score-review.json)。製品本体・READMEの実績・リリースには未採用。

## 境界

DBの選択、元headとの照合、完全なブロック検証、キャッシュ、寸法・サイズ制限、期限、停止、被覆情報、順位はLeanが扱う。既存の数値daemonが、DBごとに増殖しない64 MiB・最大1,024ブロックの共有キャッシュと、最大4,096ページの派生物用ページキャッシュを保持する。後者もchecksumを含む元のページ参照で照合する。検証済みの元バイトだけを再利用し、cold・変更・破損をフック内で修復しない。

NumPyの境界にはバイナリ入力用の50行の処理だけを追加した。元のbinary64をfloat32に変換し、従来と同じ行ごとの `np.dot` と質問小片の最大値を計算する。DB、保存、抽出器、router、選択、認定は含めない。GEMM・量子化・モデル変更は行っていない。MiniLMの元encoderコードのSHAは `1417508ca8aee8ee45bff632925ff6a23447d0d1a766d1c7411b775bc10a83f4` のままである。

小さな鍵・所有者情報だけを既存RPCへ送り、Leanで読み出した配列をバイナリpipeで数値処理へ渡す。実際に送るバイト数と寸法の一致は `BlockScore.Frame.byte_count` で証明した。推薦にWorkや鮮度の権限は加えず、e-class認定・字句・3種類のシナプス・配送選択は維持する。通常の明示warmはブロックの準備まで行い、現在の準備条件に結び付ける。`Main.lean` の研究用入口とハーネスも候補内だけに置いた。

## 同じ入力の部品比較

同じ5万窓DB、元99,969投影の出版、固定した3,125鍵と質問投影を使い、AB/BA/ABの3反復を事前指定した。すべてのスコアのFloatビット列・被覆情報・全数値順位が一致した。回答モデル・新seed・元文書の再埋め込みは0回。

| 反復 | 元reader初回/再読 ms | ブロック初回/再利用 ms |
| --- | ---: | ---: |
| 0 | 5,059 / 2,402 | 4,097 / 750 |
| 1 | 5,114 / 2,345 | 4,312 / 843 |
| 2 | 5,001 / 2,085 | 3,879 / 734 |

初回は128ブロックを検証し、再利用では新たなブロック検証0・3,125 hit、保持バイト数9,600,000。行ディレクトリの点照会は残る。再利用時の元読出しは603/690/585 msで、これは採点RPC時間の内数である。同点・複数質問・非有限値の拒否と次の要求での復帰、数値子プロセスの再利用、最後の所有者による終了も確認した。

OSのページキャッシュはflushしていない。反復1の最初の区間には別の読み取り専用ファイルSHA監査が重なったため、静かな環境での独立した速度反復とは扱わない。最初の試作は、値と順位が一致しても初回5,510・再利用4,179 msと遅かった。バッチごとにページキャッシュを作り直していたためで、失敗記録を残し、同じdaemonの派生物reader間でキャッシュを共有するように直した。

## 実フック

製品の生成関数で隔離prefixにlauncherを作り、通常の `UserPromptSubmit` を直接呼んだ。普段使うプラグインやmarketplace設定は変えていない。3つの固定した合成clock質問で、新しいmanager/chatから初回とACK後の継続を測った。LLVMの題材1・2・3とは別の規模試験である。

| 組 | 初回 ms（manager起動込み） | 継続 ms | 初回本文 bytes |
| --- | ---: | ---: | ---: |
| 0 | 7,364 | 4,284 | 9,316 |
| 1 | 9,420 | 4,733 | 9,311 |
| 2 | 8,631 | 4,719 | 9,304 |

全6回で意味検索が完了し、字句へのタイムアウト退避とフック内warmは0。初回は元観測を含む本文を配送し、継続は受領済みの記憶を重複配送せず空本文を返した。実stdoutと出版のSHA、初回/継続の区分、履歴12件のACK、所有managerの正常終了・endpoint撤去・残存プロセス0を確認した。認定の `completed` は0で、意味検索の完了とは区別する。

保存済みの親候補と同じ質問で比較できる組0は、初回9,316 bytesと継続の空本文が両方バイト一致した。親候補の実行体は削除指示に従って既に削除しており、新しい並行A/B速度比較ではない。他の2問の親本文との一致も主張しない。

最初の実フック試行は終了検査で失敗した。ハーネスがmanagerだけに `PLUGIN_ROOT` を渡し、直接起動したhook clientには渡していなかったため、launcherと実行体のmetadataが別の世代として扱われ、managerを置き換えていた。guardが残存プロセスを回収した失敗を残し、製品コードを変えず、両者に同じ環境を渡して新しいchatの初回から測り直した。

元DBの同じ出版に対する明示warm・再warmは147,573/142,930 msで、元埋め込み・投影生成・行列/router/ブロック追記はいずれも0。これは全文検証時間で、フックの時間ではない。環境設定を修正した再試行では、この完了済み準備を独立した準備専用記録として元headへ結び付け、現行 `Warm.required` の検査を経て再利用した。失敗したforegroundの合格記録にはしていない。

最終ビルド・ContractAuditと上記検査が完了し、最大合計RSSは1,775,808 KiB。3.5 GiB guardを維持し、失敗も含め全guardは終了・所有プロセス残存0、元DB/字句6ファイルのSHAも不変だった。初期のbuild・helperエラー、ディスクguardによる拒否、環境設定の失敗も記録に含めた。アーカイブは作っていない。

## 残る条件

これはブロック後段を通常経路につないだ結果であり、100万窓・複数DBの通常federation・共有並行利用・MCP実サーバー・大規模Pre/Post・p99・必要履歴recallの合格ではない。既存の軸方向routerも未変更であり、過去の数値上位8件との重なり0という否定的な結果を覆していない。次はデータに基づく分割と、未探索部分の安全なスコア上界を、厳密な採点を基準に評価する。

題材1・2・3と両周の、同条件での複数反復・失敗とcached input込みの総トークン・回答品質の比較は未実施。現在の採用条件を満たすまで未採用のままとする。部品の時間や配送本文の一致からトークン改善を推定しない。
