# 選択された出典だけに共通費用を課す隔離候補

欠落0件は未達。総トークン・品質の比較も未実施であり、本体・README実績・リリースへは採用しない。

従来のplannerは、全候補の関連グラフと所有者別の鮮度表示の予約を固定費に含めていた。
隔離候補では、その表示行を、実際に選ばれる出典が共有する費用ノードに移す。
必須の表示と、選択後に付く全体通知の予約は固定費に残す。
数値検索・MiniLM・順位・重み・3辺の依存recipe・原文record・認定・鮮度の判定は変えない。
文字数とUTF-8 bytesの両上限を維持し、最後に実際のpacket費用も検査する。

Leanの`ScopedCosts`は、完全な構造を持つscopeで表示を共有し、同じキーの異なる費用を拒否する。
重み・上限・候補数・cue incidenceの維持、固定費からの移動量、scope cacheの完全一致を検査した。
共通行の二重請求、非選択所有者、必須費用、矛盾する費用、引き過ぎをnativeで検査した。
実際の`fit`に接続する試験と既存の認定境界の試験、ContractAuditも通った。
これらは候補の実装検査であり、削減率の改善を意味しない。

最初の実走は題材1・2を通過し、題材3の初回でCompile境界が欠けた。
2周目の題材1は本文の必要範囲が揃ったが、ACKが期限切れとなり、shutdownも失敗した。
ここで検証は停止し、後続の3チャットは実行していない。

その後、候補ごとの分類で所有者の識別子を繰り返し作る処理を、所有者ごとに一度だけ作る形にした。
`active_annotated_exact`で順序を含む分類結果の一致を証明し、題材1から再実行した。
ビルドは正常終了したが、実走は次のとおりで、期限切れは解消しなかった。

今回実行した7本文は全て高速化前とバイト一致した。期限切れの本文も比較対象には残すが、配送成功には数えない。
位置だけが渡された範囲は本文配送に数えず、DB自体にない項目は「保存済みなのに欠けた項目」と分けた。
独立したLean監査で、実行した4段階の元DB事実・出版済みpage prefix・元入力SHAと、
実stdoutのSHA・保存本文との対応を確認した。欠けたチャットを既存本文で代用していない。

2回目の実走はguardが失敗を記録して終了し、残った子プロセスも回収した。成功へ書き換えていない。
記録された最大RSSは実走1,434,160 KiB、ビルド2,360,672 KiBで、停止上限は3,072 MiB。
回答モデル・seedの新規呼出しは0。各段階は新しい私有rootを使うため、利用辺が長期蓄積したときの改善も未計測である。

新旧両方の失敗、元ソース・実行ファイル・入力固定、証明・native試験、全7本文・ACK・独立監査は
`candidates/canonical-scoped-costs-review.json`からたどれる。
候補のLeanソースと、直前のrecord候補からのruntime差分も隔離して保存した。
全6段階の成功、総トークンと品質の比較、全Phases0–6の目標は未完了である。

その後、本文出力後の受領キー更新を独立に高速化した組み合わせでは全12フックを完走した。
ただし原文欠落は0/0/1/0/0/2で、元の原文record候補の0/0/1/1/0/0から別の箇所へ移った。
共通費用の変更による改善とは判断せず、未採用を維持する。
費用変更を含めず受領処理だけを接続した候補も独立に検査した。詳細は`delivery-ledger.md`。
