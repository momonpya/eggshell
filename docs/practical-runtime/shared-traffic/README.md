# 保存とLLVM照会を同時に流す

共有準備の修正候補 `0411e492…` の製品実行体を変更せず、native制御器だけを追加した。
同じサービスに、4 sourceを持つ共有プロジェクトへの保存と、保存済みLLVM調査DBへの照会を流す。
各照会が読むDBは一つで、複数DBを一つの照会で結合する試験とは分ける。
回答モデルは呼ばない。元の取得は未受理seedのため、モデル比較の完成seedにも数えない。

## 10クライアントの完了した系列

[実行前の条件](local-plan.json)は4保存、共有側3照会、LLVM題材1/2/3を各1照会の合計10クライアント、3回。
SessionStartとwriterの最初のUserPromptSubmitを済ませてから、10操作を同じbarrierで開始した。
測定区間のwriter操作は3ツールの実Pre/Post、Stop、明示keepを含む。
各回の終了後に現在の出版を数え、明示warmで準備が完了することも確認した。
原文監査は元DBから配送前に分母を凍結し、配送後の重い検証はサービス終了後に実行した。

この制御器は各イベントを通常の `codex-hook` で呼んだ。
登録済みpluginのUserPromptSubmit / Pre / Postと通常のSessionStartも同じ通常モードである。
Stop / SessionEnd / PostCompact / Interruptは `fast` で、native側の予算が2秒・pluginの上限が3秒。
compact時のSessionStartもnative側は `fast` 2秒だが、pluginの上限は30秒である。
これらの短いnative予算で同じ混在負荷が完走するかは未確認。
通常モードの成功を、そのまま登録済みpluginの全ライフサイクルの合格にはしない。

[結果と全要求](result.json)。baselineの12観測に、各回12観測を追加した。
各writerの操作区間はreaderの操作区間と重なっている。
最初のSessionStart、writerの最初のUserPromptSubmit、後続warm、原文監査は上表の同時操作時間に含めない。
10件のUserPromptSubmitだけを同時に走らせた結果ではない。

LLVMの全体保存された必要原文は、各回で題材1が3/3、題材2が6/6、題材3が5/5。
3回合計42/42、部分保存された原文を含める別指標は48/48だった。
共有側も9照会すべてで凍結した8定義が届き、合計72/72。
[配送前の分母](frozen-before-delivery.json)は、実行後に縮めていない。
DBに存在しない範囲は配送成功に含めず、部分保存を完全な範囲としても数えない。

18照会すべてで意味検索が完了し、字句fallbackは0。
実際の本文とstdoutはSHAごとに一度だけ保持し、各要求・時刻との対応をresult.jsonに残した。
LLVM3題材は、同じsnapshotの既存の復旧試験の本文・stdoutと[byte一致した](shared-bodies.json)ため、
その保存済みファイルを参照して重複6ファイルを削除した。今回の要求や時刻を過去の測定へ置き換えてはいない。
この一致を速度や総token改善の比較には使わない。
原DBのhashは不変、frontend/publisherは[正常終了](stopped.json)、guardも終了0・ownedPids空。
関連RSSの標本最大は4,002,592KiB（4,098,654,208 bytes）で、5GBの利用者上限と既存の保護線を維持した。

## 失敗を完了系列へ混ぜない

[先行試行のguard](earlier-attempts.json)と[途中までの実結果](earlier-traffic.json)を残した。

- 最初の16クライアント試行は、LLVMのcwdをfixtureの場所にした試験側の誤りで原文監査が拒否した。成功扱いにしない。
- cwd修正後は2回の原文監査まで成功したが、3回目で保護停止した。途中の保存期限超過の警告もあり、3回一式の合格ではない。
- 原文監査を負荷の後へ移しても16クライアントは保護停止した。制御器のRSSは約733→151MiBへ減った一方、モデル・サービス・hookプロセスを含む負荷全体は保護線に収まらなかった。

16クライアントを無変更で再試行せず、利用者が認めた当面の10以上という範囲で、
10クライアントの別条件を実行前に固定した。16の失敗を10の成功で上書きしない。
80人の継続負荷やp99、一般の98%配送、LLVMのモデルによる1周目・2周目、総token改善を示す結果ではない。

## 保存とフックの残る費用

出版を行う明示keepは12件とも377〜399ms、保存側のstderr警告は0。
Preは1,463〜1,797ms、Postは1,026〜1,261msだった。
[72件の既存受領記録](hook-profiles.json)では、サービス内dispatchはPre 372〜604ms、Post 148〜223ms。
差をDBの書込み時間と決め付けず、クライアントの起動・転送・stdout/receipt処理を含む残りの範囲として扱う。
この内訳を得るための追加負荷試験は行っていない。
次は、新しい高速化候補を作る前に、実際に登録したfastイベントの予算でも保存が完了することを検査する。

[334 native object](native-local.json)が整合し、[差分](sources-local.json)は研究用制御器だけだった。
vector、3辺、e-class/認定、選択、モデル、期限、製品実行体は変更していない。
採用0、有料比較0/18。AGENTS.mdの同条件・複数反復・総token・品質の採用条件を維持する。

結果を保持後、[試験DB/cacheと今回だけのsource/build](retired.json)を25,166項目・1,001,055,533論理bytes削除した。
archiveなし。原DB、現行実行体、必要なモデル・native入力は保持してhashを確認した。
