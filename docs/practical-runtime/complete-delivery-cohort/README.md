## 50万文字が必要な根拠量なのか

[原文範囲の容量診断](capacity.json)は、上記の配送前凍結リストだけを使う。
各項目についてDB内の完全な原出力範囲を一つ選び、共有による節約をせず
文字数を足すと、次の上界になる。

| 題材 | 凍結項目 | 必要な原出力範囲の文字数上界 |
| --- | ---: | ---: |
| 1 | 5 | 2,182 |
| 2 | 7 | 2,911 |
| 3 | 6 | 1,995 |

原出力は1始まりの閉じた文字区間として数える。ファイルの行区間の幅を
文字数として比較しない。これは**出典枠・前提を含まない診断値**であり、
既存選択器がこの大きさの有効なpacketを作れると証明したものではない。
正解の範囲を製品へ渡したり、この診断packetをモデルへ投入したりしない。

50万文字を根拠そのものの必要量とは説明できない。次の検査では必要な原文・
質問・製品・配送枠を固定し、無関係な記録だけを増やす。入場、graph展開、
選択、描画のどこで必要項目が落ちるかと時間・メモリを測る。
**DB増加試験は未実行**。落ちるたびに枠を広げる評価にはしない。
モデル試行を増やす前に、この設計上の問題を切り分ける。

## 終了・復旧の検査側の修正

最初のnative gateは、管理サービスを止めた後のwarmがサービスを自動起動し、
継承されたstderrのpipeを保持したため停止した。保存された8観測を失った
失敗とは区別する。[記録](initial-native-gate.json)。所有を確認した残存group
だけを停止し、元の失敗を成功扱いにせず残した。

検査側は、日誌を専有workerで終えてからサービスを起動し、warm終了後に
停止する順序に修正した。先にサービスを起動した最初のfinalizeは背景索引と
競合し、`DB synaptic index owner is busy` を返した。
[失敗記録](initial-finalization.json)。ここは検査器側の誤りである。
既存の「同じworkerをslice間で保つ」修正も再利用し、同じseedを69.386秒で
正常に準備した。モデルを取り直していない。

管理付きwarmのnative gateは、実Pre/Post/Stop・8観測・17日誌・消費1・支持16・
共引用4、DBだけからの新規2/2配送を確認し、29.764秒で正常終了した。
[保存](native-gate.json)、[復旧](native-gate-recovery.json)、
[配送](native-gate-recall.json)。実MCPサーバーは使っていない。
この小fixtureの成功は、後のseedで判明した再生前のサービス起動順序を直す前の
ものである。順序修正後は上記seedのfinalizeを正常実行し、現行のfixture側も
型検査したが、その最終版の小fixtureを再実行したとは主張しない。
単独CLIのstderr継承を製品側で修正した、という主張はしない。

取得用の封印した実行体とsourceは保持し、終了・次段階準備の制御器だけを
別に検証した。[製品境界](product-core.json)はMainの依存表346項目との
source/literal差分の交差がないことを確認する。
[差分監査](preparation-sources.json)の変更は研究用の6 moduleだけである。
vector・work graph・synapses・e-class・認定の製品コードは変更していない。
