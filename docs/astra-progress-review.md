## 判断

実用目標への進歩が不足している、という指摘は妥当。必要原文の基準は題材1/2/3で2/4・4/6・3/5（9/15）、実hookは約15〜18秒、正式6段階は0/6のままである。表示短縮は8/15へ悪化して撤回、現在focusと過去引用の分離も実際の束選択を各1件から7件へ変えたが9/15のままで撤回した。「信号が選択へ届けば直る」という説明だけでは、この結果を説明できない。

Astraの今回の提案は、新seed・両周6段階・同時期freshの一括pilotを止め、利用の辺の因果診断を一問に絞ること。大きなpilotでは原文・過去回答・利用辺が同時に変わる。freshとの差は記憶全体の効果であり、三つ目の辺が改善に寄与したかは分からない。同じ開発セットへのselector・重み・表示・束の追加調整も止める。

## 追加検査の訂正と終了

相談と並行して、製品runtimeを変えずに空DBのgeneric出力・MCP形状出力・部分引用・source-only回復を確認した。最初の二度は研究側の部分引用検査で停止した。最初は専用のopaque入力を追加したが、それだけでは解消せず、原因の説明として不十分だった。

実装は部分引用を作る際に`Read.quotations`を引用自体のdigestへ狭める。一方、古い検査はそのdigestが含まれると失敗候補から除外していた。検査を、厳密に長い元のspelling、原文内の一致箇所、その箇所から得る`Quotation.locate?`のwitnessと永続化されたRead全体の一致で判定する形へ訂正した。ファイル座標からの支持や、record全体との一致だけでは通らない条件を維持した。製品へは変更していない。

訂正後はnative tool 8件／portable origin 8件／日誌17件、任意出力の内容対応15件、opaqueな部分引用2件、supports 13件、coquoted 10件、private usage 4件を確認。source-onlyの別私有rootで出版は不変、supports 13件とcoquoted 10件も再構築できた。sessionとpublisherは終了code 0、endpoint削除、残存owned process 0。MCPはfixture形状で、実サーバーの検証ではない。回答モデル呼出しは0件で、この検査を15項目の配送改善には数えない。

失敗と成功のtrace、guard、runtime digestを[記録](candidates/feedback-pilot/generic-verified/generic-gate/result.json)へ残し、終了したfixtureのDB/cacheは削除した。新seedの未実行planは退役させたままで、今回の相談後に新seedやfreshの回答を開始していない。
