# 推薦セルに合わせた元ベクトルの配置

2026-10-25、[前の実フック候補](partition-native.md)で残った、最初の意味検索のtimeoutを対象にした。Leanの[隔離実装](../tools/research/cluster-blocks/)と[実行記録](candidates/cluster-blocks-review.json)。5万窓の固定3組では、初回・継続の全6回で意味検索と配送が完了した。総トークンと品質の比較はまだ行っておらず、製品・README実績・リリースには未採用である。

## 原因と変更

学習したセルで元鍵を選んだ後、以前の12座標による物理配置から値を読んでいた。そのため近い推薦窓が多くのブロックへ散り、直接providerの4,132窓には1,398回のブロックmissがあった。Lean BLAKE3の式を保ったinline化だけでは、実フックの意味検索は5/6回だった。

`ClusterBlocks`は、同じ学習済みの分岐で全投影をセルへ割り当て、セル内の最大32行を連続したブロックとして保存する。discoveryだけでなくfocus専用の投影も同じ配置に含める。前景の`BlockScore.ready`はこの配置を必須とし、元の値・被覆情報・鍵を同じreaderから返す。推薦枠4,096鍵、物理行枠8,192、元の順位と同点規則、NumPyのfloat32変換と行ごとのdotは変えていない。Pythonの追加もない。

準備は元の物理順の1走査とセルごとのバッファで行う。64 MiBの上限は準備処理1件あたりであり、全並行DBの合計上限ではない。満杯の32行はすぐ書き出し、全体のバッファ予算に達した場合も書き出して空にする。元のbinary64と被覆情報をそのまま運び、質問によるコピーや全ベクトルの常駐は前景に加えない。

元行列、元入力ブロック、学習索引のheadに拘束し、新しいデータとreadyを同じPageMapのheadで原子的に出版する。DB別のsemanticサイドカー配下なのでチャットIDを含まない。保持済みのreaderは旧rootを読み続ける。形式番号や互換用readerは追加せず、準備されていない場合は前景で作らない。

これは推薦用の数値配置の変更である。Workの認定、Exactの足跡、Unionの生成元、シナプス、鮮度確認の規則は変更していない。推薦セルも物理ブロックも、completedの権限を持たない。

## 値と更新の検査

バッファの実バイト数が行数×幅に等しいことと、32行の上限から実バイト数の上限が従うことを通常Leanで証明した。既存の検証済みブロックからの切出し長と、追記で旧prefixが保たれる証明も使用する。ビルドで許可した証明依存だけであることを検査し、ContractAuditも通した。IO全体の正しさを証明したとは扱わない。

小規模DBは、discoveryに入らないfocus専用投影を加えた67行すべてで元の値・被覆が一致した。物理ブロックが同じモデルセルの行だけを持つこと、cold照会が準備しないこと、再実行の書込み0、68行への更新後の旧pin維持、行列変更時の古い配置の拒否を確認した。破損コピーは実際の`vector block checksum mismatch`で拒否された。最初の型・record layout・依存したバッファのlookupのビルド失敗も残す。

5万窓の元DBは、discoveryとfocusを合わせて99,969投影である。独立監査で全307,104,768 bytesと全被覆情報を元の配置と比較し、すべて一致した。この監査だけは期待する列を512 MiB以下に制限して保持し、前景や製品の準備には持ち込まない。内部の照合区間38,365 ms、監査プロセス全体48,366 ms、最大合計RSS 739,536 KiBだった。

新配置は3,379ブロック。準備75,935 ms、書込み335,778,988 bytes、バッファ最大25,952,256 bytesで、上限内だった。明示warm全体は207,206 msで、元文書の再埋込み、元行列・元物理router・入力ブロック・学習索引の追加書込みはいずれも0。再warmの新配置確認は6 ms・書込み0だが、元キャッシュ全体の検証を含む再warm全体は131,002 msである。

## 実フック

同じ固定DB、キャッシュ済み質問、MiniLM、harness、推薦枠、3質問と3組を事前に固定した。明示warm、全投影の独立照合、再warmを別プロセスで終え、前景には準備heapを残さない。再利用する準備はsource headと実際の`Warm.required`で照合した。

| --- | ---: | ---: | ---: |
| 0 | 7,877 ms | 4,366 ms | 元の観測9,308 bytes |
| 1 | 6,829 ms | 4,507 ms | 元の観測9,300 bytes |
| 2 | 6,883 ms | 4,378 ms | 元の観測9,322 bytes |

全6回で意味検索が完了し、前景のwarm要求は0。初回は原文を配送してACKを確認し、継続は確認済み履歴を重複配送しない正しい空だった。stdout・本文・出版SHA・初回/継続の状態、manager終了とendpoint撤去も照合した。この課題で作業を省略する権限のcompletedは0であり、意味検索の処理完了と区別する。

初回のdiscovery採点のブロックmissは185 / 180 / 186、継続は全組0だった。最初の質問の直接providerではmiss 185、hit 3,947、保持16,106,496 bytes、採点3,503 ms、うち読出し3,145 msだった。前の配置の完全providerと4,101所有者の全順位・根拠窓・related・coverageが一致した。前の候補で意味検索が完了した質問2・3の初回配送本文もバイト一致した。

これらは事前固定した少数の測定であり、OS cacheはflushしていない。一般的な速度改善率やp99、LLVMの題材1・2・3の成績にはしない。元DB・字句・元数値ファイルと入力ブロックの16ファイルは実行前後でSHAが一致した。全guardは終了済み・所有プロセス残存0、途中失敗を含む最大合計RSSは1,499,120 KiB。追加の回答モデル、新seed、元文書の埋込みは0で、アーカイブも作っていない。

## 残る仕事

前景のtimeoutをこの固定条件では解消したが、維持管理は全体metadata、元の軸配置の入力、denseな全量出版に依存している。今回の配置は約320 MiBの派生コピーを追加するため、これを100万窓以上の最終保存構成とは扱わない。次は重複した旧物理配置への依存を除き、変更分だけの準備・segment・再集約と圧縮へ進む。

実際の複数DB・共有並行利用、100万窓以上、p99、MCPの保存前policy、独立した必要原文の保留条件は未完了。routerの再現率も変えておらず、以前の自己照会での取りこぼしを消したとは主張しない。同条件の題材1・2・3、両周、複数反復による総トークンと品質の採用条件、および論文の残りも継続する。
