# 選択結果を変えずに最後のフックを期限内へ戻す

共通原文の隔離候補に、既存の選択結果を保つ二つの改善を加えた。
最初は元の順位係数を候補行ごとに再計算せず共有するもの。全11本文のバイト一致は確認したが、
最後の段階で初回本文がincompleteとなり、もう一方も受領を拒否された。
その失敗を`candidates/canonical-weights-review.json`に残した。

次はgreedyの候補比較中に選択済みリストを複製せず、勝った候補だけを具体化するもの。
所属判定は元リストと一致することを証明したhash lookupに置き換えた。
元の`SharedCoverage.choose?`全体との等式をLeanで証明し、その等式だけでコンパイルする。
順位、安定した同点処理、費用、価値、依存閉包、予算、単独候補との比較は同一である。
MiniLMと数値producer、推薦と認定の境界も変更していない。
nativeの依存束・予算検査とContractAuditは通った。

同じ保存スナップショット・質問・固定native harnessで、題材1から全6段階をやり直した。
各段階は独立した新規チャット2件で、私有query/usage/sessionを引き継がず、公開ready cacheだけを複製した。
元head/pages/provenanceのSHA、原文の事実、出版済みpage prefixの不変性も全段階で通った。

全12件で本文が返り、ACKのrpcCompleted/offerAcceptedがともにtrue、shutdownもexit0だった。
同じ段階の2本文は一致し、前候補の完成本文との比較も12件すべてバイト一致した。
最後の段階では、前候補の受領に失敗した全文を**本文だけの比較対象**とした。
以前の受領失敗まで成功扱いに変えるものではない。
最大RSSは2,396,592KiB、guardの終了はexit0、3GiB停止条件も発火していない。

残る二つの欠落は、DBに存在する原文が本文から落ちる選択上の失敗である。
1周目題材3の元スナップショットに存在しない別の2項目とは分けている。
期限内の本文と受領は回復したが、必要原文の完全配送は未達である。
回答モデル・seedの新規呼出しは0。品質と総トークンの改善は未計測なので未採用のまま保ち、
通常runtime・README実績・リリースには取り入れていない。

全試行とバイト比較は`candidates/canonical-deferred-review.json`からたどれる。
